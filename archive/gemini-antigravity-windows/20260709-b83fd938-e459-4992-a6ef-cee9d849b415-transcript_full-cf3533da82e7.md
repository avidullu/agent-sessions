17: ## 1. Problem Statement
18: 
19: The **Agent Sessions** repo (`Projects/Agent Sessions`) is a Python-based private
20: archive for coding-agent sessions. It discovers, extracts, and exports agent
21: transcripts as Markdown/PDF files. Currently it supports Codex, Claude, Gemini,
22: Grok, and DeepSeek — but **VS Code Copilot Chat and other VS Code-based agents
23: have no live routing mechanism**. Their session data is scattered across
24: `globalStorage` and `workspaceStorage` directories that the Python tool can only
25: treat as static inventory.
26: 
27: ### 1.1 What the Agent Sessions repo does today
28: 
29: | Step | Mechanism |
30: |------|-----------|
31: | **Discovery** | TOML-configured source roots with glob patterns |
32: | **Extraction** | Per-agent extractors (`@register("kind")`) that parse raw files → `ExtractedSession` |
33: | **Rendering** | `render.py` → Markdown with metadata header + transcript |
34: | **Indexing** | `archive/index.jsonl` + `archive/INDEX.md` |
35: | **Baseline** | Knowledge/replay system for analyzing archived sessions |
36: 
37: ### 1.2 The gap
38: 
39: - **Copilot Chat**: listed as `inventory`-only. Sessions are in
40:   `workspaceStorage/*/GitHub.copilot-chat/debug-logs/` (JSONL) and
41:   `chat-session-resources/` but no extractor exists.
42: - **DeepSeek V4**: has a `deepseek_request_dump` extractor, but only captures raw
43:   request text — no structured conversation, no metadata enrichment.
44: - **No live routing**: the Python tool is batch-oriented. A VS Code extension
45:   can provide real-time or near-real-time routing of finished sessions.

49: ## 2. Vision: The VS Code Agent Session Router Extension
50: 
51: A VS Code extension that acts as a **bridge** between VS Code's internal agent
52: session storage and the Agent Sessions archive pipeline. It is the first in a
53: suite of helper tools for processing agent session handoffs and transcripts.
54: 
55: ### 2.1 Core capabilities
56: 
57: 1. **Discover** — scan VS Code's `globalStorage` and `workspaceStorage` for
58:    agent session files (Copilot Chat, DeepSeek, and any future agent extensions).
59: 2. **Extract** — parse raw session formats into structured conversation
60:    transcripts (user ↔ agent turns with tool calls).
61: 3. **Render** — produce Markdown files in the exact format the Agent Sessions
62:    repo expects (metadata header + numbered transcript sections).
63: 4. **Route** — place rendered Markdown files into a configurable output
64:    directory (default: the Agent Sessions `archive/` dir or a staging folder).
65: 5. **Watch** — optional filesystem watcher that auto-exports sessions as they
66:    are completed or modified.

173: ### 2.4 Why aggregators are transparent to the architecture
174: 
175: The key insight: **model backends (Ollama, OpenRouter, LM Studio) are just API
176: endpoints**. They do not persist chat sessions. The VS Code extension that uses
177: them (Continue, Cline, etc.) is responsible for session storage.
178: 
179: This means the agent-session-router needs discoverers/extractors for the VS Code
180: EXTENSIONS (Category B), not for the backends (Category C). Once an extension's
181: storage format is understood, the router handles it identically regardless of
182: which backend model was used.
183: 
184: ```
185: ┌──────────────┐     ┌──────────────────┐     ┌─────────────────┐
186: │  Ollama       │     │  Continue.dev     │     │  agent-session- │
187: │  (backend)    │◄────│  (VS Code ext)    │────►│  router          │
188: │  No storage   │     │  ~/.continue/     │     │  → archive/*.md │
189: └──────────────┘     └──────────────────┘     └─────────────────┘
190: 
191: ┌──────────────┐     ┌──────────────────┐     ┌─────────────────┐
192: │  OpenRouter   │     │  Cline            │     │  agent-session- │
193: │  (backend)    │◄────│  (VS Code ext)    │────►│  router          │
194: │  No storage   │     │  globalStorage/   │     │  → archive/*.md │
195: └──────────────┘     └──────────────────┘     └─────────────────┘
196: ```
197: 
198: Adding a new aggregator-backed extension always follows the same 3-step recipe:
199: 1. **Install** the extension + run a test session
200: 2. **Locate** its session storage (check `globalStorage/{id}/`, `~/.{name}/`)
201: 3. **Write** a discoverer + extractor (~50 lines of TypeScript each)

258: #### 3.2 Key design decisions
259: 
260: 1. **Extractor registry pattern** — same as Agent Sessions' `@register("kind")`
261:    decorator, but in TypeScript. Each agent source gets a registered extractor.
262: 2. **Markdown format compatibility** — the renderer MUST produce the exact
263:    format that Agent Sessions expects:
264:    ```markdown
265:    # {source_name} / {session_id}
266:    ## Metadata
267:    - Source: `{source_name}`
268:    - Kind: `{source_kind}`
269:    - Source file: `{path}`
270:    - SHA-256: `{digest}`
271:    - Source modified: `{timestamp}`
272:    - Imported at: `{timestamp}`
273:    ## Transcript
274:    ### 1. user (2024-01-01T00:00:00Z)
275:    {message text}
276:    ### 2. assistant (2024-01-01T00:00:01Z)
277:    {message text}
278:    ```
279: 3. **Output routing** — configurable destination:
280:    - `agentSessions.archiveDir`: direct write into Agent Sessions archive
281:    - `agentSessions.stagingDir`: write to a staging area for manual review
282:    - `agentSessions.outputDir`: generic output directory

284:    already-exported sessions (same as Agent Sessions' `_can_reuse_record`).

286:    Sessions repo does its own post-processing (indexing, PDF, baseline).
