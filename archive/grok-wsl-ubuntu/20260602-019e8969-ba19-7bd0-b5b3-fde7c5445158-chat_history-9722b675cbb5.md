1→# Gmail Attachments → Google Drive
2→
3→A Google Apps Script that copies your Gmail attachments into a `GmailAttachments`
4→folder in Google Drive and keeps it updated as new mail arrives. You choose how
5→the attachments are organised (by content type, by month, or by year) and how
6→far back the first sync should reach.
7→
8→Originally a 2013 Chrome Web Store app; this is a modernised rebuild on the
9→**V8 runtime** with a TypeScript source, an esbuild build, and a local Jest test
10→suite. The web app runs **as each accessing user** (`executeAs: USER_ACCESSING`),
11→so it can serve just you, a small group, or a Google Workspace org — each
12→person's attachments are copied within their own account. See
13→[Multi-user deployment / publishing](#multi-user-deployment--publishing).
14→
15→## How it works
16→
17→- `doGet` serves a setup form (`html/index.html`).
18→- `processInput` stores your choices and schedules the first background run.
19→- `syncUserDrives` is a self-rescheduling time-based trigger that walks Gmail in
20→  30-day windows, copying allowed attachments into Drive while respecting a
21→  daily file cap (`MAX_FILES_ADD_PER_DAY`) and a per-run wall-clock budget.
22→
23→State lives in `PropertiesService` (user properties). Existing Drive files are
24→never modified — re-running setup only resets the script's own bookkeeping.

82→/**
83→ * A single sync pass:
84→ *   1. reschedules a fan-out of backup triggers (self-healing if one is lost),
85→ *   2. syncs forward in 30-day windows until it runs out of time, hits the
86→ *      daily file cap, or fully catches up,
87→ *   3. persists progress and schedules the next run.
88→ */
89→function runSyncOnce(): void {
90→  const today = new Date();
91→
92→  // On the first run of a new calendar day, summarise the previous day.
93→  maybeSendDailySummary(today);
94→
95→  // Recover state if the debug flag was cleared (e.g. properties were wiped).
96→  const debug = state.getDebug();
97→  if (debug == null || debug === "0") {
98→    state.setDebug("1");
99→    state.setLastSynced(new Date(today.getTime() - 365 * ONE_DAY).toJSON());
100→  }
101→
102→  // Create the backup triggers BEFORE deleting the current ones, so a failure
103→  // here can never leave us with no scheduled run.
104→  const previousTriggers = getSyncTriggers();
105→  try {
106→    newSyncTrigger(60 * ONE_MINUTE);
107→    newSyncTrigger(SIX_HOURS);
108→    newSyncTrigger(2 * SIX_HOURS);
109→    newSyncTrigger(4 * SIX_HOURS);
110→    newSyncTrigger(8 * SIX_HOURS);
111→    newSyncTrigger(28 * SIX_HOURS);
112→  } catch (e) {
113→    // Could not install new triggers; leave the old ones and try again later.
114→    logError("Could not install triggers: " + e);
115→    return;
116→  }
117→  deleteTriggers(previousTriggers);
118→
119→  const filesAddedToday = state.getFilesAddedToday();
120→  let added = filesAddedToday.added;
121→  const lastCountDate = new Date(Date.parse(filesAddedToday.date));
122→
123→  if (isSameCalendarDay(lastCountDate, today) && added >= MAX_FILES_ADD_PER_DAY) {
124→    logDebug("Used up all quota for today. Can't add more files.");
125→    newSyncTrigger(60 * ONE_MINUTE);
126→    return;
127→  }
128→  if (!isSameCalendarDay(lastCountDate, today)) {
129→    added = 0;
130→  }
131→
132→  const structure = state.getFolderStructure();
133→  let lastSynced = state.getLastSynced();
134→
135→  // Load the dedup set once; thread it through the run and persist at the end.
136→  let processedIds = state.getProcessedIds();
137→  const processedSet = new Set(processedIds);
138→
139→  // This run's contribution to the day's stats.
140→  const addedAtStart = added;
141→  let runErrors = 0;
142→  let runLastError = "";
143→
144→  // Folds one updateDrive result into this run's accumulators.
145→  const applyResult = (result: UpdateResult): void => {
146→    added += result.addedFiles;
147→    runErrors += result.errors;
148→    if (result.lastError) {
149→      runLastError = result.lastError;
150→    }
151→    for (const id of result.processedIds) {
152→      if (!processedSet.has(id)) {
153→        processedSet.add(id);
154→        processedIds = addProcessedId(processedIds, id);
155→      }
156→    }
157→  };
158→
159→  try {
160→    // Incremental mode is opt-in (ENABLE_INCREMENTAL_SYNC) so it rolls out
161→    // gradually over the proven date-window backfill. A stored historyId only
162→    // exists once a backfill has caught up while the flag was on.
163→    const historyId = ENABLE_INCREMENTAL_SYNC ? state.getHistoryId() : null;
164→    if (historyId) {
165→      // Incremental: process only messages added since the stored historyId.
166→      const changes = listAddedSince(historyId);
167→      if (changes == null) {
168→        // History expired: clear the cursor and re-scan a bounded recent window
169→        // (the next catch-up re-captures a fresh historyId). Overlap is safe —
170→        // dedup by message id and the Drive filename guard prevent re-copying.
171→        state.clearHistoryId();
172→        lastSynced = new Date(today.getTime() - THIRTY_DAYS).toJSON();
173→        logDebug("History expired; reverting to date-window sync.");
174→      } else {
175→        if (changes.messageIds.length > 0 && added < MAX_FILES_ADD_PER_DAY) {
176→          const threads = threadsForMessageIds(changes.messageIds);
177→          if (threads.length > 0) {
178→            applyResult(
179→              updateDrive(
180→                threads,
181→                structure,
182→                MAX_FILES_ADD_PER_DAY - added,
183→                processedSet,
184→              ),
185→            );
186→          }
187→        }
188→        // Advance the cursor so the next run only sees newer changes.
189→        state.setHistoryId(changes.historyId);
190→      }
191→    } else {
192→      // Backfill: walk forward in 30-day windows until caught up to today.
193→      // Capture the mailbox historyId BEFORE processing so mail arriving
194→      // mid-run is still picked up by the first incremental scan.
195→      const candidateHistoryId = ENABLE_INCREMENTAL_SYNC
196→        ? getCurrentHistoryId()
197→        : null;
198→      let fullSynced = false;
199→      while (
200→        hasTime(new Date(), today, MAX_RUNTIME_MS) &&
201→        added < MAX_FILES_ADD_PER_DAY &&
202→        !fullSynced
203→      ) {
204→        const maxToAdd = MAX_FILES_ADD_PER_DAY - added;
205→        const search = buildSearchQuery(lastSynced, new Date());
206→        logDebug("Query: " + search.query + "  files asking: " + maxToAdd);
207→
208→        const threads = GmailApp.search(search.query);
209→        if (threads.length > 0) {
210→          applyResult(updateDrive(threads, structure, maxToAdd, processedSet));
211→        }
212→
213→        fullSynced = search.isToday;
214→        if (added < MAX_FILES_ADD_PER_DAY) {
215→          lastSynced = fullSynced
216→            ? today.toJSON()
217→            : new Date(Date.parse(lastSynced) + THIRTY_DAYS).toJSON();
218→        }
219→      }
220→      // Caught up: switch future runs to the cheaper incremental path.
221→      if (candidateHistoryId && fullSynced && added < MAX_FILES_ADD_PER_DAY) {
222→        state.setHistoryId(candidateHistoryId);
223→        logDebug("Backfill complete; stored historyId " + candidateHistoryId);
224→      }
225→    }
226→  } catch (e) {
227→    logError("Some error in execution: " + e);
228→    state.setLastError(String(e));
229→    runErrors++;
230→    runLastError = String(e);
231→  }
232→
233→  // Fold this run into the day's accumulator.
234→  const dayStats = recordRun(state.getRunStats(dayKey(today)), {
235→    filesAdded: added - addedAtStart,
236→    errors: runErrors,
237→    lastError: runLastError,
238→  });
239→  state.setRunStats(dayStats);
240→
241→  state.setProcessedIds(processedIds);
242→  state.setLastSynced(lastSynced);
243→  state.setFilesAddedToday({ added, date: today.toJSON() });
244→  newSyncTrigger(20 * ONE_MINUTE);
245→}

71→/**
72→ * Copies every allowed, not-yet-present attachment from the given threads into
73→ * the GmailAttachments folder, organised per the user's chosen structure.
74→ * Stops once `maxToAdd` files have been written.
75→ *
76→ * `alreadyProcessed` is the set of Gmail message ids handled in previous runs;
77→ * such messages are skipped wholesale, avoiding a Drive `getFilesByName` probe
78→ * per attachment when an overlapping date window is re-scanned. Ids fully
79→ * handled here are returned in `processedIds` for the caller to persist.
80→ */
81→export function updateDrive(
82→  threads: GoogleAppsScript.Gmail.GmailThread[],
83→  structure: string,
84→  maxToAdd: number,
85→  alreadyProcessed: ReadonlySet<string> = new Set(),
86→): UpdateResult {
87→  const head = getOrCreateFolderInFolder(DriveApp, GMAIL_ATTACHMENT_FOLDER);
88→
89→  // Pre-load existing sub-folders so we reuse rather than duplicate them.
90→  const existingFolders = new Map<string, Folder>();
91→  const currentFolders = head.getFolders();
92→  while (currentFolders.hasNext()) {
93→    const folder = currentFolders.next();
94→    existingFolders.set(folder.getName(), folder);
95→  }
96→  logDebug("Already present folders: " + existingFolders.size);
97→
98→  const addedFiles = new Map<string, Folder>();
99→  const processedIds: string[] = [];
100→  let addMore = maxToAdd > 0;
101→  let hasError = false;
102→  let errors = 0;
103→  let lastError = "";
104→
105→  for (const thread of threads) {
106→    if (!addMore) break;
107→    for (const message of thread.getMessages()) {
108→      if (!addMore) break;
109→      const messageId = message.getId();
110→      // Skip messages we fully handled on a previous run.
111→      if (alreadyProcessed.has(messageId)) {
112→        logDebug("Skipping already-processed message " + messageId);
113→        continue;
114→      }
115→      let messageFailed = false;
116→      const from = message.getFrom();
117→      // GmailMessage#getDate is typed as the stripped Base.Date interface but is
118→      // a real JS Date at runtime.
119→      const date = message.getDate() as unknown as Date;
120→      const attachments = message.getAttachments();
121→      let lastHandled = -1;
122→      for (let a = 0; a < attachments.length && addMore; a++) {
123→        const attachment = attachments[a];
124→        lastHandled = a;
125→        const contentType = attachment.getContentType();
126→        const fileName = getAttachmentName(attachment.getName(), from, date);
127→
128→        if (!isAllowedContentType(contentType) || addedFiles.has(fileName)) {
129→          logDebug("Rejected file of type: " + contentType);
130→          continue;
131→        }
132→
133→        let folder = resolveFolder(
134→          head,
135→          existingFolders,
136→          structure,
137→          contentType,
138→          date,
139→        );
140→        if (folder == null) {
141→          // Unknown structure: drop it in the top-level folder for recovery.
142→          logError("Could not resolve directory; using top-level folder.");
143→          folder = head;
144→        }
145→
146→        try {
147→          // Skip if a file with this name already exists in the folder.
148→          if (folder.getFilesByName(fileName).hasNext()) {
149→            continue;
150→          }
151→          const blob = attachment.copyBlob();
152→          blob.setName(fileName);
153→          const file = folder.createFile(blob);
154→          file.setDescription(
155→            "Created from a Gmail Attachment from " +
156→              from +
157→              " sent on date " +
158→              date,
159→          );
160→          addedFiles.set(fileName, folder);
161→          Utilities.sleep(100);
162→          if (addedFiles.size === maxToAdd) {
163→            addMore = false;
164→          }
165→        } catch (e) {
166→          logError("Some problem with an attachment: " + e);
167→          hasError = true;
168→          messageFailed = true;
169→          errors++;
170→          lastError = String(e);
171→          Utilities.sleep(1000);
172→        }
173→      }
174→      // Mark the message done only if we handled all its attachments cleanly.
175→      // If we stopped early on the daily cap (lastHandled short of the end) or
176→      // hit a transient failure, leave it unmarked so the next run retries it.
177→      const completed = !messageFailed && lastHandled === attachments.length - 1;
178→      if (completed) {
179→        processedIds.push(messageId);
180→      }
181→    }
182→  }
183→
184→  return { addedFiles: addedFiles.size, hasError, errors, lastError, processedIds };
185→}

12→/**
13→ * Builds the Gmail search for the next 30-day window after `lastSynced`.
14→ *
15→ * `now` is injected (rather than read from the clock) so the windowing logic is
16→ * deterministic under test. NOTE: this intentionally preserves the legacy
17→ * behaviour of mixing a UTC upper bound (`Date.parse`) with local-time day
18→ * parts (`getFullYear`/`getMonth`/`getDate`) when formatting the Gmail
19→ * `before:`/`after:` strings, so the day boundaries follow the script's
20→ * configured timezone.
21→ */
22→export function buildSearchQuery(lastSynced: string, now: Date): SearchQuery {
23→  let query = "to:me in:all has:attachment -in:trash -in:spam ";
24→  let nextDate = THIRTY_DAYS + Date.parse(lastSynced);
25→  const today = now.getTime();
26→  let isToday = false;
27→  if (today < nextDate) {
28→    isToday = true;
29→    nextDate = today;
30→  }
31→  nextDate += ONE_DAY;
32→
33→  const afterDate = new Date(Date.parse(lastSynced) - ONE_DAY);
34→  const beforeDate = new Date(nextDate);
35→  const beforeQ = `${beforeDate.getFullYear()}/${beforeDate.getMonth() + 1}/${beforeDate.getDate()} `;
36→  const afterQ = `${afterDate.getFullYear()}/${afterDate.getMonth() + 1}/${afterDate.getDate()} `;
37→
38→  if (beforeQ === afterQ) {
39→    // Window collapses to a single day; just search "after yesterday".
40→    const yesterday = new Date(Date.parse(lastSynced) - ONE_DAY);
41→    const yesterdayQ = `${yesterday.getFullYear()}/${yesterday.getMonth() + 1}/${yesterday.getDate()} `;
42→    query = query + "  " + "after:" + yesterdayQ;
43→  } else {
44→    query = query + "before:" + beforeQ + "  " + "after:" + afterQ;
45→  }
46→
47→  return { query, before: beforeDate.toJSON(), isToday };

29→ * must fall back to a full sync). Only `messageAdded` events are requested.
30→ */
31→export function listAddedSince(
32→  startHistoryId: string,
33→): IncrementalChanges | null {
34→  const responses: HistoryListResponse[] = [];
35→  let pageToken: string | undefined;
36→  try {
37→    for (let page = 0; page < MAX_HISTORY_PAGES; page++) {
38→      const response = Gmail.Users.History.list("me", {
39→        startHistoryId,
40→        historyTypes: ["messageAdded"],
41→        pageToken,
42→      }) as HistoryListResponse;
43→      responses.push(response);
44→      if (!response.nextPageToken) {
45→        break;
46→      }
47→      pageToken = response.nextPageToken;
48→    }
49→  } catch (e) {
50→    if (isHistoryExpired(e)) {
51→      logDebug("History id expired; full sync required.");
52→      return null;
53→    }
54→    throw e;
55→  }
56→  return {
57→    messageIds: collectAddedMessageIds(responses),
58→    historyId: nextHistoryId(responses, startHistoryId),
59→  };
60→}
61→
62→/**
63→ * Resolves the distinct Gmail threads containing the given message ids. Threads
64→ * are de-duplicated by id so a multi-message thread is processed once. Messages
65→ * that can no longer be fetched (deleted since the change was recorded) are
66→ * skipped.
67→ */
68→export function threadsForMessageIds(messageIds: string[]): GmailThread[] {
69→  const threads = new Map<string, GmailThread>();
70→  for (const id of messageIds) {
71→    const message = GmailApp.getMessageById(id);
72→    if (!message) {
73→      continue;
74→    }
75→    const thread = message.getThread();
76→    threads.set(thread.getId(), thread);
77→  }
78→  return Array.from(threads.values());
79→}

44→      runs: parsed.runs ?? 0,
45→      filesAdded: parsed.filesAdded ?? 0,

**Code-level feedbacks (issues, tech debts, small-to-medium improvements)**

- **Unsafe / non-portable attachment filenames (naming.ts:13 `getAttachmentName`)**: Raw `from` (typically `"Name <email@ex.com>"`) and `date.getHours():getMinutes():getSeconds()` with literal colons are concatenated directly. Resulting names contain `<`, `>`, and `:` (e.g. the docstring example and the test expectation at naming.test.ts:14). Windows forbids these; Drive for desktop (explicitly recommended in ui.ts:69 and the success message) will fail to sync or produce errors for many users. Original attachment names are appended unsanitized too. No `sanitizeForDriveName` helper exists.

- **Fragile and mixed date/time handling (query.ts:17–46, naming.ts:18–40, drive.ts:119, sync.ts:121 etc.)**: Heavy use of `toDateString().split(" ")` (locale- and TZ-dependent month abbrs), `Date.parse` + local `getFullYear/getMonth/getDate` for Gmail `before:/after:`, and the `as unknown as Date` cast for `GmailMessage.getDate()`. The query builder even has a comment admitting it preserves "legacy behaviour" of mixing UTC epoch math with local day parts. This is already a source of off-by-one window bugs across TZ changes and will destroy fidelity for any date-sensitive extraction (flights, statements with period dates, etc.).

- **Overly strict and incomplete attachment whitelist (contentTypes.ts:5–49)**: Only ~40 exact MIME strings; images lack `image/png` (very common for receipts/screenshots), no `image/webp`, limited audio/video, no `application/octet-stream` fallbacks, no handling of `; charset=...` or `application/pdf; name=...` variants. `isAllowedContentType` is a pure `Set.has`. Future grocery/flight/bank work will hit this immediately for real mail. Bodies are never inspected (see below).

- **Full in-memory blob materialization on every candidate (drive.ts:151)**: `attachment.copyBlob()` + `createFile` with no `getSize()` guard, no streaming, and no early skip for large items. Bank statements, high-res scans, and zips will blow the 6-minute wall-clock or JS heap. Paired with `Utilities.sleep(100)` (or 1000 on error) after every attempt—brittle, non-adaptive, and wastes the already-tight `MAX_RUNTIME_MS` budget.

- **PropertiesService as the only persistent store + tight size hacks**: Short keys (`"f"`, `"l"`, `"pid"`, ...), `MAX_PROCESSED_IDS=400` specifically "to fit under 9 KB", JSON blobs with no schema version, and `clearAll()` on every re-setup (ui.ts:37). `setLastError` writes but there is no `getLastError` reader. This design is already at its limit for cross-run dedup; it is fundamentally unsuitable for storing extracted entities, per-message extraction status, or per-extractor state.

- **Stringly error handling and minimal observability**: All paths do `String(e)`, last-error overwrite, and `logError("Some problem with an attachment: " + e)`. `logger.ts` is just level prefix + `String(data)`. No structured fields, no messageId context, no per-extractor metrics. `ENABLE_DEBUGGING` is a boolean flag that requires rebuild. Daily stats (stats.ts) only count files/errors at the copy layer.

- **Within-run and cross-run dedup are filename- and messageId-based only**: `addedFiles` Map by constructed name (drive.ts:128) + `processedSet` of messageIds (with the "only mark done if we handled the last attachment" logic). No content hash, no Gmail attachmentId/partId, no subject+date key. Fine for "copy once" but insufficient once you care about "this is the same receipt as the one emailed yesterday."

- **No email body, subject, or label access anywhere**: `getAttachments()` + `getFrom`/`getDate`/`getId` only. Zero calls to `getPlainBody`, `getBody`, `getSubject`, `getRawContent`, or advanced `Users.Messages.get`. The base query hard-codes `has:attachment`. This is the single biggest blocker for the described future (most flight confirmations, bank alerts, coupons, and many receipts are body-first or body-only).

- **Folder and structure management is rigid and reload-heavy**: Every `updateDrive` does a full `head.getFolders()` preload + per-attachment `getFilesByName` probes (unless the messageId was in the processed set). Only three static structures chosen once at setup; changing structure leaves orphan folders. `getFolderNameForStructure` returns `""` for unknown and falls back to the root (with a logged error). No per-sender, label-driven, or nested options (ROADMAP already calls this out).

- **Hybrid incremental logic is complex and mostly dormant (sync.ts:160–225, gmailHistory.ts, historySync.ts)**: `ENABLE_INCREMENTAL_SYNC=false` by default for good reason. Capture-before-process, 404 fallback that rewinds `lastSynced` by 30 days, `threadsForMessageIds` N+1 fetches, `MAX_HISTORY_PAGES=20`, and loose `isHistoryExpired` string matching on the advanced service error shape. The state machine is clever but will be a maintenance surface once extraction adds its own cursors and re-processing needs.

- **Other smaller debts**:
  - Magic trigger fan-out and intervals (6 backups + 20m tail) in sync.ts.
  - `resolveFolder` / `getOrCreateFolderInFolder` do linear scans and can create same-name folders (Drive allows it).
  - UI is 2013 static HTML + `google.script.run` + `parentNode` hack; `processInput` does zero validation on `folderStructure`.
  - Build is esbuild + fragile footer globals + `globalName` (entry.ts + esbuild.config.mjs); adding entrypoints touches multiple places.
  - `historyId` + processed IDs + stats are all independent JSON blobs; no coordinated snapshot or compaction.
  - Tests are strong for pure modules (excellent isolation of query/naming/historySync/stats/processed) but the shells require heavy global mocking; no golden email samples or extraction-oriented tests yet.

The code is overall clean, well-modularized (pure logic vs. GAS shells), heavily tested for its current scope, and shows real care for GAS quotas, locks, self-healing triggers, and dedup. Many of the "debts" are direct consequences of the original "just copy attachments reliably" charter.

**Architectural improvements (oriented to high-fidelity extraction of grocery bills, flights, bank statements, receipts, coupons, etc.)**

The current system is a quota-aware, per-user, trigger-driven *attachment archiver*. Email extraction for life organization requires treating mail as a *structured data source*, not a bag of files. The biggest change is that "copy if MIME allowed" becomes the (optional) leaf of a classification + parsing pipeline.

- **Decouple ingest from extraction**. Produce a stable, rich `EmailMessage` shape (id, threadId, subject, from/to/cc, date, labels, plainBody, htmlBody, attachments with metadata + optional content ref) once per message. Current `GmailThread[]` + `getAttachments()` path is too narrow. This lets you re-run better extractors over history without re-copying blobs, and supports body-only items (itineraries, alerts, coupons).

- **First-class classification + pluggable extractors**. Add a classifier stage (sender domain + subject keywords + lightweight body heuristics today; LLM later) that assigns types with confidence: `Receipt` (sub: grocery/shopping), `FlightItinerary`, `BankStatement`, `Coupon`, `TravelDoc`, etc. Then a registry of `Extractor` implementations that know how to turn (message + attachment or body) into a normalized entity. Support multi-extractor and cross-source fusion (email confirmation + PDF ticket). Version the extractors so you can detect stale extractions.

- **Storage model that is not "more folders of raw files"**. Keep the raw archive (it's still valuable) but add a queryable extraction layer:
  - Structured records (JSON sidecars next to the Drive file, or Sheets per type, or a single "LifeIndex" Sheet with messageId + entityType + extracted JSON + Drive file link).
  - Stable entity keys for dedup (e.g., `receipt:${merchant}:${amount}:${date}:${sourceMsgId}`).
  - Provenance everywhere (source messageId(s), attachment index, extractor version, extraction timestamp, confidence).
  - Support for user corrections and re-extraction.

  PropertiesService + short-key JSON will not scale here.

- **Replace or augment the processed-IDs set with extraction-aware cursors and status**. You will need "last fully extracted up to X for extractor v2", per-message extraction status, and the ability to run a "re-extract window for new rules" without duplicating entities. The existing hybrid history + date-window backfill is a good skeleton; extend it rather than duplicate the complexity.

- **Handle rich + non-attachment content and heavy formats**. This means:
  - Conditional or separate queries that drop `has:attachment`.
  - Body parsing (HTML stripping, date/amount/merchant regex or better parsers).
  - PDF text/OCR (Drive file + advanced Drive or the classic "upload as Google Doc then read text" trick; or accept that some fidelity requires external steps).
  - Image handling (flag for later OCR; don't always copy the pixels).
  - Container formats (.zip receipts, .ics calendars, .csv statements).

- **Quota, cost, and pacing redesign for "expensive" work**. Copying is relatively cheap; running an LLM or even a non-trivial PDF parser per item is not. You will need per-item time budgets, separate daily extraction caps, prioritization (recent + high-confidence senders first), deferral of heavy items, and metrics on "extraction time / tokens / API calls". The current `MAX_FILES_ADD_PER_DAY` + wall-clock loop will need siblings.

- **Better folder / organization strategy + virtual views**. Physical folders (byContentType / byMonth / byYear) are too static. Move toward metadata-driven or query-driven organization. Long-term the "smart life organizer" surface is probably not just Drive folders—it may be Sheets dashboards, Calendar events auto-created from flights, Tasks from action items in receipts, or a small webapp UI. Support Shared Drives (already on ROADMAP).

- **State, schema, and migration story**. Introduce a versioned schema for persisted state and for extracted entities. Provide a way to "reprocess from date X with extractor set Y" from the setup UI or a maintenance page. Make `clearAll` less destructive (or add an "archive my extraction metadata" step).

- **Observability and feedback that matches the goal**. Per-classifier and per-extractor success/failure/ambiguity rates, not just "files added." Ability to surface "messages that matched no extractor" or "low confidence extractions" for review. Structured logs with messageId. Optional richer notifications.

- **UI / configuration / operations evolution**. The 2013 form will need pages for: which extractors to enable, custom sender/domain rules, review queue, "re-extract this message", export, and accuracy feedback. Because everything runs as the accessing user, a richer single-page HtmlService app (or CardService if you go the add-on route) becomes attractive. Multi-user / Workspace org deployment story will need to consider shared configuration vs. per-user rules.

- **Platform reality check for high fidelity at scale**. Apps Script + Gmail advanced service is excellent for reliable, in-account, zero-extra-infra archiving and lightweight triggers. It is a poor environment for serious PDF parsing, HTML DOM work, or LLM calls at volume. Plan for a spectrum:
  - Pure-GAS conservative extractors (regex + known formats + Drive OCR) for the easy 70%.
  - Optional UrlFetch to a trusted LLM / Vision endpoint (with user consent + privacy update) for the hard cases.
  - Long-term possibility of a thin "watcher + archiver" Apps Script + a separate processing service that still writes back into the user's Drive/Sheets under their authority.

- **Preserve and extend the current strengths**. The separation of pure testable logic, the lock + trigger self-healing, the hybrid sync design, the "mark done only on clean completion" rule, and the per-user isolation are all valuable. New extraction code should follow the same "shells around pure functions" pattern and keep the same ruthless respect for quotas and 6-minute boundaries.

- **Other forward-looking items**: content-addressable or hash-based dedup for attachments that get re-mailed; support for message updates (rare but possible); label-driven routing ("if user has 'receipts' label, treat specially"); and making the raw archive optional or configurable per type once extraction is trustworthy.

The project is in an unusually good position for this evolution precisely because it was recently rewritten with clean boundaries and tests. The main risk is trying to bolt rich extraction onto the existing "walk threads, copy allowed attachments" loop instead of introducing a proper ingest → classify → extract → persist pipeline. Start by modeling the richer `EmailMessage` and a couple of narrow extractors (e.g., "PDF whose filename or subject smells like receipt") while keeping the copier working unchanged.
