## 1. WHAT BREAKS WITH APPLICATION-LEVEL ENCRYPTION

### 1.1 Loss of SQL Queryability on Encrypted Numeric Columns

When you encrypt transaction amounts or balances at the application level before storing them in plain SQLite:

- **Exact-match queries only:** `WHERE amount = 50000` requires deterministic encryption to work, where the same plaintext always encrypts to the same ciphertext. This enables exact equality comparisons.
- **Range queries break completely:** `WHERE amount >= 50000 AND amount <= 100000` fails because encrypted numbers are opaque bytes; the database cannot compare encrypted values numerically.
- **Aggregations require homomorphic encryption:** `SELECT SUM(amount)` cannot be performed on encrypted columns without homomorphic encryption (a theoretically sound but computationally expensive and impractical technology for general use). Standard AES-GCM or Fernet cannot perform computations on encrypted data.
- **ORDER BY breaks:** `ORDER BY closing_balance` is impossible with encrypted columns — the database has no way to sort opaque ciphertexts in numeric order.
- **GROUP BY breaks:** `GROUP BY merchant` on encrypted merchant names fails unless using deterministic encryption, which leaks patterns.

**Source:** [Microsoft Learn: Always Encrypted — How queries against encrypted columns work](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/always-encrypted-how-queries-against-encrypted-columns-work?view=sql-server-ver17) — encrypted columns support **only exact equality (=) and IN** operations with deterministic encryption; everything else requires the application to decrypt client-side.

### 1.2 Deterministic Encryption's Critical Leakage Problem

The only way to make `WHERE amount = X` work is **deterministic encryption**: same plaintext → same ciphertext, always. But this creates **frequency-analysis vulnerability**:

- An attacker observing the encrypted values can infer which transaction amounts appear most frequently (e.g., salary deposits always same amount; fixed bill payments repeat).
- **Frequency-ranking attacks** can reconstruct plaintext values by matching frequency distributions. If the attacker knows income patterns or typical amounts (salary, rent, utilities), frequency analysis may leak those exact values.
- This is **not theoretical**: [Information Leakage in Encrypted Deduplication via Frequency Analysis](https://arxiv.org/pdf/1904.05736) (ACM Transactions on Storage, 2021) demonstrates frequency analysis breaks deterministic encryption in practice.

**For muneem's use-case (personal finance with highly repetitive patterns — same salary, same bills, same subscriptions):** deterministic encryption leaks the entire transaction pattern even if individual values are encrypted.

## 4. HYBRID PATTERN: TRANSPARENT DB + SELECTIVE APP-LEVEL

The **only** sensible hybrid is:
1. **Full-DB encryption via SQLCipher** (primary hardening, transparent, preserves all queries)
2. **App-level encryption for non-queryable PII** (narration, merchant names, raw OCR text) using PyCA cryptography

### What to Encrypt at Application Level

- **Narration/description fields** — free-form text, not queried, low-value in leakage
- **Raw merchant names** — stored as-is, not normalized, can be encrypted
- **OCR output** — intermediate extraction text, not persisted long-term
- **Customer notes** (not in current schema but future)

### What to Leave Plaintext (for SQL)

- **Amounts** — required for `WHERE amount >=`, `SUM()`, `AVG()`, range queries
- **Dates** — required for `WHERE txn_date BETWEEN`, time-series ordering
- **Account balances** — required for `ORDER BY closing_balance`, trend analysis
- **Account numbers** — required for `WHERE account_number =` (exact match, low cardinality, not sensitive given amounts are visible)
- **Transaction dates / value dates** — required for temporal queries
- **Category codes** (if added) — required for `GROUP BY`

### Does This Reduce Sensitivity?

**No, not meaningfully.** The combination of plaintext amounts + plaintext dates forms a **near-unique fingerprint** of the entire transaction ledger:
- The sequence of 50 transactions with dates and amounts uniquely identifies a person's financial life.
- Encrypting merchant names adds minimal real protection when the amounts and dates are visible.
- An attacker with amounts + dates can infer merchant identity (a 10,000 INR debit on 15th of each month is rent; a 500 INR daily debit is groceries).

**Conclusion:** Hybrid doesn't solve the core problem. The right answer is **do not store unencrypted financial data on disk at all** — which is what SQLCipher solves.

## 5. APP-LEVEL VS TRANSPARENT DB ENCRYPTION: COMPARISON TABLE

| Dimension | Application-Level (AES-GCM/Fernet) | Transparent DB (SQLCipher) |
|-----------|--------------------------------------|----------------------------|
| **SQL Queryability** | Breaks: no `WHERE amount >=`, no aggregation, no ORDER BY | ✅ Full: all queries work |
| **Exact-match queries** | Yes, with deterministic encryption | Yes, naturally |
| **Leakage risk** | High: frequency analysis defeats deterministic | Very low: attacker sees ciphertext only |
| **Performance overhead** | Per-field encryption/decryption (moderate) | Page-level encryption (5–15% overhead typical) |
| **Key management** | Application must manage keys, caching | Single key per database, OS keychain |
| **Operational complexity** | High: schema design, serialization, field selection | Low: drop-in transparent |
| **Schema modifications** | Requires schema migration for encrypted fields | No change to schema |
| **Backup/restore** | Encrypted blobs portable but queryability lost | Entire DB encrypted as single file |
| **Multi-process access** | Possible but requires key distribution | Single-user local access natural |

## 6. WHEN APP-LEVEL ENCRYPTION IS BETTER

Application-level encryption (PyCA cryptography) is the right choice **only** when:

1. **You have multi-tenant SaaS** and the database server itself is untrusted (needs end-to-end encryption from client → storage). Single-user muneem doesn't fit this.
2. **You need encryption in transit + at rest with key material never touching the server.** Not needed for local SQLite.
3. **You're protecting specific sensitive fields that are never queried** (SSN, credit card PAN, vault comments) while other fields remain plaintext. Use this selectively within a SQLCipher DB, not instead of it.
4. **You need field-level access control** (different users see different fields). Single-user, so not applicable.

**For muneem:** None of these apply.

## 9. CONCLUSION: APP-LEVEL IS NOT PRIMARY HARDENING FOR MUNEEM

**Statement:** "Is app-level encryption appropriate as the PRIMARY hardening for muneem?"

**Answer:** **No.**

**Reasons:**
1. **Breaks SQL queryability** — the core requirement. `WHERE amount >=`, `SUM()`, `ORDER BY`, `GROUP BY` all fail on encrypted amounts/dates.
2. **Deterministic encryption (the only workaround) leaks patterns** — frequency analysis defeats it for a ledger with highly repetitive transactions (same salary, same bills, same subscriptions).

5. **Operational simplicity** — single key in OS keychain, no schema redesign, drop-in replacement for sqlite3 (same PEP-249 API).

**Recommended approach:**
- **Primary:** SQLCipher for transparent full-database encryption at rest.
- **Secondary (optional):** PyCA cryptography for non-queryable metadata (narration, free-form descriptions) if additional defense-in-depth is desired.

Both solutions meet muneem's hard constraints (permissive licenses, local-first, Windows + Linux wheels available, cross-platform Python 3.11–3.13 support).

### Executive Summary

## PART A: THREAT SCENARIOS & WHAT EACH ENCRYPTION LAYER STOPS

### Scenario 1: Physical Disk Theft / Hardware Discarded
**Threat**: Attacker has physical access to the storage media; user is offline.

| Scenario | FDE Only (BitLocker/LUKS) | FDE + SQLCipher | Notes |
|----------|--------------------------|-----------------|-------|
| **Stolen drive, attacked offline** | ✅ Stops (if TPM+PIN or strong passphrase) | ✅✅ Stops (defense-in-depth) | FDE is sufficient for this threat. SQLCipher adds zero marginal value if the key is in the OS keychain on the same disk—the attacker extracts the keychain entry and unlocks the database. |

### Scenario 2: Cloud Backup Sync (Backblaze, OneDrive, Google Drive, etc.)
**Threat**: Database file is synced to cloud storage; attacker breaches cloud provider or account.

| Layer | FDE Only | FDE + SQLCipher | Notes |

| **Local copy** | ✅ Encrypted at rest on disk | ✅✅ Double-encrypted | FDE protects the local copy. |
| **Cloud copy** | ❌ **NOT encrypted at rest in cloud** | ✅ Cloud sees encrypted blob | FDE applies only to local storage. Cloud provider stores plaintext (or applies their own encryption, which is opaque). **SQLCipher is essential here.** |
| **In-transit to cloud** | Depends on sync client (usually TLS) | Same (TLS covers network) | SQLCipher doesn't affect network encryption; TLS does. |

**Verdict**: SQLCipher is **critical** if backups are synced to uncontrolled cloud storage. FDE alone is **insufficient** for this threat.

### Scenario 3: Malware Running as User
**Threat**: Ransomware, spyware, or trojan executes in user context (no privilege escalation).

| **Malware reads plaintext DB from disk** | ✅ Encrypted at block level, not visible | ❓ **Encrypted file, but key is in keychain** | FDE is effective *if* the disk is not mounted or the malware can't bypass volume lock. ## PART D: SQLCIPHER vs. ENCRYPTION APPROACHES

### Option A: SQLCipher (Full-Database AES-256 Encryption)
**What it does**:
- Encrypts entire SQLite file at the page level (4 KB pages)

- Transparent to SQL queries (WHERE, aggregates work without decryption changes)
- Key provided via `PRAGMA key = 'passphrase'` or hex string

**Advantages**:
- ✅ Transparent: Existing SQL queries unchanged
- ✅ Integrity: HMAC detects tampering
- ✅ Can be used with keyring-provided key: `conn.execute(f"PRAGMA key = '{key_from_keyring}';")`
- ✅ Prebuilt wheels available (sqlcipher3-wheels, rotki-pysqlcipher3, sqlcipher3-binary)
- ✅ Platforms: Windows, Linux (x86_64, ARM supported)

**Disadvantages**:
- ❌ **Key must be provided at every connection** (no persistent "unlock" of the file)
- ❌ If key is in keychain + malware can access keychain, DB is decrypted
- ❌ Performance: ~10-30% slower than plaintext SQLite (cipher overhead)
- ⚠️ **License**: BSD 3-Clause (Zetetic, Community Edition)—permissive, safe

**Query performance on encrypted data**:
- ✅ WHERE clauses: No degradation (encrypted index comparison works)
- ✅ Aggregations (SUM, COUNT, AVG, GROUP BY): Work transparently on numeric fields
- ✅ ORDER BY, LIMIT: Full support

#### **Operational Issues**

**WAL Mode & Backup/Restore:**

SQLCipher (and SQLite3MC) both suffer the same WAL (Write-Ahead Logging) complications:

- **Backup Problem:** Simple file copy (`shutil.copy()`, `cp`, `fs.copyFile()`) of the `.db` file while WAL is active leaves `.db-wal` and `.db-shm` files behind, creating an **inconsistent snapshot → instant corruption** on restore.
- **Safe Backup:** Must use `BEGIN IMMEDIATE; backup_api()` or `VACUUM;` before copying, OR delete `.wal` + `.shm` files after restore.
- **Critical Fix:** SQLCipher 4.14.0+ includes a WAL-reset database corruption fix from SQLite 3.51.3. Apps in WAL mode must upgrade. See [SQLCipher 4.14.0 Release](https://discuss.zetetic.net/t/sqlcipher-4-14-0-release/7186).
- **WAL Encryption Bug:** In older versions, `.wal` file could remain unencrypted while `.db` and `.shm` are encrypted; deleting `.wal` + `.shm` after backup restore works around this. See [Couchbase Lite Issue #1233](https://github.com/couchbase/couchbase-lite-ios/issues/1233).

**Query Performance:**

Both tools add overhead:
- Encryption/decryption per page (4 KB by default)
- Negligible on typical personal finance DB sizes (< 100 MB, < 1M rows)
- Noticeable on very large tables (> 10M rows), but muneem is single-user, year-scale data

**Migration & Debugging:**

- **Cannot open encrypted DB with plain `sqlite3` CLI.** Must use `sqlcipher` binary or Python binding.
- **Key rotation:** SQLCipher/SQLite3MC support `PRAGMA rekey` to change the encryption key.
- **Transparent queries:** Both preserve full SQL queryability (WHERE, ORDER BY, aggregates) on encrypted data — the key insight for muneem.

#### **Security Advisories**

**SQLCipher CVEs:**
- [CVE-2020-27207](https://www.cvedetails.com/cve/CVE-2020-27207/): Use-after-free in SQLCipher 4.x < 4.4.1 (via sqlcipher_codec_pragma). **Fixed in 4.4.1+.**
- [Critical DoS in older versions](https://security.telekom.com/): SQL injection via crafted queries to trigger DoS. **Fixed in 4.5.3+.**
- **No known critical CVEs in recent versions (4.5+).**

**SQLite3MC:**
- No dedicated CVE database, but inherits SQLite's CVE fixes. Actively maintained; latest stable is 3.51.3 (bundled in apsw-sqlite3mc 3.51.3.1).

## (3) Key-management design

**Recommended: random 256-bit key in the OS keychain via `keyring`.** This matches how muneem already handles OAuth tokens, and is the right default for a *single-user, frictionless* tool.

```
First run:  key = secrets.token_bytes(32)  →  keyring.set_password("muneem", "db-key", hex)
Every open: key = keyring.get_password("muneem", "db-key")
            conn.execute("PRAGMA key = \"x'<64-hex-chars>'\"")   # raw-key form
```

Two important details:

- **Pass the key as a raw hex key, not a passphrase.** SQLCipher's `PRAGMA key = 'string'` runs the string through PBKDF2 key derivation; `PRAGMA key = "x'<64 hex>'"` supplies the 256-bit key directly and **skips the KDF**. Since the key is already random and full-entropy, the raw-key form is correct and faster — KDF stretching only matters for low-entropy human passphrases. ([SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/))
- **Keychain backing:** Windows → Credential Manager via DPAPI (scoped to the user SID); Linux → Secret Service (GNOME Keyring / KDE Wallet). `keyring` (MIT) auto-selects. ([keyring](https://pypi.org/project/keyring/))

**Passphrase + KDF — when, and how.** A user-typed passphrase (run through **Argon2id**, OWASP params, or PBKDF2-HMAC-SHA256 ≥600k iters as a FIPS-friendly fallback) is *stronger against a stolen file* because the key is never stored — an attacker must brute-force it. But it adds per-launch friction and breaks the frictionless model. **Offer it as an opt-in** ("lock with a passphrase"), not the default. ([OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html))

**Rotation.** Support `PRAGMA rekey = "x'<new-hex>'"` behind a `muneem db rotate-key` command: generate a new random key, `rekey`, then overwrite the keychain entry. Trigger only on suspected compromise — no scheduled rotation needed for a single-user local key.

**What to avoid (be explicit):**
- ❌ Key or passphrase in source, `.env`, config files, or CLI args/argv (argv is world-readable on the process table).
- ❌ Logging the key, the `PRAGMA key` statement, or full connection strings.
- ❌ Reducing KDF iterations (only relevant if you *do* use a passphrase).
- ❌ Treating the keychain as protection against malware running *as the user* — it isn't (see Risks). It defends against other users, casual access, and a stolen file/disk where the attacker lacks your logged-in session.

## (5) Top risks / gotchas for implementation

1. **WAL + temp files / backup corruption (highest-risk operational issue).** SQLCipher encrypts WAL, journal, and temp files transparently — good. **But** never back up by copying the `.db` file while WAL is active: you'll miss/desync `-wal`/`-shm` and produce a corrupt snapshot. Use `PRAGMA wal_checkpoint(TRUNCATE)` then the **SQLite Online Backup API**; or on restore, ensure `-wal`/`-shm` are handled atomically. Also: pin a recent SQLCipher (the `sqlcipher3` 0.6.2 wheel bundles current 4.x) to get the SQLite **3.51.3 WAL-reset corruption fix** carried into SQLCipher 4.14.0+. ([SQLite WAL backup guidance](https://sqlite.org/forum/forumpost/2ea989bbe9), [SQLCipher 4.14.0](https://discuss.zetetic.net/t/sqlcipher-4-14-0-release/7186))

2. **`PRAGMA key` must be the first operation on the connection**, before any other statement (including reads of `sqlite_master`). Validate the key immediately with `SELECT count(*) FROM sqlite_master;` — a wrong key throws "file is not a database" / "file is encrypted." Fail with a clear muneem-level error, not a raw stack trace.

3. **Raw-key vs passphrase `PRAGMA key` mismatch is a silent footgun.** If you store a raw 32-byte key but open with the plain-string form (or vice-versa), the DB won't open and the error looks like corruption. Standardize on the `x'...'` raw-hex form everywhere and centralize it in `db.connect()`.

4. **Migration is one-way and destructive if mishandled.** `sqlcipher_export` writes a *new* encrypted file; keep the plaintext original until the encrypted copy is verified (`PRAGMA integrity_check` + a row-count/bookend reconcile against the bank SUMMARY, consistent with muneem's existing validation pattern), then securely delete the plaintext.

5. **Debugging loses the plain `sqlite3` CLI.** An encrypted DB can't be opened by stock `sqlite3` or DB Browser-without-SQLCipher. Document using the `sqlcipher` CLI (or DB Browser for SQLite *with* SQLCipher), and provide a `muneem db dump` that opens with the key and emits SQL for inspection. Don't let this tempt anyone into leaving a plaintext copy around.

6. **Performance: ~5–15% typical overhead**, page-level. For muneem's scale (single user, ≤ low-millions of rows) it's negligible. If ever needed: raise `PRAGMA cipher_page_size`/`page_size` (can recover 5–30%) and benchmark — but don't pre-optimize. ([SQLCipher performance notes](https://www.zetetic.net/sqlcipher/sqlcipher-api/))

7. **Threat-model honesty (set expectations in docs):** keychain + SQLCipher defends against **stolen file, cloud-backup exposure, other OS users, and a powered-off stolen disk**. It does **not** defend against **malware running as the logged-in user** — that attacker can read the keychain and dump decrypted pages from RAM. Don't oversell it. The passphrase-lock mode (Phase 2) is the only thing that raises that bar, at a usability cost. ([NIST SP 800-111](https://csrc.nist.gov/pubs/sp/800/111/final))

8. **`:memory:` and CI fixtures:** in-memory and temp DBs aren't the encryption target; keep regression/Layer-1 fixtures on plaintext stdlib `sqlite3` so non-sensitive tests stay simple and the encrypted path is exercised by a dedicated test.
