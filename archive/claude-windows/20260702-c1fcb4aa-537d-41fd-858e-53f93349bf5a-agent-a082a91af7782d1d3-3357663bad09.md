## What

Fixes audit finding **R1-03**: `GET /api/source/{video_id}` called `storage.acquire_local_input` on **every** request, and for a REMOTE-backed video (`gs://` / `s3://` / `gdrive://`…) that meant a fresh `tempfile.mkdtemp(prefix="rally-input-")` + a **full object download per request** — never deleted. `FileResponse` serves Range, so one browser scrubbing a `<video>` tag issues many independent requests to the same URL: ~10 seeks on a 4 GB match ≈ ~40 GB of bucket egress **and** ~40 GB of orphaned temp dirs, with every seek stalling behind a multi-GB download.

Now (`backend/main.py::_acquire_source_for_serving`):

- A remote source is fetched **once** into `<output>/source_cache/<video_id>/<name>` and every later request streams that local copy.
- **Atomic publish**: the download goes to a unique `.<name>.<uuid>.partial` in the cache dir, then `os.replace` onto the served name — a truncated file can never sit at the served path, and a failed fetch cleans its partial (502 surfaced, retry starts clean). No `finally`-delete of the served file — `FileResponse` streams after the handler returns.
- **Concurrent first requests** serialize on a per-video lock; losers re-check under the lock and reuse the winner's copy (one download total).
- The download is **free-space guarded** (`require_free_bytes`, D11 / #407) when the backend can `stat` the object size — refused with 507 *before* any bytes move; the cache lives under the guarded output root and is a regenerable intermediate (safe to delete any time).
- **Local-path videos stay a byte-identical identity passthrough** — no copy, no cache dir, `storage.fetch` never called; path-safety unchanged (`safe_output_filename` on the video_id path component + a sanitized cached filename).
- **Proxy warming now covers remote sources too** (the cached copy is a plain local file), closing the "remote-source proxying is a follow-up" note from #406 — once the D4 proxy exists it wins as before.
