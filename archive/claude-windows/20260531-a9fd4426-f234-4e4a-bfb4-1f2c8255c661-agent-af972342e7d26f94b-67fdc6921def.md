# SQLite3 Multiple Ciphers Overview

## Supported Ciphers

SQLite3MC implements six encryption cipher schemes:

1. **wxSQLite3: AES 128 Bit CBC**
2. **wxSQLite3: AES 256 Bit CBC**
3. **sqleet: ChaCha20-Poly1305 HMAC** (recommended default)
4. **SQLCipher: AES 256 Bit CBC**
5. **System.Data.SQLite: RC4**
6. **Ascon: Ascon-128 v1.2**
7. **AEGIS: AEGIS Family**

The ChaCha20-Poly1305 option is recommended because it combines modern encryption standards, key derivation functions (PBKDF2), and cryptographic nonces to prevent brute-force attacks.

## Page-Level Encryption

**Important limitation:** Bytes 16-23 of the database file typically remain unencrypted, and temporary tables/in-memory databases are not encrypted.

# SQLite3MC: FAQs, Licensing, and Limitations

## Frequently Asked Questions

The documentation covers four main FAQs:

1. **Non-default VFS encryption**: You can enable encryption for alternative VFS implementations by prefixing the VFS name with `multipleciphers-`. For example, use `multipleciphers-win32-longpath` to encrypt databases on Windows with long path support.

2. **Changing page size**: Standard SQLite page size changes don't work for encrypted databases. Instead, decrypt first with `PRAGMA rekey=''`, set the new page size, run `VACUUM`, then re-encrypt.

3. **Schema-independent selects**: Since SQLite 3.48.0, "executing a `SELECT` statement will now always access the underlying database file," which fails before encryption setup. Configure the cipher scheme using PRAGMA statements or URI parameters rather than SQL functions.

4. **iOS app suspension**: Encrypted databases in shared app containers cause iOS app termination. The solution involves using `plain_text_header_size` to leave part of the database header unencrypted, allowing iOS to identify SQLite files while maintaining security.

The project is "Distributed under an MIT license," making it permissive open-source software suitable for commercial and private use.

### (c) Keying & SQL Queryability

**Keying mechanism (apsw-sqlite3mc):**

```python
import apsw

# Create or open encrypted database
conn = apsw.Connection("mydb.db")

# Set encryption key (passphrase or hex)
conn.pragma("cipher", "chacha20")      # Select cipher (optional; ChaCha20 is default)
conn.pragma("key", "mypassphrase")     # Set key from passphrase
# OR: conn.pragma("hexkey", "0x...")  # Set key from hex bytes

# Execute queries immediately — they work transparently
cursor = conn.cursor()
cursor.execute("SELECT * FROM transactions WHERE amount > 100")

# Change key (rekey existing DB):
conn.pragma("rekey", "newpassphrase")
```

**SQL Queryability:** ✅ **FULLY PRESERVED**  
Encryption is transparent page-level encryption (SQLite WAL/B-tree page level), not field-level. All standard SQL queries (WHERE, ORDER BY, aggregations, JOINs) work unchanged on encrypted databases.

**Key derivation:** PBKDF2 (configurable iterations, default 24000).

**Journal encryption:** Yes — WAL and rollback journals are also encrypted.

**Limitation:** Bytes 16–23 of the database file remain unencrypted (SQLite format header); temporary tables and in-memory databases are NOT encrypted.

Source: [SQLite3MC SQL Pragmas](https://utelle.github.io/SQLite3MultipleCiphers/docs/configuration/config_sql_pragmas/), [SQLite3MC FAQs](https://utelle.github.io/SQLite3MultipleCiphers/docs/faq/faq_overview/)

### (e) APSW API Differences from stdlib sqlite3

**Important:** apsw-sqlite3mc uses the APSW API, NOT the stdlib sqlite3 API. They are **NOT transparent drop-in replacements.**

**Key differences:**

| Aspect | sqlite3 | APSW |
|--------|---------|------|
| **Architecture** | DB-API (PEP 249) compliant wrapper | Exposes SQLite C API directly |
| **Thread safety** | Per-thread connections required | Single connection safe across threads |
| **SQL batching** | Single statement per execute() | Multiple statements + semicolons in execute() |
| **Cursor pattern** | Required | Optional; connection executes directly |
| **Virtual tables / VFS** | Limited | Full support |

**Implications for muneem:**

1. **Current code using sqlite3:** Would require refactoring to APSW API (e.g., `conn.execute()` instead of `cursor.execute()`, etc.)
2. **Migration effort:** Non-trivial but not massive (similar scope to switching between DB libraries)
3. **Developer experience:** APSW is more Pythonic for advanced SQLite use; less boilerplate for async and threading.

**For muneem specifically:** Given the project's stated goal of "transparent full-DB page encryption" and "keep SQL queryability", switching to APSW-based encryption at DB initialization time is acceptable — it's a deliberate architecture decision, not a hidden gotcha.

Source: [APSW vs sqlite3 Differences](https://rogerbinns.github.io/apsw/pysqlite.html)
