### 3. The pipeline — `_execute_processing`
`backend/main.py:439-556`. This is the former synchronous `/api/process` body. Sequence:
1. `notify("hashing")` → `storage.acquire_local_input(req.video_path, ...)` resolves URI/path to a local file (`main.py:458`); `video_id = compute_video_id(local_video)` (MD5, `main.py:459`); `was_reingest = db_instance.get_video(video_id) is not None` (`main.py:460`).
2. `notify("validating")` → `registry.run_all_with_context(...)` (`main.py:465`). If any validator fails (`main.py:475-485`): `db_instance.add_video(video_id, req.video_path, "failed", [...])` (UPSERT, no cascade — `database.py:405-422`), returns `{"video_id","status":"failed","message","results"}`.
3. Else: `db_instance.add_video(video_id, req.video_path, "processed", [...])` (`main.py:489`). Resolve segmenter: `seg_name = req.segmenter or default_seg` (`main.py:469-470`); `segmenter_cls = segmenter_registry.get(seg_name)` (`main.py:491`).
4. **Destroy-after-confirm**: capture `play_wm, cand_wm = db_instance.segment_watermarks(video_id)` (`main.py:510`, `database.py:424-436`). Build segmenter: `segmenter = segmenter_cls(db_instance, global_config)` (`main.py:511`).
5. **Run the core**: `result = segmenter.process_video(video_id, local_video, req.player_pool, req.max_frames)` (`main.py:513`). On raise → `prune_segments(... play_after=play_wm, cand_after=cand_wm)` drops new partial rows and re-raises (`main.py:514-519`). On `Failure` → same prune + `status:"failed"` response (`main.py:522-532`).
6. `segments = result.value` (`main.py:534`); `notify("finalizing")`; `_finalize_reingest(video_id, segments, play_wm, cand_wm)` (`main.py:536`, `:283-293`) — on a non-empty run drops the PRIOR rows (`prune_segments play_upto=play_wm`); on empty drops the NEW rows (keeps prior good data).
7. Returns the success dict (`main.py:538-544`): `{"video_id", "status":"success", "message", "results":[validators], "play_segments": segments}`.
8. `finally:` always emits the per-video observability report and grafts `response["reports"] = paths` (`main.py:546-556`).

**How segments actually land in SQLite:** `_execute_processing` does **not** insert segments itself. The segmenter (`segmenter.process_video`, ABC at `backend/pipeline/segmenters/base.py:23-33`) writes them **as a side effect** via its injected `self.db`, calling `db_instance.add_play_segment(video_id, start, end, server, receiver, metadata)` (`database.py:459-471` — `INSERT INTO play_segments (...) VALUES (...)`, returns `lastrowid`) and optionally `add_candidate_segment` (`database.py:480-501`) / `add_event` (`database.py:473-478`). The returned `result.value` list is the same segments, used for the count + watermark finalize. So persistence is: **segmenter → `self.db.add_play_segment` → `play_segments` table**, with `_execute_processing` only managing the watermark/prune lifecycle around it.

### result dict shape stored on the job
`mark_job_done(job_id, result)` (`database.py:671-679`) does `UPDATE jobs SET status='done', progress='finished', result=<json.dumps(result)>, finished_at=CURRENT_TIMESTAMP`. The stored `result` is exactly the `_execute_processing` return dict:
```
{"video_id", "status": "success"|"failed", "message", "results": [...validators...],
 "play_segments": [...] (success/segmenter-fail branches), "reports": {...} (grafted in finally)}
```
Note `result["status"]` is the **pipeline verdict** (`success`/`failed`), distinct from the job's **execution** `status` column (`done`).

### status transitions (jobs.status)
`queued` (create_job, `database.py:635`) → `running` (claim_due_job CAS, `database.py:846`) → terminal `done` (mark_job_done, `database.py:675`) **or** `failed` (mark_job_failed on worker crash, `database.py:684`) **or** parked `waiting` (set_job_waiting, `database.py:802`, unused in prod) which re-enters `claim_due_job` when `next_poll_at` is due. Crash recovery: `fail_stale_jobs` (`database.py:856-870`) sweeps any `queued`/`running` rows to `failed` at startup (the in-process executor died with the process).

### GET /api/query reads segments afterward
`POST /api/query` (`main.py:694-703`, body `QueryRequest` at `main.py:268-273`) calls `db_instance.query_play_segments(req.video_id, filters)` and returns `{"play_segments": segments}`. `query_play_segments` (`database.py:564-612`) does `SELECT r.* FROM play_segments r WHERE r.video_id = ?` with optional `duration_min` / `server` / `receiver` / `event_type` (EXISTS-subquery on `events`) filters, deserializes `metadata` JSON, and attaches each segment's `events` (`database.py:597-610`). It reads **only** `play_segments`/`events` keyed by `video_id` — it has no knowledge of jobs. `/api/compile` (`main.py:705-717`) reads the same way and filters by the client-supplied `segment_ids`.

## Where the cloud-dispatch branch must slot in

The cloud-dispatch interface **already exists but is NOT wired**: `backend/compute/` has `ComputeBackend` ABC + `ComputeJobSpec`/`ComputeResult` (`backend/compute/base.py`, full file above) and `cloud_run.py` (155 lines). **`backend/main.py` never imports `backend.compute`** (grep confirmed — only `compute_video_id` and `compute_target` from `/api/capabilities` appear). So today the dispatch decision is implicit: `_execute_processing` always runs the segmenter in-process on the worker thread.

The natural insertion point is **`_execute_processing` at `main.py:511-513`** — right where it builds `segmenter = segmenter_cls(db_instance, global_config)` and calls `segmenter.process_video(...)`. Per `base.py:8-10`, the seam is gated on `deployment.compute_target == "cloud_run"`: a factory returns a `ComputeBackend` (cloud) or `None` (run inline / byte-identical today). The cloud branch would replace the local `process_video` call with `backend.run_infer(ComputeJobSpec(video_uri=..., out_uri=..., segmenter=seg_name, ...))`, then ingest the remote `ComputeResult.outputs_uri` artifacts back into `play_segments` so that the downstream contract — the same `result` dict stored by `mark_job_done`, and `query_play_segments` reading `play_segments` by `video_id` — stays identical. The watermark/`_finalize_reingest` lifecycle (`main.py:510, 536`) and the `result["video_id"]`/`play_segments` shape must be preserved for `/api/query` and `/api/compile` to keep working unchanged.
