37	def slugify(heading: str) -> str:

40	    collapsing, so a heading with removed punctuation (e.g. 'a / b' → 'a  b') yields '--' like GitHub."""
41	    s = re.sub(r"[^\w\s-]", "", heading.strip().lower())
42	    return s.replace(" ", "-")

45	def heading_slugs(text: str) -> Set[str]:

47	    counts: Dict[str, int] = {}
48	    out: Set[str] = set()

50	    for line in text.splitlines():
51	        if _FENCE_RE.match(line):
52	            in_fence = not in_fence
53	            continue
54	        if in_fence:
55	            continue
56	        m = _HEADING_RE.match(line)
57	        if not m:
58	            continue
59	        base = slugify(m.group(2))
60	        n = counts.get(base, 0)
61	        out.add(base if n == 0 else f"{base}-{n}")

68	    dest = dest.strip().split()[0]  # drop a trailing "title"

### 3.1 Reading a job's state

`GET /api/jobs/{job_id}` returns `{job_id, status, progress, video_id, error, result, reports, created_at, started_at, finished_at}` (`backend/main.py:1008-1027`). Two failure channels, deliberately distinct (`backend/api/job_worker.py:148-153`):
- `status='done'` + `result.status='failed'` → the **pipeline's verdict** (validation, staging, dispatch, cloud rc≠0, stitch…) with a human `result.message`;
- `status='failed'` + `error="<ExcType>: <msg>"` → the **worker itself crashed** (`backend/api/job_worker.py:191-193`).

The `progress` field is the first triage signal — the worker stamps every stage: `starting → hashing → validating → staging upload to bucket → dispatching (cloud_run) → ingesting (cloud_run) / segmenting (<name>) → finalizing`; compile: `resolving → stitching → uploading reel → finished` (`backend/infrastructure/database_jobs.py:105-118`; `backend/orchestration.py:287,324,363,447,516,559,608,793,816,851,861`). A stuck job's last `progress` value tells you which stage it died in.

### 3.3 Correlating a client `job_id` to a Cloud Run execution

There is no single trace id — the chain is: **job_id → video_id → execution name**, stitched from the job row plus two log lines:

1. `job_id → video_id`: the worker stamps `video_id` onto the job row as soon as the result carries one (`job_worker.py:177-178`); it's in every `GET /api/jobs/{id}` response.
2. **Dispatch token**: each dispatch mints `done_uri = <output_root>/_dispatch/<uuid4-token>.done` (`cloud_run.py:179-182`) and logs `cloud-run: dispatched job=<job> exec=<execution>; bucket-polling <done_uri>` (`cloud_run.py:200-205`) — this CP line is the token↔execution join point. The worker's side logs `[worker] wrote completion marker -> <done_uri>` in the **execution's** logs (`backend/worker/__main__.py:188`), closing the loop from the other end.
3. **Provenance on the result**: a successful cloud job's `result.compute` = `{path:"cloud_run", job, region, execution, outputs_uri}` and the CP logs `[COMPUTE] cloud_run dispatched: execution=… job=… region=… out=… video_id=…` (`orchestration.py:384-400`); the docstring's own cross-check is `gcloud run jobs executions describe <execution>` (`orchestration.py:386`). Every pipeline run also ends with `[COMPUTE] video_id=… requested=… actual=… dispatched=… status=…` (`orchestration.py:632-640`).
4. On a **poll timeout** the execution name is carried inside the failure message itself (`cloud_run.py:281-285`), so it reaches the client. But on other dispatch failures the `compute` dict in the failed result has **no execution field** (`orchestration.py:206-221`) — the CP `dispatched` log line is then the only record. Note the token/execution are **not persisted on the job row**; if the instance recycles, this mapping survives only in Cloud Logging.

### 3.4 GAPS — what an operator cannot currently see

1. **No request tracing/replay** — issue **#326** (open). No request id crosses the API→worker→L4 boundary.
2. **No per-video runlog surface** — issue **#328** (open). `emit_indexer_report` writes per-video reports on every run (`orchestration.py:645-660`) and the paths ride the job result (`main.py:1023`), but they are **server-local paths on an ephemeral instance** — unreachable by client or operator after recycle.
3. **`job_id` is absent from nearly all pipeline logs** — `[COMPUTE]`, `[API] cloud-serving…`, `cloud-run: dispatched…` key on video_id/execution, not job_id (`orchestration.py:325-329,393-400,632-640`; `cloud_run.py:200-205`). Only crash/park lines carry it (`job_worker.py:189-193`). Triage from a user's job_id starts with an extra DB/API hop that dies with the instance.
4. **Job history is ephemeral** (issue #471) — the `error` column and `result` JSON, the primary triage record, vanish on every deploy/recycle; only what was logged survives.
5. **Stuck-queue blindness** — no per-job wall-clock timeout and no log when a job wedges the single drain lane (`job_worker.py:40-48`); the failure mode is pure silence.
6. **Client 4xx are unlogged app-side** — upload 409/413, jail 400s and auth 401s raise HTTPException without a logger call (`uploads.py:127-170`; `main.py:910-913`), leaving only status codes in request logs.
7. **No metrics/alerting** — zero counters; failure detection is entirely reactive log-grepping.

**Top 3 cheapest wins** (all log-only, no infra):
1. **One structured terminal line per job** in `_run_claimed_job` — `[JOB] id=… kind=… status=… video_id=… compute=… execution=… wall=…s error=…` at done/failed/parked (`job_worker.py:177-193`). Single choke point; makes every triage class above greppable by the id the client actually has, and closes gap 3 for ~10 lines.
2. **Persist/log the execution name + dispatch token at dispatch time keyed by job_id** — e.g. thread job_id into the dispatch logs, or stamp `execution` into `progress` ("dispatching (cloud_run exec=…)"). Cost: a few lines; makes job→execution correlation survive crash-before-result.
3. **Mirror the per-video report JSON to `gs://…/outputs/<video_id>/`** next to `intervals.csv` (the worker already pushes artifacts there — `worker/__main__.py:327`) and/or serve it via a small authenticated endpoint — a minimal first slice of #328 that also survives instance recycling (gaps 2 and 4).

*Launch-facing note:* these gaps are operability debt, not A13 blockers by themselves — but with A10/A11 still owner-gated, gaps 4+5 (silent stuck jobs on an ephemeral store) are the ones most likely to burn an alpha tester: a tester whose job wedges gets silence, and a redeploy erases the evidence. Acceptable at 4 users with email support (§4.6); not beyond.

### 5.5 Runtime service-account blast radius (fix before wider invites)

The control plane and worker run as the **project default compute SA** (`492532266377-compute@developer.gserviceaccount.com`).
