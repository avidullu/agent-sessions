49	## 2. Core architecture
50	
51	### 2.1 The "by design" invariant — no hardcoded user-facing strings
52	
53	Every coach-facing string is a **stable key** resolved at render time against the active locale.
54	Code references `t("compile.button")`, never the English prose. This is the single rule that
55	makes "add a language = add a catalog" true, and it is **enforced by CI** (§2.6) so it cannot
56	silently regress as the codebase grows.
57	
58	```
59	"Validate & Index Video"                         →  t("video.action.validate_index")
60	alert("Validation Failed! …review the checklist") →  t("toast.validation_failed")
61	`${count} Rally Segment${count>1?'s':''} Selected`→  t("compile.selected", {count})   # ICU plural
62	HTTPException(detail="Video file not found at …")→  detail = tr(lang, "error.video_not_found", {path})
63	```
64	
65	### 2.2 One canonical English source catalog, per-locale siblings
66	
67	```
68	locales/
69	  en/  common.json   # source of truth — devs author keys here
70	  kn/  common.json   # Kannada  (Gemini-draft → human-review)
71	  hi/  common.json   # Hindi    (next; first exercise of the extensibility checklist)
72	```
73	
74	- **Format: i18next-flavored JSON** — works for the vanilla shim today *and* react-i18next in
75	  the SPA, with no conversion.
76	- **ICU MessageFormat** for interpolation and plurals: `"{count, plural, one {# rally} other {# rallies}}"`.
77	  This matters immediately — the current UI already hand-rolls English plurals
78	  (`Rally Segment${count > 1 ? 's' : ''}`), and Kannada/Hindi plural rules differ from English.
79	  ICU encodes each language's rules in the catalog, not the code.
80	- `en` is the source of truth; **every other locale is keyed identically** (enforced by the
81	  key-parity check in §2.6).
82	
83	### 2.3 Locale-negotiation contract (shared frontend ↔ backend)
84	
85	One resolution order, defined **in one place** and honored by both UI and backend:
86	
87	```
88	persisted user preference  →  UI switcher / ?lang=<code>  →  Accept-Language header  →  default "en"
89	```
90	
91	- Supported locales are enumerated in **a single module** (one list to grow). Anything outside
92	  it falls back to `en`.
93	- The backend localizes its own responses (`HTTPException.detail`, report `customer_*`) from the
94	  same `lang` query param / `Accept-Language` header, so a Kannada UI gets Kannada errors.
95	- **Always-fallback to `en`** for any missing key — a missing translation must degrade to
96	  English, never to a blank or a raw key in front of a user.
97	
98	### 2.4 Backend text → keys + params, not prose
99	
100	Validator `message`s and API errors today bake in English prose *and* interpolated values
101	(`f"…sharpness score of {avg} is below … threshold of {threshold}."`). The design separates
102	the two:
103	
104	- The validator/endpoint emits a **stable code + a params dict** (`("blur.below_threshold",
105	  {"score": avg, "threshold": threshold})`).
106	- The **prose lives in the catalog**, looked up at the API boundary in the negotiated locale.
107	- `ValidationResult` keeps an English `message` for logs/back-compat, but gains an optional
108	  `message_key` + `message_params`; the report/serializer prefers the key when present. This
109	  keeps internal/technical messages English (good for debugging) while customer-facing text
110	  localizes.
111	
112	`spec.yaml` `customer_verdict` and per-rule `customer_message` become **keyed** (or per-locale
113	overlays keyed by rule `code`); the technical `message` blocks stay English (they cite
114	`README#Qn` and are for the operator, not the end user).
115	
116	### 2.5 Indic font strategy ⚠ (open decision — see §4)
117	
118	The bundled UI/watermark fonts (Outfit, Roboto Slab) **do not cover Kannada or Devanagari**.
119	**Noto Sans Kannada / Noto Sans Devanagari are OFL-licensed**, which is the same tension we hit
120	with the watermark font: OFL is not in the strict **MIT/Apache/BSD** code/data/weights guardrail.
121	Fonts are *media assets*, not code or model weights, and OFL is explicitly designed for
122	unrestricted redistribution — so the cleanest path is to **carve out an explicit OFL-for-fonts
123	exception**, the same way we'd treat any bundled media. Options put to the owner in §4.
124	
125	Note the **video watermark already takes a `font_path`** (`WatermarkConfig.font_path`,
126	`backend/pipeline/stitcher/compiler.py`), so stamping a Kannada/Hindi watermark is a
127	*configuration* change (point it at a Noto font) once the font decision is made — no new code.
128	
129	### 2.6 CI enforcement (the guardrail that keeps it "by design")
130	
131	Two checks, both pure-Python and runnable in this repo (no GPU/torch needed):
132	
133	1. **Key-parity test** — every locale catalog has *exactly* the `en` key set; fail on missing
134	   keys, extra keys, or untranslated placeholder markers (e.g. a `"__MISSING__"` sentinel left
135	   by the draft script). This is also the **extensibility proof**: drop a stub `ta.json` with
136	   one key and CI immediately lists every gap.
137	2. **No-bare-strings lint** — a check that flags user-facing string literals not routed through
138	   `t()` / the backend `tr()` (scoped to the UI handlers and the API/validator/report text
139	   paths). Starts as a curated allowlist so it can land without boiling the ocean.
140	
141	### 2.7 Translation pipeline
142	
143	```
144	dev authors en keys  →  scripts/i18n_draft.py  (Gemini, INFERENCE only)  →  kn/hi draft
145	                     →  native-speaker review (owner reviews first draft)
146	                     →  CI key-parity + placeholder check  →  merge
147	```
148	
149	`scripts/i18n_draft.py` reads `locales/en/*.json`, asks Gemini for each missing key in the
150	target locale **with the key name and any ICU placeholders preserved**, and writes a draft
151	catalog with every machine-drafted value flagged for review. It never touches `en`, never
152	invents keys, and is a *drafting aid* — a human reviews before merge. (Reuses the existing
153	Gemini provider credentials/config; this is the same "paid LLM = inference, never training"
154	posture as the rest of the system.)

50	## 4. Design / architecture
51	**Two surfaces, one shared source of truth.**
52	
53	```
54	locales/                      # shared catalogs — co-located in khelsutra (D-CATALOG-HOME, see §8)
55	  en/  common.json            # source of truth — devs author keys here
56	  kn/  common.json            # Kannada  (Gemini-draft → human-review)
57	  hi/  common.json            # Hindi    (next — the extensibility proof)
58	
59	web/   → react-i18next        # I18N_PLAN P3: provider in main.tsx; useTranslation in components
60	site/  → t(key,vars) shim      # I18N_PLAN P1 retargeted: data-i18n attrs over the static HTML

63	- **Negotiation contract (one order, both surfaces):** `persisted pref (localStorage) → switcher / ?lang=<code> → navigator/Accept-Language → "en"`. Supported locales in a single module; anything else falls back to `en`; **a missing key degrades to English, never to a raw key.**

98	## 6.5 Testing strategy — automatic language negotiation (rigorous, owner-required)
99	**The bar (owner, #41):** a user whose **computer/browser language is Kannada or Hindi must get the respective version automatically** — that is the core promise and it is **proven by tests at every layer, never assumed.** Auto-selection IS the negotiation order (persisted pref → `?lang=` → browser/`Accept-Language` → `en`); each step gets a test.
100	
101	**Negotiation matrix — every row is an automated test:**
102	
103	| # | Signal under test | Setup | Expected | Proven in |
104	|---|---|---|---|---|
105	| N1 | **Browser/OS = Kannada** | no persisted pref, no `?lang`, `navigator.languages=["kn-IN", …]` | resolves to **kn** → Kannada content (once the kn catalog ships) | **B1** detection · **B5** content |
106	| N2 | **Browser/OS = Hindi** | `navigator.languages=["hi-IN", …]` | resolves to **hi** → Hindi content | **B6** (hi added to the supported set + catalog) |
107	| N3 | **`?lang=` override** | `?lang=kn`, browser = en | kn | B1 |
108	| N4 | **Persisted pref wins** | `localStorage=kn`, browser = en, no `?lang` | kn (a returning user keeps their choice) | B1 |
109	| N5 | **Region subtag normalizes** | `navigator.language="kn-IN"` | base **kn** (not a "kn-IN" miss) | B1 |
110	| N6 | **Unsupported language** | `navigator="ta-IN"` (Tamil, not yet supported) | **en** fallback — never a locale we can't serve | B1 |
111	| N7 | **Missing key in active locale** | kn active, a key absent from `kn/common.json` | **en** fallback for that key (no raw key shown) | B1/B5 |
112	| N8 | **Static site (vanilla shim)** | `Accept-Language: kn` / `?lang=kn` on a `site/` page | kn-rendered page (same order as the SPA) | B3 |
113	| N9 | **Backend (engine P2)** | `Accept-Language: kn` to the API | kn customer/report text | B7 (owner-gated) |

115	**Levels & tooling:**
116	- **SPA (`web/`):** jsdom tests stub `navigator.language`/`navigator.languages`, `localStorage`, and the `?lang` query → assert `i18n.language`/`resolvedLanguage` + rendered text per the matrix. *(B1 lands N1/N3–N7 at the **detection** level now — `kn` is supported; the kn/hi **content** assertions ride the catalogs in B5/B6.)*
117	- **Static site (B3):** the shared `t()` shim's negotiation is unit-tested the same way; plus a server test that `Accept-Language: kn`/`?lang=kn` returns the kn-rendered page.
118	- **CI key-parity:** guarantees every locale has every key, so a correctly-negotiated locale can never fall through to a raw key.
119	- **End-to-end (manual, owner machine — per I18N_PLAN §6):** set the real OS/browser to Kannada, then Hindi → load both surfaces → confirm the right language renders **and the Noto fonts display** (the cloud CI container can't render fonts; the owner eyeball is the final gate).
120	- **⚠ Query parsing / semantic understanding (forward-looking, owner directive 2026-06-21) — i18n testing is MANDATORY there.** The query bar is **English-grammar-only** today (a documented limit, tracker A9): the user types English queries (`over 10s`, `top 15 longest`) and a localized **sample-query prompt** shows them what to type in *every* locale (kn/hi included). The **moment** the parser gains **semantic understanding** or accepts **Kannada/Hindi query input** (e.g. typing a Kannada/Hindi phrase, or a conversational/NL builder — I18N_PLAN P4), i18n tests become a **merge gate**: a kn/hi query (typed or spoken) must parse to the **correct selection**, the localized **parse-feedback** ("parsed-pill") must render in the active locale, and the unsupported/empty-result messages must localize. **No query-NL / semantic-parsing work merges without those tests.**
121	
122	A locale that's reachable by the switcher but **not auto-selected from the browser language is a bug, not a "later".** This matrix is a DoD gate (§9).
