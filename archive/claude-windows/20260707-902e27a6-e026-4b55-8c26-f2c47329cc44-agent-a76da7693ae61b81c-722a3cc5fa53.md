dispatches a Cloud Run **Job** execution running this image's worker on an **L4**, then **bucket-polls**
a done-marker for completion (D16). Scale-to-zero (D7) — no warm pool.

> **Status:** the dispatch shim + image are **landed + mock-tested** (M6). The **real build + push +
> run on an L4** is the **M7** owner step, within the **$100/₹10k** budget (D17) — confirm cmd + hourly
> cost first, **delete every resource after** ([[gcp-vm-always-delete]]). CI does **not** build this image.

## 2a. GPU-resident WASB decode (#506/#507) — the current serving default
The image ships the **py3.10 + torch 2.6.0+cu124 + PyNvVideoCodec==2.1.0** WASB env with
`libnvcuvid`/`libnvidia-encode` **baked in** (multi-stage layer from the matching NVIDIA driver —
Cloud Run injects the host driver, not these userspace codec libs). `indexing.wasb.decode_backend`
selects the decode path:
- `cpu` (model default) — the historical cv2 decode; **byte-unchanged** by this work.
- `nvdec_resident` — NVDEC decode + cv2-faithful affine `grid_sample` resize + GPU normalize, all
  on-GPU. **The cloud-serving preset default** (validated: offline golden gate @ SERVED F1 0.574 ≈
  baseline 0.582, AND on the live L4 the served GX010128 trajectory reproduced the VM run —
  26 479 ≈ 26 481 visible). CUDA-only (config-validator-enforced).

**How the knob reaches the worker.** The worker Job runs with NO `DEPLOYMENT_PROFILE`, so it does
**not** apply the cloud-serving preset itself. The control plane (which *does* have the profile)
resolves the config and **forwards** `indexing.wasb.{decode_backend,batch_size,prefetch_batches}`
to the worker as `--set` overrides (`orchestration.py`, alongside `skip_ai_handoff`). So the
**preset is the single source of truth** — changing `presets.py` + redeploying the control plane
changes serving; no per-Job knob needed.

**Override / rollback lever (no redeploy).** The native runner reads `WASB_DECODE_BACKEND` FIRST,
so a Job env var wins over the forwarded `--set`:
```bash
# force nvdec (or pin cpu) on the Job regardless of the forwarded config; instant rollback = remove it
gcloud run jobs update rally-worker --region $REGION --update-env-vars WASB_DECODE_BACKEND=nvdec_resident
gcloud run jobs update rally-worker --region $REGION --remove-env-vars WASB_DECODE_BACKEND   # → forwarded/preset default
# full revert: pin the prior image by digest
gcloud run jobs update rally-worker --region $REGION --image $REGION-docker.pkg.dev/$PROJECT/$REPO/rally-worker@sha256:<prev>
```

`--decode-backend` (≥ #507). Roll the **worker image and the control plane together** — a new
control plane forwarding nvdec to an old worker image argparse-fails (rc 2).

### 3a. Control-plane SERVICE deploy — required flags for reliable async jobs

The API server (`/api/process`, `/api/compile` — #329) runs its **job worker IN-PROCESS**: the
request returns `202` and a background thread drains the job (GPU detection dispatches to the Job;
the reel stitch runs on the control plane itself). On Cloud Run that background thread only makes
progress while the instance has CPU, so a scale-to-zero **service** deploy MUST set:

**The canonical deploy path is the committed manifest generator** (#473) — it bakes the
cloud-serving config.json into a startup wrapper, sets every flag below, pins `maxScale=1`

reserved runtime env name that gets a manifest rejected; the code default is already right):
```bash

```
`--edge-auth off` is only for the pre-CF identity-token smoke/e2e window; redeploy with `on`

## Gotchas
- The dispatched container **must run inline** — `CloudRunCompute` forces `compute_target=local_gpu`
  + `indexing.detector_impl=native` in the per-execution args so the Job never re-dispatches itself.
- Completion is a **bucket marker** (`<out_uri>/_dispatch/<token>.done`), not the Cloud Run API status
  — so it reuses the storage layer + `execution_policy.poll_until` and survives a control-plane restart.
- A **failed** Job (validation rc 2 / segmenter rc 3) now writes a **failure marker** carrying the
  real non-zero rc, so the dispatcher's poll terminates **FAST + accurately** (no 30-min hang on a bad
  video). Only a **hung/crashed** container (no marker at all) makes the bounded poll time out
  (`ExecutionPolicy.max_wait_sec`); the worker CLI maps that to a clean **rc 4**, and the API path
  surfaces it as a `cloud dispatch error` job failure (not a traceback).
- libx264 encode (parity, D16) + NVDEC decode-only; the image keeps ffmpeg's default libx264.
- **`GOOGLE_CLOUD_PROJECT` is required** for the real client — `GoogleCloudRunJobClient.run_job`
  fails fast with a clear `RuntimeError` if it is unset/empty (it must resolve a real `job_path`;
  an unset project would otherwise build a bogus `projects/None/...` name). Export it (step 3) before
  dispatching. The guard runs before the `google-cloud-run` import, so it is exercised in CI even
  though the SDK isn't a CI/test dependency.
- **Hand-rolled `jobs execute --args` with `gs://` URIs:** gcloud's default comma-split plus its
  alternate-delimiter syntax both bite — repeated `--set` tokens trip the comma parser, and a
  `^:^` delimiter splits the `:` inside `gs://`. Use a delimiter that appears nowhere in the args,
  e.g. `--args='^@@^-v@@infer@@--video-uri=gs://…'`. (The dispatcher path doesn't have this
  problem — prefer it; this is for one-off diagnostics.) Container-arg overrides must include the
  dispatcher's two forced `--set`s: `deployment.compute_target=local_gpu`,
  `indexing.detector_impl=native`.
- **Git Bash (MSYS) on Windows mangles Unix-looking values** before gcloud sees them:
  `--add-volume-mount …mount-path=/gcs` became `C:/Program Files/Git/gcs`, and
  `--command=/bin/bash` became `C:/Program Files/Git/usr/bin/bash` (the container then exec-fails).
  Run gcloud commands with such flags from PowerShell (`MSYS_NO_PATHCONV=1` breaks gcloud's own
  wrapper). PowerShell has its own trap: quote any flag value containing commas.
- **First execution after an image push** spends minutes in "Container image import in progress"
  (visible in `executions describe status.conditions`, NOT in logs) — that's progress, not a hang;
  later executions reuse the imported image.
