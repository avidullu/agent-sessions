111	    predictions = process(video)                                 # existing production pipeline → DB

49	
50	### What delivery formats do we accept?
51	Both. A **CVAT export** (image- or track-mode XML — rally fields carried as box

57	One row per rally:

62	We recompute each rally's interval from its **frame range × the true fps**

**sports-data-collector** uses **yt-dlp** (not ffmpeg) to download at best resolution, then **ffprobe only** to validate. This is where **Roora vendor ingestion** happens.

**rally-annotator**: VLC UI, no ffmpeg.

### Critical Finding: Video ID / Re-Encoding Risk

The indexer uses **MD5 of the entire file** as `video_id` (the DB primary key). **If you create a re-encoded copy, it gets a different MD5 and becomes a "new" video in the DB.** This matters because the current Roora brief explicitly states: "Do not trim, clip, or re-encode the video — our pipeline identifies a video by its file checksum."

### Where to Build the Vendor-Prep Feature

**`sports-data-collector/src/core/`** — either a new `vendor_prep.py` module or an extension to `downloader.py`. This is where source videos are acquired and sent to Roora, making it the natural fit.

**What it would do:**
1. Detect if source exceeds vendor specs (file size, resolution, variable frame rate)
2. Re-encode to vendor-friendly profile: **1080p max, 30 fps constant, H.264, dense keyframes**
3. Send re-encoded copy to vendor, but **label the CSV with the original video_id** (not the re-encoded MD5) to preserve database identity
