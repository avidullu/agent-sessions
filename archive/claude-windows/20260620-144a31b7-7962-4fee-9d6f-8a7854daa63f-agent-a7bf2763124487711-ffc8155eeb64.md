30	## 1. The central insight: timestamps are the product; the video is dead weight
31	
32	Walk the pipeline and ask what each stage actually consumes:
33	
34	- The **Gemini segmenter** never sees the original — it re-encodes chunks down to
35	  **1280 px** (`indexing.ai_chunk_scale_width`) before uploading them to Google.
36	- The **detectors/featurizer** consume downscaled frames and trajectories.

38	  and only to cut clips — a pure-ffmpeg operation that can run **wherever the
39	  original lives**.
40	- What the customer receives is `{rally intervals, report, reel}`. Intervals +
41	  report are **kilobytes**. Given the intervals, the reel can be cut on the
42	  machine that already has the original.
43

45	is never "how do we upload the video" but "what is the smallest artifact that
46	must cross the network for this tier of service."

The cloud-upload product surface fails them on every axis: slow on a typical Indian uplink (`VIDEO_LOCALITY_MODEL.md` §0: 10 GB ≈ ~1 h at 20 Mbps, ~4.5 h at 5 Mbps), bandwidth-costly, privacy-fraught, and it bloats both our storage and their drives. The thing the customer actually wants back is **kilobytes of timestamps → a highlight reel** (`VIDEO_LOCALITY_MODEL.md` §1: *"timestamps are the product; the video is dead weight"*).
19	
20	**The concrete outcome ("good" looks like this):**
21	1. User plugs the GoPro/phone SD card or camera USB into their laptop.
22	2. The app detects the card, lists the match videos on it.
23	3. User clicks **Generate Highlights**.
24	4. The app makes an on-device proxy, runs WASB detection + windowing + stitches the reel — **100% locally**.
25	5. The reel(s) land in a user-chosen folder. **The originals are never copied off the card and never bloat any drive.**
26	
27	No account, no upload, no cloud dependency in the default path. Gemini stays an **optional** "better brain if you want it" toggle — never required, never bundled as a hard dependency, never a training source (`COMMERCIALIZATION` C4).

29	**Read to get current:** `VIDEO_LOCALITY_MODEL.md` (the L0/locality framing + OQ5 packaging seed), `PLATFORM_ARCHITECTURE.md` §3.2 (the ComputeBackend seam), [`backend/pipeline/detectors/base.py`](../backend/pipeline/detectors/base.py) (the detector ABC that already anticipates a Linux-native runner), `tools/generate_highlights.py` (the local entrypoint this app wraps).

42	## 3. Foundation — research / prior art `[design]` / `[researched]`
43	
44	### 3.1 The compute reality (the crux) — what we know vs must measure
45	- **WASB on a discrete laptop GPU is acceptable** `[verified, measured]`: on the owner's **RTX 2070 Super Max-Q (8 GB)**, WASB inference is the pipeline driver at **~3.2–3.4× real-time** (≈3.4 GPU-min per footage-min, ~0.055 s/frame), peak VRAM ~5.7–6.0 GB; proxy (NVENC) ~0.2× RT; 4K stitch (CPU libx264) ~16 s/rally; end-to-end ≈5× clip length. Source: `current-state.md` `COST_SCALING.md` checkpoint (6 Boxhill clips, 2026-06-18).
46	- **The typical enthusiast laptop has NO discrete GPU.** A 10-min 4K clip at 3.4× RT is ~34 GPU-min *with* a 2070S. On integrated graphics / CPU-only the wall-clock is unknown and could be 10×+ worse — possibly **hours per clip**, which would kill the one-click promise.
47	- **Apple Silicon has no CUDA.** WASB/TrackNet weights are PyTorch; PyTorch MPS (Metal) backend *may* run them, but op-coverage and speed on the WASB model are **unverified** `[design]`. CPU fallback on Apple is also unverified.
48	- **Owned-model tie-in.** `OWNED_MODEL_IMPLEMENTATION_PLAN.md` already states the on-device answer: *train in Python → **export across the boundary** (ONNX / Core ML / ExecuTorch / GGUF) → a thin device shell runs the artifact with zero Python*, with the standing constraint to **train with export-clean ops**. A smaller, exported, quantized shuttle detector is a credible answer if the CPU/MPS numbers on the current WASB weights are bad. **This makes P0 partly a referendum on whether the desktop product needs the owned-model track.**
49	
50	### 3.2 The de-WSL native runner is already designed-for `[verified]`
51	The detector layer was deliberately built to make this port low-regret. [`backend/pipeline/detectors/base.py`](../backend/pipeline/detectors/base.py) documents, verbatim, an **"Optional Linux-native path (the main de-risk goal)"**: a `LinuxNativeRunner`/`ONNXRunner` that *"Skip[s] all wsl / _stage / conda activate, load[s] weights locally (torch or onnx)… write[s] the exact same CSV format so `trajectory_to_action_windows` works verbatim."* The WSL plumbing lives in a separate `WslCommandMixin`, explicitly so a native runner *"must not inherit WSL plumbing."* The actual inference math is already isolated in [`wasb_infer.py`](../backend/pipeline/detectors/wasb_infer.py) (torch + the WASB-SBDT modules, emitting `Frame,Visibility,X,Y`). **So the port is: lift `wasb_infer.py` out of WSL, load weights with native torch/onnxruntime per-OS, keep the identical CSV contract.** The windowing brain (`trajectory_to_action_windows`) and stitch are untouched.

70	## 2. Target layered architecture
71	
72	Decouple into layers with a clean **control-plane vs data-plane** split — the
73	orchestrator coordinates *metadata and jobs*; the heavy *bytes and GPU work* can live
74	elsewhere (even in the user's own cloud).
75	
76	```
77	                ┌──────────────────────────────────────────────┐
78	   CONTROL      │  Presentation / API  (auth, per-tenant)        │
79	   PLANE        │  Identity & Tenancy  (org→coach→athlete→user)  │
80	                │  Orchestration / Jobs (submit→status→result)   │
81	                └───────────────┬───────────────┬────────────────┘
82	                                │ dispatch       │ metadata
83	                ┌───────────────▼───────┐  ┌─────▼───────────────┐
84	   DATA         │  Execution / Compute  │  │  Data / Serving     │
85	   PLANE        │  (local | BYO-VM |    │  │  (per-tenant DB:    │
86	                │   hosted GPU)         │  │   videos, segments, │
87	                │   runs the Pipeline:  │  │   highlights, jobs, │
88	                │   detect → highlight  │  │   history)          │
89	                └───────────┬───────────┘  └─────────────────────┘
90	                            │ read input / write artifacts
91	                ┌───────────▼───────────────────────────────────┐
92	                │  Storage  (local upload | Google Drive | S3 |  │
93	                │  GCS | Azure)  — raw video + highlight outputs │
94	                └────────────────────────────────────────────────┘
95	```
96	
97	The two **new pluggable seams** are **Storage** and **Compute/Execution**; everything
98	else either exists (pipeline) or is net-new infra (identity, orchestration, serving). A
99	**model/training layer** — the owned generative video-QA model (§5A) — sits atop these,
100	fed by Storage (training corpus), Data (labels), and Compute (training + inference), and
101	is delivered through the existing **AI-provider registry with a paid fallback**.

103	## 3. Pluggable abstractions (extend the existing registry pattern)
104	
105	The codebase already proves the model: an `ABC` + a `Registry` singleton with
106	`register/get/list_available` (e.g. `SegmenterRegistry`). Add two more registries with
107	the same shape so they're plug-and-play and testable in isolation.
108	
109	### 3.1 `StorageBackend` registry
110	Replace the bare `video_path: str` that flows through the pipeline with a
111	**`StorageRef`** (a backend id + a key/URI), resolved by a backend.
112	
113	```python
114	class StorageBackend(ABC):
115	    name: str
116	    def open_read(self, ref: StorageRef) -> BinaryIO: ...      # stream large video
117	    def download_to_local(self, ref: StorageRef, dst: str): ...  # for ffmpeg/cv2/WSL
118	    def upload(self, local_path: str, ref: StorageRef): ...     # persist highlight/artifacts
119	    def signed_url(self, ref: StorageRef, ttl: int) -> str: ... # hand to LLM / browser
120	    def stat(self, ref: StorageRef) -> StorageStat: ...
121	    def list(self, prefix: StorageRef) -> list[StorageRef]: ...
122	```
123	
124	- **Recommended implementation:** build the backend over **`fsspec`** (one matrix —
125	  local / S3 (`s3fs`) / GCS (`gcsfs`) / Azure (`adlfs`) + Google Drive via `gdrivefs`,
126	  Dropbox via `dropboxdrivefs`), reaching for **`smart_open`** as the robust large-MP4
127	  byte-streaming primitive. Storage becomes one more registry. (Treat Drive/Dropbox as
128	  add-ons — less battle-tested than `s3fs`/`gcsfs`; cover with integration tests.)
129	- **Backends:** `local` (upload dir), `gdrive`, `s3`, `gcs`, `azure`. **BYO-storage**:
130	  the tenant registers their own bucket/Drive; raw video **never leaves their account**.
131	- **Auth — never persist users' long-lived keys.** For buckets, have the user create an
132	  IAM role you **`AssumeRole`** into, scoped to one bucket/prefix, and mint **presigned
133	  URLs** so raw video moves **browser ↔ the user's bucket directly, never through our
134	  servers**. For Drive, OAuth with the narrow **`drive.file`** scope; for academies, a
135	  **service account with domain-wide delegation**. Store any per-tenant creds encrypted.
136	- **Why it matters for the pipeline:** ffmpeg/OpenCV/WSL need a **local file**, while the
137	  LLM provider can take a **signed URL**. The backend exposes both `download_to_local`
138	  (for compute) and `signed_url` (for the provider/browser), so the pipeline stops caring
139	  *where* the bytes live.
140	- **Migration path:** introduce `StorageRef` alongside the current local path; a `local`
141	  backend wraps today's behavior so nothing breaks; adapters land incrementally.
142	
143	### 3.2 `ComputeBackend` / `ExecutionBackend` registry
144	Where the pipeline actually runs for a given job.
145	
146	- **`local`** — in-process / local subprocess (today's behavior; dev + self-host).
147	- **`hosted`** — our GPU VM pool (the SaaS default).
148	- **`byo_worker`** — the tenant runs a **pull-based worker** (a small agent) on their own
149	  VM/GPU. **Critical security property:** the worker *pulls* jobs scoped to its tenant
150	  from the control plane, pulls input from the tenant's **own** storage, runs the
151	  pipeline, and writes artifacts + results back — so **the orchestrator never holds the
152	  user's cloud credentials** and needs **no inbound access** to their network. This
153	  mirrors the **self-hosted CI runner** pattern (GitHub Actions runners use a 50s
154	  outbound-only HTTPS long-poll). This pull-based runner is the **cheapest, most
155	  credential-safe v1** for BYO-compute.
156	- For users who want the platform to **provision GPUs in their *own* cloud account on
157	  demand** (an academy with an AWS account but no standing GPU box), add **SkyPilot**
158	  (BYOC: everything launches in the user's accounts/VPCs; creds stay with them).
159	  **Modal** is the managed fallback for users wanting zero infra (accepting that raw
160	  video then flows through Modal).
161	- **⚠️ Operational / support burden (a real adoption risk).** For the primary beachhead —
162	  Indian badminton **academies/coaches** — asking them to *run and maintain a worker on
163	  their own VM/GPU* is a meaningful ongoing load (updates, monitoring, firewall/NAT, the
164	  "it stopped after our IT change" ticket). So: **default academy users to `hosted`**, and
165	  treat `byo_worker`/SkyPilot as a **power-user / enterprise / privacy-sensitive tier**,
166	  not the academy default. If/when BYO ships, plan for **auto-updating, self-healing
167	  agents + health heartbeats + clear worker status in the UI**, and budget the support cost.
168	- **Middle tier to consider — "zero-infra BYO":** a managed-but-isolated path where the
169	  **storage** stays in the user's bucket (signed URLs) while compute runs on **our** GPUs
170	  in a **strictly isolated, per-tenant, ephemeral sandbox** (nothing persists our side).
171	  This gives the BYO *privacy* benefit (raw video never persists on our infra) **without**
172	  the user running a worker — a pragmatic default between full-hosted and full-BYO.
173	
174	The pipeline code is unchanged; only *where it's invoked* and *how it gets bytes* vary.
175	
176	### 3.3 Reuse, don't reinvent
177	The existing `segmenter` / `provider` / `validator` / `sport` / `annotation` registries
178	are the proven precedent and stay as the **pipeline** layer. The `annotation` registry +
179	`candidate_segments` table are also the natural seam for the **coach-correction / golden
180	-set** loop in the assistant-coach phase (§6, P4).

182	## 4. Multi-tenant data model & serving layer
183	
184	### 4.1 Entities — generic core, with the coach model as an optional overlay
185	The foundational schema is deliberately **domain-neutral** so we don't overfit to the
186	coach mindset — the coach/athlete framing is a **market-fit hypothesis that will iterate**
187	(see C13 / PMF), not a load-bearing assumption. **Generic core:**
188	```
189	User ──< VideoCollection ──< Video ──< Highlight ──< HighlightMetadata
190	                                 └──< PlaySegment ──< Event
191	Video / Highlight ──< Job (processing record: status, compute backend, timings)
192	```
193	- **Generic & re-targetable:** a `VideoCollection` groups a user's videos (a season, an
194	  event, a "folder") with no assumption of a coach or academy — a power user, a coach, or a
195	  parent are all just `User`s with collections.
196	- **Highlights are first-class** (today compile only writes a file): a `highlights` table
197	  (segment ids + output `StorageRef` + params + created_at) powers "see past videos and
198	  highlights by history," and **`HighlightMetadata`** carries the **rich semantic tags**
199	  (shot type, rally outcome, etc. — see §6 metadata stage) plus titles / ratings / notes.
200	- **`video_id` stays the content MD5** (dedup within a tenant), scoped by `tenant_id`.
201	- **Coach overlay (optional, additive):** for the academy/coach GTM, layer
202	  `Org/Academy → Coach → Athlete` *on top* (e.g. a `Membership`/role table + an `athlete_id`
203	  tag on collections/videos) **without** baking it into the core tables — so the schema
204	  stays usable for solo power users and the coach model can evolve, or be dropped, as PMF
205	  dictates.
206	- **History/serving API:** list collections/videos/highlights per user (and, with the
207	  overlay, by athlete/coach/date); **query highlights by `HighlightMetadata`** (e.g. shot
208	  type / outcome); re-stitch from stored segments without reprocessing.
209	
210	### 4.2 Tenancy isolation — options & recommendation
211	| Model | Isolation | Ops cost | Best for |
212	|---|---|---|---|
213	| **Shared DB + `tenant_id`** (row-level, ideally Postgres **RLS**) | logical | low | **Hosted SaaS, many small tenants** ← *recommended default* |
214	| Schema-per-tenant | medium | medium | tens–hundreds of mid tenants |
215	| **DB-per-tenant** (incl. **SQLite-per-tenant**) | strong/physical | higher at scale | **self-hosted single-academy**, or high-isolation enterprise |
216	
217	**Recommendation:** for the hosted product, **migrate SQLite → Postgres with shared-DB +
218	`tenant_id` + Row-Level Security**; keep **SQLite-per-tenant** as the **self-hosted /
219	single-academy** deployment (it reuses today's code almost verbatim). Either way,
220	**abstract DB access behind a repository layer now** so the engine is swappable, and
221	graduate the `PRAGMA user_version` migration discipline to **Alembic** under Postgres.

223	## 5. Orchestration / async jobs
224	
225	This is the serving layer that makes multi-user real. It is the **multi-user superset of
226	[`DEFERRED_HARDENING_PLAN.md`](DEFERRED_HARDENING_PLAN.md) #16** (async job model) — build
227	that first, single-tenant, then generalize.
228	
229	- **Job record** (`jobs` table): `id, tenant_id, video_id, type (index|compile|analyze),
230	  status (queued|running|done|failed), progress, compute_backend, result_ref, error,
231	  timestamps`. `/api/process` returns **202 + job_id**; `/api/jobs/{id}` polls.
232	- **Idempotency** keyed on `(tenant_id, video_id, pipeline_version)` — reuse the
233	  content-hash discipline already in `compute_video_id`.
234	- **Dispatch:** the orchestrator enqueues; a worker (hosted or `byo_worker`) claims jobs
235	  for its tenant, resolves input via the tenant's `StorageBackend`, runs the pipeline,
236	  writes artifacts + DB rows. **Observability reports** (already per-video) become the
237	  job artifact surfaced in history.
238	- **Queue/worker backend — a decision to prototype in #16, *not* a default here.** The
239	  *requirements* are firm — **idempotency**, **resumability** (a 40-min GPU job mustn't
240	  restart on a worker blip), **progress states** — which rule out fire-and-forget Celery/RQ
241	  for the long jobs. The *choice* should be made by prototyping in the
242	  [`DEFERRED_HARDENING_PLAN.md`](DEFERRED_HARDENING_PLAN.md) #16 slice, weighing:
243	  - **Start simplest:** **Arq** (async-native, natural FastAPI fit) or even a **plain
244	    Postgres-backed queue + worker** — likely sufficient for the *first* single-tenant
245	    async slice, with the lowest operational complexity and the easiest debugging.
246	  - **Durable-execution upgrade if/when needed:** **Hatchet** (Postgres-backed, per-step
247	    retries/timeouts/concurrency; pairs neatly with the pull-based worker) — attractive
248	    because it adds **no new datastore** once we're on Postgres, but it *is* a new
249	    dependency + operational/debugging surface; adopt only when long-job resumability/
250	    observability demands it.
251	  - **Heaviest:** **Temporal** — most mature durable workflows, operationally heavy;
252	    reserve for genuinely complex multi-stage pipelines at scale.
253	
254	  Record the decision criteria in #16: operational complexity, maturity, **debugging
255	  experience for long GPU jobs**, and whether durability is worth a new dependency.
256	  **Bias: start with the simplest thing that gives retries + status; graduate only on
257	  evidence.**

259	## 5A. Owned generative model (the video-QA assistant) & the data flywheel
260	
261	The north-star capability: an **owned, self-hostable generative video model** —
262	fine-tuned on sports video (including **consented, user-contributed** footage) — that
263	**answers questions about rallies, shots, and technique**. This is the conversational
264	brain of the "assistant coach." Crucially, it does **not** replace the known stack; it
265	is introduced **behind the same abstraction, with the paid API as an always-ready
266	fallback**.
267	
268	> **The moat is *not* the model.** Anyone can download Qwen-VL/Gemma. The defensible
269	> assets are **(a) the consented, badminton-specific video→QA dataset** and **(b) the
270	> eval harness**. Build and message *those* — not "we own an LLM."
271	
272	This conversational surface (NL queries + coach-mode recommendations) must be **localized
273	from the start** for the Bangalore beachhead — the query *and its answer* in the user's
274	language. The locale foundation and the templated-answer approach are specified in
275	[`I18N_PLAN.md`](I18N_PLAN.md) (phase P4 ties to this section).
276	
277	> **✅ Committed guardrail (legal, non-negotiable).** We respect the licensing findings in
278	> full. **Paid frontier models (Gemini / OpenAI / Anthropic) are used for *inference /
279	> serving / fallback* only — never as a *training* data source.** Harvesting their outputs
280	> to train our owned model would breach their "no competing model" terms (a terms/copyright
281	> violation), so it is prohibited in both engineering and legal process. **Training teachers
282	> are open, Apache-2.0 models only** (Qwen-VL / InternVL / Gemma 4). Detail in the
283	> distillation constraint below.
284	
285	### Core principle: AI is a pluggable provider with a paid fallback
286	The codebase already abstracts the cloud AI behind `provider_registry` /
287	`AIVideoProvider` (`backend/providers/`). Make that a **first-class platform principle**:
288	- Every generative capability routes through the **provider registry**.
289	- The **owned model** plugs in as a new provider (`owned_vlm`); **Gemini (paid, via
290	  Vertex AI)** stays registered as the **fallback** (failover on error/low-confidence,
291	  or as the quality ceiling/teacher reference).
292	- This lets us **ship today on the known paid stack** and **swap in the owned model when
293	  its quality clears a measured bar** — with zero architectural churn and the paid path
294	  always one config flip away. (Mirrors the COMMERCIALIZATION C4 A/B/C strategy: the
295	  owned model is the long-run "(A) eliminate the per-call dependency"; paid is "(C)".)
296	
297	### The model / training layer (new sub-layer, fed by the scaffolding)
298	```
299	Data curation        Training              Eval                 Serving
300	(consented user vid  (fine-tune an open,   (extend the existing (self-host inference
301	 + golden set +      commercially-usable   eval harness to QA   as a provider /
302	 rally/segment/event base VLM via          quality + the        ComputeBackend;
303	 annotations →       LoRA/QLoRA)           regression gate)     paid fallback)
304	 video-QA pairs)
305	```
306	This layer **reuses every other layer**: **Storage** holds the training corpus;
307	**Data** supplies labels (the `annotation` registry + `candidate_segments` +
308	golden set are already the labeling seam); **Compute/Orchestration** runs training and
309	inference jobs (even **BYO-compute** can serve inference on the tenant's GPU); the
310	**eval harness** already in `backend/eval/` extends to grade QA quality. **In other
311	words, the rock-solid scaffolding is exactly what makes the model flywheel possible** —
312	which is why scaffolding comes first (see §6).
313	
314	### Base model & training (Apache-2.0 only — licensing is decisive)
315	**Recommended near-term base: `Qwen2.5-VL-7B-Instruct`** — Apache-2.0, native long-video
316	(dynamic-FPS sampling, temporal mRoPE), mature LoRA tooling. Upgrade path
317	**Qwen3-VL-4B/8B (Apache-2.0)**; **Gemma 4 multimodal (Apache-2.0, 2026)** is a clean
318	Google-stack alternative to evaluate.
319	- ⚠️ **Lock to Apache-2.0-clean bases** so you can fine-tune, **keep weights private,
320	  gate behind subscriptions, and never owe open-sourcing or branding**. (Note Qwen2.5-VL
321	  is Apache **only at 7B/32B** — 3B/72B use the custom Qwen license.)
322	- ❌ **Reject for the flagship:** **Gemma 3** — custom terms with a **viral derivative
323	  clause** (anything fine-tuned on it, *or even trained on its synthetic outputs*, stays
324	  permanently bound to Google's *updatable* Prohibited-Use Policy); **Gemma 4's switch to
325	  Apache-2.0 removes this**. **Llama 3.2 Vision** — custom license forces a "Llama-…"
326	  model name + "Built with Llama" badge and a 700M-MAU ceiling. **`gpt-oss`** — Apache-2.0
327	  but **text-only**, so usable only as an optional text-reasoning layer, never the video
328	  encoder.
329	- **Training method:** **QLoRA** (≈ r=64, α=128) on the 7B — fits one prosumer GPU and
330	  avoids catastrophic forgetting of general video skills. Build the dataset by converting
331	  the existing rally/shot/segment annotations + golden set into templated **clip→QA
332	  pairs**, expand synthetically with **open-model teachers only** (see constraint below),
333	  and hold out a **golden QA eval** that gates every fine-tune. A few hundred gold pairs →
334	  **5k–20k** curated is a realistic band for this narrow domain.
335	- **Serving economics:** a 7B VLM ≈ 14 GB VRAM (FP16) / ~3.5 GB (INT4); a ≥16 GB GPU is a
336	  comfortable serve target (vLLM for throughput). Self-hosting wins **only** once you have
337	  sustained video-QA volume **+** a defensible consented dataset **+** real per-call API
338	  cost pain — below that, the paid API is cheaper than a standing GPU and the second stack
339	  is overhead. Hence: **paid-primary now → owned-primary / paid-fallback later.**
340	
341	Base-model licensing + training-data policy are tracked as **COMMERCIALIZATION C14**.

343	### Training backend — managed service vs self-managed (the fine-tune "forge")
344	*Where* you run the LoRA/RL fine-tune. Weigh on **video support, weight export/ownership,
345	smallest servable model, RL support, no-train DPA, and infra burden**.
346	
347	**Decisive finding (researched 2026-06):** managed fine-tuning services are
348	**image-based** (JSONL + base64 images) — for video you pre-sample frames and feed them
349	as image sequences. **Only the self-managed `ms-swift` explicitly advertises *native*
350	video (+audio) training.** So for true video-QA, a self-managed framework is the
351	strongest technical fit — and it also lets you fine-tune the **small 7B** (cheap to
352	serve) and keep full ownership. Managed services trade some of that for zero infra.
353	
354	| Option | Type | Video / VLM support | Smallest VL | RL | Export weights | Best for |
355	|---|---|---|---|---|---|---|

357	| **LLaMA-Factory** | Self-managed | Qwen3-VL + 100+ VLMs; video datasets | any incl 7B | ✅ | ✅ | popular, well-documented |
358	| **Unsloth** | Self-managed (1-GPU optimized) | Qwen3-VL LoRA (vision+lang; frames) | any incl 7B | ✅ GRPO | ✅ | cheapest first runs |
359	| **Tinker** (Thinking Machines) | Managed API (low-level) | Qwen3-VL **30B-A3B+ only**; image input (video **unverified**) | 30B-A3B MoE | ✅ PPO/GRPO, custom loss | ✅ adapters + ckpt; no-train ToS | zero-infra RL/research at MoE scale |
360	| **Together AI** | Managed (tune + serve) | Qwen3-VL / Gemma-3 / Llama-4; image data | verify | partial | ✅ adapters downloadable | managed Qwen3-VL + serving |
361	| **Fireworks AI** | Managed (tune + serve) | Full Qwen2.5-VL (3B–72B SFT; LoRA@32B + LoRA-upload) | **7B** | partial | ⚠️ verify export (lock-in risk) | managed *small*-VL + serving |
362	| **Predibase** (Rubrik) | Managed **+ VPC self-host** | VLM instruct-tune; **LoRAX** multi-adapter | verify | ✅ (VPC) | ✅ **RFT/GRPO** flagship | RL "creativity" + multi-adapter + privacy |
363	| ~~OpenAI GPT-4o / Gemini tuning~~ | Closed | — | — | — | ❌ no export | **non-fit — violates "own the model"** |
364	
365	*(Enterprise clouds — Databricks Mosaic / SageMaker / Vertex on open models — give full
366	control but are only worth it if you're already on that stack.)*
367	
368	**Recommendation:**
369	- **Early iteration / true video-QA →** self-managed **`ms-swift`** (or LLaMA-Factory /
370	  Unsloth) on a **rented GPU** (RunPod / Lambda / Modal / SkyPilot-to-your-cloud): native
371	  video, any size incl. **7B** (cheap to serve), full ownership, and it drops into the
372	  **ComputeBackend / BYO-compute** seam (§3.2). **Likely a better fit than Tinker** for
373	  the video requirement *and* serving economics.
374	- **Managed, no GPU ops →** **Together AI** (Qwen3-VL + downloadable adapters + serving)
375	  or **Fireworks** (full Qwen2.5-VL incl. 7B + serving) — confirm frame/video support and
376	  adapter export.
377	- **If RL "coaching creativity" + per-sport multi-adapter is central →** **Predibase**
378	  (RFT + LoRAX, VPC self-host for the biometric/privacy posture) or **Tinker** (lowest-
379	  level RL primitives).
380	- **Tinker** remains a strong zero-infra RL-research option with clean weight export — just
381	  not the cheapest path to a *small video* model (its VL floor is 30B-A3B).
382	- **Portability is the hedge:** you own the **data + recipe + exported weights**, so the
383	  backend is swappable — same ethos as the provider/registry pattern. Don't get locked in.
384	
385	**Verify before committing (any backend):** (1) **native video / frame-sequence**
386	ingestion + max frames per example; (2) **weight export** + a **commercial DPA** covering
387	consented, minors-excluded video (biometric, §7); (3) the **inference plan** for the size
388	you train (a self-managed **7B** is far cheaper to serve than a 30B-A3B MoE).

390	### Training harness — make it agent-runnable (nanochat-style operability)
391	The goal: **an agent (or CI) can run a fine-tune on a fresh batch of golden-labeled video
392	and get a trustworthy ship / no-ship verdict, unattended.** Karpathy's **nanochat** is the
393	reference for that *operability* — one MIT repo, one `speedrun.sh` that runs
394	tokenizer→train→eval→serve, a single complexity dial, and an automatic **report-card**
395	score. It is **not** a usable engine here (text-only, from-scratch GPT-2-class), but its
396	five properties are exactly what make training agent-runnable, and we copy them:
397	**(1)** one command, end-to-end; **(2)** one complexity dial (sane auto-derived defaults);
398	**(3)** an automatic **report card** — a deterministic pass/fail vs a target (the crux);
399	**(4)** reproducible + deterministic + cheap; **(5)** minimal/readable.
400	
401	**Engine (don't reinvent):** **`ms-swift`** already delivers this for VLMs — CLI-driven,
402	**native video**, Qwen3-VL support, an eval backend (EvalScope), and reproducibility via
403	`args.json` + `full_determinism`. (LLaMA-Factory is the close second; HF **`nanoVLM`** —
404	~750 lines — is the minimal reference to *learn* VLM training, not the production path.)
405	
406	**The harness = thin glue over components we already have** — one declarative,
407	agent-invokable job (call it `train_speedrun`):
408	1. **Build dataset** from golden labels → clip→QA pairs (reuse the `annotation` registry +
409	   `candidate_segments` + golden set — the labeling seam in `backend/`).
410	2. **Fine-tune** via ms-swift on a **ComputeBackend** GPU (§3.2), run as an orchestration
411	   job (§5 / DEFERRED #16): one config, idempotent, logged.
412	3. **Auto-eval + report card** — extend the existing `backend/eval/` regression harness to
413	   **QA quality**; emit a `report.md` pass/fail vs the **held-out golden QA eval**.
414	4. **Register** the result as the `owned_vlm` provider (Gemini paid fallback stays) **only
415	   if it beats the bar**.
416	
417	So: **golden labels → ms-swift train (on a compute backend) → eval gate → register
418	provider**, behind one command an agent or CI runs. nanochat is the inspiration for the
419	wrapper; ms-swift is the engine; the **golden QA eval is the report card**.
420	
421	> **Prerequisite (the crux):** the harness is only as trustworthy as the **golden QA eval
422	> set**. nanochat's speedrun is meaningful *because* its eval (CORE score) is automatic and
423	> trustworthy; ours is the golden QA eval — **build that first**, or an agent-run loop
424	> optimizes blind. (Same "moat = dataset + eval", scaffolding-first principle.)
425	
426	### ⚠️ Teacher / distillation constraint (the single biggest legal landmine)
427	You **cannot** train the owned model on outputs from the paid frontier APIs — a general
428	video-QA assistant is squarely a *"competing model"*: **Gemini** ("may not use the
429	Services to develop models that compete"), **OpenAI** ("may not use Output to develop
430	models that compete"), **Anthropic** (bars using Outputs to train competing models). Two
431	safe lanes: **(1)** generate synthetic QA with **open-model teachers only** (Qwen-VL /
432	InternVL / Gemma 4 — Apache-clean); **(2)** keep the paid API strictly as a **runtime
433	fallback** — serving answers is fine, *harvesting its outputs to train the model that
434	replaces it is not*. Write a hard **"no training on competitor-API outputs"** rule into
435	eng + legal process. (This makes the ROADMAP's "Gemini as offline teacher only" precise:
436	the teacher is *open models*, not the paid APIs.)
437	
438	### Data flywheel, personalization & consent tiers
439	Two complementary loops, each with its **own** opt-in (training consent is separate from
440	processing consent — §7):
441	
442	- **Global model (shared — raises the floor).** Train the base owned model on an
443	  **explicitly-contributed, licensed** corpus — *not* on whatever sits in a tenant's bucket
444	  (preserves "your video, your storage"). Flywheel: *more consented, labeled matches → a
445	  better shared model → better highlights/answers → more reason to contribute.* Higher
446	  consent bar (pooled data, biometric/minor care — §7); **minors excluded by default**.
447	
448	- **Per-user adapters (personalized — raises the ceiling) — owner hunch, under exploration.**
449	  A small **per-user (or per-tenant) LoRA adapter, fine-tuned *only on that user's own
450	  consented videos*** on top of the shared base, served via **multi-LoRA** (LoRAX /
451	  Together / Predibase). Why it's compelling:
452	  - **Precision:** adapts to *that user's* court, camera angle, lighting, and players'
453	    styles → materially better detection/highlights for them.
454	  - **Cleanest consent story:** *"improve **your** detection using **your** data"* is far
455	    lower-friction and lower-risk than contributing to a global model — the data improves
456	    **only the user's own adapter**, with **no cross-user mixing**, sidestepping much of the
457	    pooled-corpus biometric/minor entanglement. Reinforces the differentiator: *your video,
458	    your storage, your compute — and now **your model**.* With BYO-compute the adapter can be
459	    trained/served on the user's own GPU and **never leave their boundary**; **deletion =
460	    drop the adapter** (clean erasure).
461	  - **Open questions (still a hunch):** cold-start (need enough of the user's labeled data
462	    before a personal adapter beats the base — fall back to the shared model meanwhile); a
463	    **per-user held-out eval** to prove the adapter helps (don't ship a regression); base +
464	    optional global-adapter + per-user-adapter stacking; per-user training cost at scale.
465	    Worth a spike once the harness + golden eval exist.
466	
467	**Two consent tiers, then:** **(a)** "improve **my own** detection with **my** data"
468	(per-user, low friction) and **(b)** "contribute to the **shared** model" (global, higher
469	bar). **Default for both is off.**

494	## 7. Privacy & legal (gait raises the bar — design for it now)
495	
496	- **The load-bearing nuance:** biometric data is special-category **only when used to
497	  *uniquely identify* a person** (GDPR Art. 9). **Highlight/shot detection on players a
498	  coach already knows is general analytics — generally *not* Art. 9.** But
499	  **gait/biomechanics that builds a per-athlete identifying template tips into Art. 9**
500	  and needs **explicit, granular consent** referencing biometric data. Engineer gait
501	  with that boundary (consent gate, purpose limitation, no cross-account identification);
502	  decide whether it runs **locally/on-tenant only** (strong posture) vs our cloud. (EDPB
503	  Guidelines 3/2019 on video devices apply.)
504	- **Minors (e.g. academies).** Parental/guardian consent and safeguarding are first-order,
505	  not an afterthought. Model consent explicitly per relationship (user↔subject, coach↔athlete
506	  where the overlay applies, parent↔minor).
507	- **BYO-storage is the central privacy/liability lever:** if raw video stays in the
508	  tenant's own bucket/Drive and we process via signed URL or their compute, we minimize
509	  what we hold — shrinking breach surface, residency, and erasure obligations.
510	- **Paid-LLM no-train (C4):** use **Gemini via Vertex AI** (contractual no-training),
511	  **not the consumer/free tier**; set short/zero retention, document it in the DPA, and
512	  surface "your footage is never used to train AI" as a trust feature for academies. For
513	  the gait phase, prefer keeping biometric inference off third-party APIs entirely.
514	- **Training consent is a distinct, higher bar (for the owned model, §5A).** Training on
515	  user video needs a **separate, explicit, opt-in training licence** — not bundled with
516	  processing consent — and it **compounds** the biometric (Art. 9) and minor-consent
517	  issues above. Train **only on explicitly contributed/licensed video**; never train on
518	  what merely passes through a tenant's bucket. **Exclude minors' video from the training
519	  pool by default**, keep the training corpus a **separate, firewalled, opt-in sub-pool**,
520	  and log **per-clip consent/provenance** for revocation + audit. Incentives must not make
521	  consent non-free (the product stays fully usable without contributing). And the
522	  **teacher-distillation rule** (§5A): never train on paid-LLM outputs. **Two consent tiers
523	  (§5A):** *(a)* "improve **my own** detection with **my** data" — a per-user adapter trained
524	  only on the user's own video (lowest friction; no cross-user mixing; deletion = drop the
525	  adapter); *(b)* "contribute to the **shared** model" — pooled corpus, higher bar. Default
526	  for both is **off**.
527	- **Right to erasure / retention:** per-tenant, per-athlete delete must cascade across DB +
528	  storage artifacts (the `ON DELETE CASCADE` discipline already in `database.py` extends here).

530	## 8. Key decisions for the owner (the forks)
531	
532	1. **Hosted-first vs BYO-first.** Recommended: **hosted control-plane first** (P0–P1) with
533	   **BYO-storage soon after** (P2); **BYO-compute later** (P3) as a power-user/enterprise
534	   option — it's the highest-complexity, highest-security item.
535	2. **Database now or later.** Move to **Postgres at P1** for the hosted path, or stay
536	   SQLite-per-tenant if self-hosted-single-academy is the first GTM. (Abstract DB access
537	   regardless.)
538	3. **Auth: build vs buy** (Auth0 / Clerk / Supabase Auth / Cognito).
539	4. **Orchestration tech** (see research recommendation) — bias to the simplest that gives
540	   retries + status.
541	5. **Gait processing location** — local/on-tenant (privacy-max) vs cloud (capability-max).
542	6. **How far to push BYO-compute** given its security/ops complexity.
543	7. **Owned-model base + licensing (§5A).** Which commercial-OK video VLM to build on
544	   (Qwen-VL Apache-2.0 vs Gemma 3 custom license vs …) and confirm a gated commercial
545	   derivative is permitted — see COMMERCIALIZATION C14.
546	8. **Training-data sourcing & consent.** Opt-in contribution terms, incentives, and the
547	   teacher-distillation constraint (whether paid-LLM outputs may seed the corpus).
548	9. **When to start the owned model** — strictly after the scaffolding + flywheel are
549	   solid (the explicit directive), with the paid provider as the standing fallback.
550	
551	**Risks:** scope explosion (sequence strictly P0→P5); multi-tenant data-leak bugs (RLS +
552	tests); BYO-compute security; **biometric/minor liability** (get this right before any
553	gait feature ships); **training on user video without proper opt-in/licence**, and
554	**base-model / teacher-distillation licence violations**; cost of hosted GPU (training
555	*and* inference); **premature model-building** before data/eval are ready (mitigated by

1	#!/usr/bin/env bash
2	#
3	# Detect a spare local NVMe and mount it at /scratch for fast video decode.
4	#
5	# DO GPU Droplets ship a SECOND raw NVMe (the "scratch" disk), unmounted by default; a
6	# regular CPU box has only the boot disk — then we just create /scratch on it. The hot path
7	# is sync-first (copy video local -> ffmpeg-decode there), so scratch belongs on the fast
8	# local disk. Point the pipeline at it with  export TMPDIR=/scratch  or  --scratch /scratch.
9	#
10	# EPHEMERAL by design (wiped on destroy / may not survive a power-cycle) and deliberately NOT
11	# added to /etc/fstab (a renamed device could block boot). Nothing durable lives here.
12	set -euo pipefail
13	MNT=/scratch
14	mkdir -p "$MNT"
15	
16	root_src=$(findmnt -n -o SOURCE / 2>/dev/null || true)
17	root_disk=$(lsblk -no PKNAME "$root_src" 2>/dev/null | head -1 || true)
18	[ -z "$root_disk" ] && root_disk=$(basename "${root_src:-}" | sed -E 's/p?[0-9]+$//')
19	
20	cand=""
21	while read -r name type; do
22	  [ "$type" = "disk" ] || continue
23	  [ "$name" = "$root_disk" ] && continue
24	  bytes=$(lsblk -bdno SIZE "/dev/$name" 2>/dev/null | head -1)
25	  [ "${bytes:-0}" -lt 10000000000 ] && continue            # skip tiny config drives (<10 GB)
26	  if lsblk -no MOUNTPOINT "/dev/$name" | grep -q '/'; then continue; fi   # skip if already mounted
27	  cand="$name"; break
28	done < <(lsblk -dno NAME,TYPE)
29	
30	if [ -n "$cand" ]; then
31	  dev="/dev/$cand"
32	  echo "[scratch] spare disk: $dev"
33	  if ! blkid "$dev" >/dev/null 2>&1; then
34	    echo "[scratch] no filesystem -> mkfs.ext4 $dev"
35	    mkfs.ext4 -F -q "$dev"
36	  fi
