The headline finding: the `python -m backend.main` CLI single-shot does **checksum → validate → segment → report** but **never stitches**; stitching lives on the API/job path and requires explicit segment IDs. There is **no aggregated per-phase wall-clock timing in the live pipeline** — the one real timing/cost harness is `scripts/nightly_reelcount.py` (segmentation only), and `RunTelemetry` exists but is wired only into the fusion-golden eval.

### Exact programmatic call to stitch ALL indexed rallies (no SPA)

**Option A — direct compiler call (simplest; this is exactly what the dev script does).** Query every play segment for the `video_id`, turn them into time-pairs, and call the compiler:

**Option B — go through orchestration (applies the min_shot_count floor + watermark localization):**

### Ready-made script (nearly turnkey, one caveat)

## Q3 — Existing performance / latency instrumentation

### There IS a telemetry module — but it is not in the live pipeline
`backend\utils\run_telemetry.py` — `class RunTelemetry` (`:135`) is a rotating ~10 KB JSONL "black box" of execution velocity + machine health (GPU temp/util/VRAM via `nvidia-smi`, CPU/RAM via `psutil`):
```python
# backend/utils/run_telemetry.py:186-209 (snapshot derives fps + elapsed_s)
now = self._clock()
rec = {"t": self._iso(now), "elapsed_s": round(now - self._t0, 1)}
if phase is not None: rec["phase"] = phase
...
rec["fps"] = round((done - self._last_done) / (now - self._last_t), 1)
```
**Wiring:** it is instantiated **only** in `backend\eval\fusion_golden.py:322` (label `"fusion_golden"`, writes `output/run_telemetry.jsonl`; snapshots at `:216`, events at `:384-403`). The production CLI (`backend/main.py`) and `orchestration.py` do **not** import or use it.

### The live pipeline records NO per-phase wall-clock
- Grep for `perf_counter` / `time.monotonic` / `duration_ms` / `PhaseTimer` in `backend\orchestration.py` → **none**. The only `elapsed` there are minute-granular UI progress strings for cloud-job polling: `_wait_progress_message` (`orch:236`) and `_compile_wait_message` (`orch:1241`) — text only, never persisted.
- Repo-wide, `time.perf_counter`/`PhaseTimer`/`stopwatch` appear **nowhere in production** — the single hit is a test double `_FakeTimer` at `tests\test_job_worker_module_seam.py:78`.

### The per-video "observability report" records durations of CONTENT, not of processing
`emit_indexer_report` (`backend\reporting\__init__.py:29`) harvests into technical/customer/JSON reports. Its `duration` fields are **video/segment content durations**, not wall-clock: `backend\reporting\harvest.py:63-65` (`meta["duration_s"]`), `:111`/`:186` (`total_play = sum(segment durations)`). In-process facts arrive as **counters** via `run_signals.incr` (`backend\reporting\run_signals.py:22`), popped at report time. **No processing time is written to the DB or the report.**

### Ad-hoc `time.*()` timing that DOES exist (all in scripts/eval)
- `scripts\nightly_reelcount.py:433-435` — `t0 = time.monotonic(); result = ...process_video(...); wall = time.monotonic() - t0` → per-run `wall_seconds` (the real perf harness, see Q6).
- `scripts\run_phase3_eval.py:193,206` — `time.time()` around segmentation per config sweep.
- `scripts\run_process_and_stitch.py:70-72` — times the MD5 only.
- `scripts\verify_compute_path.py:99,102` — `time.monotonic()` for a poll timeout (not perf).

**Bottom line for your benchmark:** nothing in the live pipeline emits stage timings you can read back; you will need to wrap the four stages yourself (or reuse `RunTelemetry` from `backend/utils/run_telemetry.py`, which is already GPU-health aware and designed for exactly this).

## Q4 — Segmenters and local-GPU feasibility (8 GB RTX 2070)

Registered in `backend\pipeline\segmenters\__init__.py`; each registers under its `name`:

| Segmenter (`--segmenter` value) | Class / file:line | Local? | Needs cloud key? | GPU? |
|---|---|---|---|---|
| `motion` | `motion.py:14`, reg `:243` | ✅ fully local | No | No (pure OpenCV CPU) |
| `gemini` | `gemini.py:75`, reg `:707` | ❌ cloud | **Yes** `GEMINI_API_KEY` (`gemini.py:106-113`) | No local GPU |
| `yolo_hybrid` | `yolo_hybrid.py:48`, reg `:596` | partial | **Yes, always** (`yolo_hybrid.py:87-98`, no skip path) | ✅ torch/CUDA (PersonDetector) |
| `wasb_hybrid` | `wasb_hybrid.py:25`, reg `:68` | ✅ if `skip_ai_handoff` | Only if handoff on | ✅ (WSL2 or native) |
| `tracknet_hybrid` | `tracknet_hybrid.py:23`, reg `:48` | ✅ if `skip_ai_handoff` | Only if handoff on | ✅ (WSL2 only) |
| `fusion_hybrid` | `fusion_hybrid.py:41`, reg `:243` | ✅ if `skip_ai_handoff` | Only if handoff on | ✅ (WSL2 or native) |

Key mechanics:
- **The hybrid trajectory segmenters skip the cloud entirely when `indexing.skip_ai_handoff=True`** — `backend\pipeline\segmenters\trajectory_hybrid.py:199-208` sets `model_name="local-noai"` and does no provider call / no API key. With the default `False`, they require `GEMINI_API_KEY` for the Phase-3 handoff (`trajectory_hybrid.py:209-225`).
- **`yolo_hybrid` has no such escape** — it unconditionally requires the key (`yolo_hybrid.py:87-98`) and returns `Failure` without it.
- **GPU placement:** the torchvision person detector picks CUDA at `backend\pipeline\detectors\person_detector.py:84-85` (`self.device = "cuda" if use_gpu and torch.cuda.is_available() else "cpu"`). WASB/TrackNet shuttle detection runs torch/CUDA either inside **WSL2** (`detector_impl="auto"`, the default — `tracknet_runner.py`/`wasb_runner.py`) or **Linux-native** (`detector_impl="native"` → `backend\pipeline\detectors\native_wasb_runner.py`). That native runner's docstring explicitly records validation **on an RTX 2070** (`native_wasb_runner.py:30-32`) — but via WSL; on your Windows box the practical GPU path for wasb/tracknet is `detector_impl="auto"` (WSL2).
- **Defaults:** `config.json:26` sets `default_segmenter: "gemini"` (note the code default in `models.py:203` is `"yolo_hybrid"` — config.json wins). Per-run override flag: `--segmenter` at `backend\main.py:1316-1320` (choices = registered names).

**Truly-local, no-key options on the RTX 2070:** `motion` (CPU) or `wasb_hybrid` / `tracknet_hybrid` / `fusion_hybrid` with `skip_ai_handoff=true` + `use_gpu=true` + `detector_impl="auto"` (WSL2). `gemini` and `yolo_hybrid` both need the cloud key.

### Concrete recommendation for a repeatable performance-benchmark script
Deterministic config: `default_segmenter=wasb_hybrid` (or `motion`), `indexing.skip_ai_handoff=true`, `use_gpu=true`, `detector_impl=auto`, `deployment.compute_target=""` (all-local). Then, per input video, wrap the four call sites — `compute_video_id` (`main.py:1508`), `registry.run_all_with_context` (`main.py:1513`), `segmenter.process_video` (`main.py:1552`), and `VideoCompiler(...).compile_highlights(video_path, [(s["start_time"], s["end_time"]) for s in db.query_play_segments(video_id, {})], "highlights.mp4")` (Q2 Option A) — in `time.monotonic()` (or reuse `RunTelemetry` from `backend\utils\run_telemetry.py:135` for GPU-health-annotated phase snapshots). This stitches the entire reel with zero user interaction, which no current CLI entry point does.
