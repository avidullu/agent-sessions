## 1. String-externalization model (§2.1, lines 44–56)

- **The invariant:** *no hardcoded user-facing strings.* Every coach-facing string is a **stable key** resolved at render time against the active locale. Code references `t("compile.button")`, **never the English prose** (lines 46–47). This single rule is what makes "add a language = add a catalog" true, and it is **CI-enforced** (§2.6) so it cannot silently regress.
- **`t("key")` frontend / `tr(lang, key, params)` backend** are the two accessors.
- **Key naming convention** — dotted, hierarchical, namespaced-by-surface/intent. Exact examples the doc commits to (lines 52–56):
  - `"Validate & Index Video"` → `t("video.action.validate_index")`
  - `alert("Validation Failed! …")` → `t("toast.validation_failed")`
  - `` `${count} Rally Segment${count>1?'s':''} Selected` `` → `t("compile.selected", {count})` *(ICU plural)*
  - `HTTPException(detail="Video file not found at …")` → `detail = tr(lang, "error.video_not_found", {path})`
- **ICU MessageFormat for interpolation + plurals** (§2.2, lines 69–72): `"{count, plural, one {# rally} other {# rallies}}"`. Rationale called out explicitly: the current UI hand-rolls English plurals (`Rally Segment${count > 1 ? 's' : ''}`), and **Kannada/Hindi plural rules differ from English** — ICU encodes each language's rules **in the catalog, not the code.**

## 2. Catalog layout (§2.2, lines 58–74)

```
locales/
  en/  common.json   # source of truth — devs author keys here
  kn/  common.json   # Kannada  (Gemini-draft → human-review)
  hi/  common.json   # Hindi    (next; first exercise of the extensibility checklist)
```

- **Format: i18next-flavored JSON** (line 67) — deliberately chosen to work for **both** the vanilla shim today *and* react-i18next in the SPA, **with no conversion**.
- **`en` is the single source of truth**; every other locale is **keyed identically** to `en`, enforced by the key-parity check (§2.6) (lines 73–74).
- Proposed file/seam paths (§5, lines 195–199): new dirs `locales/{en,kn,hi}/`, `backend/i18n/`, `scripts/i18n_draft.py`; fonts under `backend/assets/fonts/`.

## 3. Locale-negotiation order (§2.3, lines 76–89)

**One resolution order, defined in one place, honored by both UI and backend** (line 81):

```
persisted user preference  →  UI switcher / ?lang=<code>  →  Accept-Language header  →  default "en"
```

- Supported locales enumerated in **a single module** (one list to grow); anything outside it falls back to `en` (lines 84–85).
- Backend localizes its **own** responses (`HTTPException.detail`, report `customer_*`) from the *same* `lang` query param / `Accept-Language` header, so a Kannada UI gets Kannada errors (lines 86–87).
- **Always-fallback to `en`** for any missing key — a missing translation degrades to English, never to a blank or a raw key shown to a user (lines 88–89).

## 4. Backend text → keys + params (§2.4, lines 91–107)

- Today validators/errors bake English prose *and* interpolated values together (`f"…sharpness score of {avg} is below … threshold of {threshold}."`). Design **separates the two**:
  - Validator/endpoint emits a **stable code + params dict** — e.g. `("blur.below_threshold", {"score": avg, "threshold": threshold})` (lines 97–98).
  - **Prose lives in the catalog**, looked up at the API boundary in the negotiated locale (line 99).
  - `ValidationResult` keeps an **English `message`** for logs/back-compat but **gains optional `message_key` + `message_params`**; the report/serializer prefers the key when present. Internal/technical messages stay English (debugging) while customer-facing text localizes (lines 100–103).
- `spec.yaml` `customer_verdict` + per-rule `customer_message` become **keyed** (or per-locale overlays keyed by rule `code`); the technical `message` blocks stay English (they cite `README#Qn`, are for the operator) (lines 105–107).

## 5. Translation pipeline — Gemini-DRAFT → human-REVIEW (§2.7, lines 134–147; also §1 lines 35–38)

```
dev authors en keys → scripts/i18n_draft.py (Gemini, INFERENCE only) → kn/hi draft
                    → native-speaker review (owner reviews first draft)
                    → CI key-parity + placeholder check → merge
```

- `scripts/i18n_draft.py` reads `locales/en/*.json`, asks Gemini for each **missing** key in the target locale **with the key name and any ICU placeholders preserved**, and writes a draft catalog with **every machine-drafted value flagged for review** (lines 142–144).
- It **never touches `en`, never invents keys**, and is a *drafting aid only* — a human reviews before merge (lines 144–145).
- **GUARDRAIL (load-bearing, stated twice — lines 37–38, 146–147, and §"Guardrail alignment" lines 222–223):** Gemini is used for **inference only** (drafting); it is **NEVER a training-data source.** This is the same "paid LLM = inference, never training" posture as the rest of the system, consistent with `CLAUDE.md` and the ratified licensing guardrail. The owner reviews the first draft of **every** string.

## 6. CI enforcement (§2.6, lines 122–132) — "the guardrail that keeps it by design"

## 1. What KhelSutra is (one breath, for context)

KhelSutra turns ordinary badminton video (phone/GoPro on a tripod behind the court) into useful pieces **automatically**: it finds the rallies, stitches a **highlight reel** (MP4 with a small *"Generated by Khelsutra.guru"* mark), and gives a **simple summary** (how many rallies, how much real play time). Core loop: **record → upload → get back a reel + summary.** No editing skill, no special hardware, no manual scrubbing. (KHELSUTRA_PRODUCT_OVERVIEW "In one line"; "What it does today.")

The hard, differentiating problem is **multi-court** halls (busy/noisy footage); it already works very well on **clean single-court** recordings and multi-court is the sharpening focus. (OVERVIEW "the problem we're solving"; VIDEO_RECORDING_GUIDELINES §"#1 capture rule": multi-court precision measured ≈0.20 vs ≈0.31 single.)

## 3. Non-tech-savvy UX principles the docs assert

These are stated or directly implied by the docs — each is real, not invented:

1. **Zero hand-holding / guided happy path with zero knobs.** Alpha goal is "10–25 invited testers, **end-to-end, zero hand-holding**" (UI_PROPOSAL §3). The OVERVIEW core loop is deliberately three steps: record → upload → reel + summary.
2. **Hide all technical machinery.** "Segmenter choice hidden"; the WASB/owned-model path is **not exposed** in alpha; alpha serves the Gemini path with no GPU in the request path (UI_PROPOSAL §1). 3. **Recording-education FIRST (teach before upload, don't fail after).** "The UI must teach recording guidelines *before* upload, not fail videos after" (UI_PROPOSAL §2). A2 carries an **inline recording-guidelines checklist** (pre-upload education from VIDEO_RECORDING_GUIDELINES) (UI_PROPOSAL A2). Already partly shipped: a homepage **"Record it right"** gist + a `/capture` checklist page (next-session handoff "Already shipped"). The capture rules to surface plainly: fixed tripod, elevated, **whole court in frame**, landscape, keep it still (no pan/zoom), good lighting, **single match per frame**, **audio on/mic unobstructed** (VIDEO_RECORDING_GUIDELINES §2, §"#1 rule"; OVERVIEW "capture matters").
4. **Plain language / low jargon.** Product copy is deliberately plain: "**in plain words**" (FLYER); "**the simple summary**", "**no editing skill needed**", "(plainly)" framings throughout OVERVIEW. The handoff lever: "**plain-language/low-jargon copy**."
5. **"Simple summary" as a first-class output.** Repeatedly named — not "analytics dashboard" but "a **simple summary** — how many rallies were found and how much actual play time" (OVERVIEW; FLYER; PLAYBOOK; PMF_FIELD_SIGNALS). Keep the numbers minimal and human.
6. **Fewer steps + bigger touch targets + mobile-first.** Named levers in the handoff: "**fewer steps + bigger touch targets**, **mobile-first** (coaches use phones)." Today's alpha is only "usable on phone, optimized for laptop" (UI_PROPOSAL §3) — closing the mobile gap is the work.
7. **Visual / iconographic over text.** Handoff lever: "**visual/iconographic over text**." Status is already expressed as **chips/icons** (verdict ✅/⚠️/❌ per video) (UI_PROPOSAL A1). The capture guide is meant to be "short, friendly, **illustrated**" (VIDEO_RECORDING_GUIDELINES §4).
8. **WhatsApp-native sharing / feedback.** The field channel is WhatsApp (FLYER "phone/WhatsApp"; PLAYBOOK; UI_ALPHA_EXECUTION_PLAN feedback channel = "WhatsApp group or Google Form"). Handoff lever: "**WhatsApp-friendly share**." Enthusiasts/parents want to **share** reels (UI_PROPOSAL §2; OVERVIEW). (Note: explicit share links are an alpha **non-goal** — Beta Drop 3 adds athlete-facing expiring share links — so "WhatsApp-friendly" today means the downloaded MP4 is easy to forward, per OVERVIEW "watch, download, and share.")
9. **Background processing the user can walk away from.** "It processes in the background. You can **close the tab and come back later**; you don't have to sit and watch it" (OVERVIEW; backed by the async job model, B1). Sets the expectation that long Indian-uplink uploads + multi-minute processing are normal and don't require babysitting.
10. **Honest, calm expectation-setting (no overpromise).** See §5 (Copy/tone). This is a UX principle, not just copy: the product tells users plainly what it does **today** vs the roadmap, and frames misses as useful feedback, not breakage (OVERVIEW "Read this honestly" callouts).
11. **Correction is easy and low-stakes (the user is a co-builder).** A4 review must let a non-technical coach accept/reject/nudge with **bulk "all good"** and simple chips; "You don't need to be technical — just tell us, in your words" (UI_PROPOSAL A4; OVERVIEW "What feedback helps us most").
12. **Localized first contact (Kannada-first, Hindi-next).** Reduce friction "exactly at the point of first contact" by speaking Kannada first; always **fall back to English** for any missing string so a user never sees a blank or raw key (I18N_PLAN §1, §2.3).

## 5. Copy / tone guidance

## 1. The recording guidance content (what the doc says to do)

The doc frames every recommendation around one fact: **highlight quality is bounded by input quality** — capture choices directly move the detector's precision/recall. The concrete guidance, dimension by dimension (from the §2 table and the #1 rule):

| Dimension | Doc guidance |
|---|---|
| **#1 rule — single match per frame** | Record ONE match on ONE court, no adjacent/background-court play. MEASURED (2026-06-18): multi-court precision ≈0.20 (~80% false positives) vs ≈0.31 single-court with tighter boundaries. This is the *dominant* precision failure. |
| **Camera position** | Fixed tripod, elevated, behind/above one baseline, whole court in frame. Static full-court view avoids the broadcast "camera-tracking" trap (ADR-004). |
| **Camera height & angle** | 3–5 m elevated (~4.5 m), **~30° down-tilt**, behind one baseline, whole court + net headroom. |
| **Framing / margins** | Entire court + a margin; players never leave the frame. Cropping breaks detection and the relevance check. |
| **Resolution** | ≥1080p preferred; 720p likely floor. (2K/4K may help shuttle tracking but cost more compute.) |
| **Frame rate** | ≥30 fps badminton/pickleball; ≥60 fps table tennis (30 fps collapses fast-ball detection: 22.5% → 93.2% at 60 fps). |
| **Stability** | Tripod / fixed mount; no panning or zoom during play. Handheld jitter inflates motion signals. |
| **Lighting / exposure** | Even indoor lighting; avoid backlight/glare; minimize motion blur. |
| **Audio (REQUIRED, ADR-007)** | Record with audio ENABLED (don't mute). Keep mic unobstructed. **Avoid aggressive wind/noise reduction** that flattens the shuttle "thwack" impact transient. Camera reasonably close to the court helps SNR (shuttle hits are quiet). |
| **Court contrast / background** | Clear court markings; minimal moving background where possible. |
| **Codec / container** | MP4 (H.264/HEVC). |
| **Landscape orientation** | (Implied by "whole court in frame"; not an explicit doc row — see Gaps.) |

The doc is explicit that the numeric thresholds are **placeholder/UNVERIFIED starting points** (to be set empirically per §3), *except* the frame-rate and camera-geometry rows (literature-backed) and the single-court rule (measured). ## 3. Gaps — what a non-tech-savvy person could still get wrong

These are items present (or implied) in the doc but **missing, vague, or under-specified** in the shipped site copy, judged from the standpoint of someone setting up a phone + tripod for the first time:

1. **Camera HEIGHT is qualitative, not numeric.** The doc says **3–5 m (~4.5 m) elevated**. The site says only "elevated (a high tripod or a balcony)" / "a few metres up." A first-timer with a standard ~1.5 m tripod on the floor behind the baseline will set up too low — exactly the occlusion/keystoning failure the doc's height row warns about. The "~30° down-tilt" number survived to the site but the height number did not, so users can't actually achieve that tilt geometry. **Highest-value gap to close.**

2. **No reference image / diagram.** The doc's §4 explicitly calls for an "illustrated" guide ("Put the camera here, this high…"). Both pages are text-only. For a non-tech-savvy user, one annotated photo (camera behind baseline, height, tilt, court fully in frame) would do more than all the prose. Currently nothing visual.

3. **"Behind one baseline" can be misread.** A novice may place the camera at *court level* behind the line, or behind the *side* line. The site never clarifies "baseline = the short back line, and the camera must be raised above head height," nor that side-on is not the supported profile. The doc's "behind/above one baseline" intent is only partially conveyed.

4. **Why audio matters / how to verify it.** The site says "Audio ON … wind/noise reduction off," but doesn't tell a user *how* to turn off a GoPro/phone's automatic wind-noise filter, or that an obstructed/cased mic defeats it. The doc's "keep mic unobstructed" and "camera reasonably close to the court helps SNR (shuttle hits are quiet)" — the proximity point is **dropped entirely** from the site.

5. **"Don't crop the players" has no failure cue.** The doc warns players must *never leave frame* (it breaks detection). The site states it as a rule but gives no check ("walk to all four corners before you start — if anyone goes out of frame, zoom out / move back"). Easy to get wrong with doubles.

6. **No "verify before you record" step.** Nothing tells a first-timer to record 20 seconds, play it back, and confirm the whole court + both ends are in frame and steady. This single habit would catch gaps 1, 3, and 5 at once.

7. **Resolution floor / "what if my phone shoots 4K vertical."** Site says "1080p+, landscape" but a user filming in default vertical 4K won't know that **portrait is wrong even at high resolution**. "Landscape" is stated but its importance isn't motivated, so it reads as optional.

8. **Tournament / multi-court reality.** The doc's measured ≈0.20 multi-court precision means a busy hall genuinely underperforms today. The site honestly says multi-court is "the hard case," but a non-tech academy user recording a 6-court hall may still expect clean reels. The honesty is present; the *practical instruction* ("for best results point the camera at one court only, even in a busy hall") could be sharper.

Items intentionally NOT user-facing (correctly omitted from the site, not gaps): codec internals, the empirical-threshold methodology (§3), the per-dimension precision numbers, ADR references, and the validator-at-ingest plan.

## 4. How this content should localize (Kannada / Hindi — high early value)

This is **instructional, action-oriented copy** aimed squarely at the non-tech-savvy academy owner / parent / player — the exact audience most likely to read in Kannada or Hindi rather than English. It is high-value to translate early, and relatively safe to translate because it is concrete and finite.

- **Prioritize the two capture surfaces first.** The `#record` homepage gist and the whole of `capture.html` are the single highest-leverage strings to localize — they gate input quality, which gates everything downstream. Translate these before marketing/FAQ prose.
- **Keep numerals and units in figures, not words.** "1080p", "30 fps", "60 fps", "~30°", "3–5 m" should stay as digits across all three languages — they read identically and avoid translation drift. Localize only the surrounding instruction.
- **Translate the Do/Avoid table as a unit** — it is the most scannable, lowest-literacy-load element and travels well into Kannada/Hindi as a two-column "ಮಾಡಿ / ಬೇಡ" · "करें / न करें" list.
- **The "golden rule" sentence is the keystone string** — one match, one court, full frame, don't move the camera. It appears verbatim on both pages; translate it ONCE and reuse, so the Kannada/Hindi wording is identical across surfaces (consistency matters for a rule users must remember).
- **Loan-word handling.** Terms like "tripod", "baseline", "landscape", "audio", "fps", "GoPro" are commonly used as English loanwords in Kannada/Hindi sports speech — prefer the transliterated loanword over a coined native term where the loanword is what coaches actually say (validate with a native speaker). "Net", "court", "rally", "smash" similarly stay as loanwords.
- **Closing the gaps above is best done in the SOURCE first, then localized** — adding the height number, a diagram (language-neutral, localize only the caption/labels), and a "record 20s and check" step in English, *then* translating, avoids translating copy you're about to rewrite. The diagram is especially valuable for low-literacy users and is reusable across all three languages with only label swaps.
- **Consent / minors line must be localized carefully** (capture.html): "Footage involving minors is never used … and is never published" is a legal/trust statement (GDPR-adjacent, per the project's guardrails) — have a native speaker confirm the translation doesn't soften the commitment.

## 5. Cleanest place to wire react-i18next

The architecture is small and clean, which makes wiring straightforward:

**Provider.** Add the i18n init + provider at the **app root in `main.tsx`** (`main.tsx:9-13`). Either import a side-effecting `./i18n.ts` (calls `i18n.use(initReactI18next).init(...)`) before render, or wrap `<App/>` in `<I18nextProvider i18n={i18n}>`. `main.tsx` is the single render entry, so this is the one place that guarantees the context wraps everything. No other provider exists to coexist with.

**Catalog dir.** Create `web/src/locales/{en,kn,hi}/common.json` (or split by namespace: `app`, `query`, `grid`, `footer`, `result`). Keys mirror §2's grouping. Vite imports JSON natively, so static `import en from "./locales/en/common.json"` in `i18n.ts` works without extra tooling (no backend/HTTP loader needed for an offline appliance).

**Derived labels.** `lib/query.ts` `filterLabel`/`sortLabel`/`limitLabel`/`summarize` (`query.ts:305-334`) are pure and must stay test-friendly (node env, `query.test.ts`). Cleanest: keep them returning **structured descriptors** (they nearly do — `{field, op, value}`, `{key, dir}`, `limit`) and move the *text* rendering into the QueryBar component using `t()` with interpolation, OR pass a `t` formatter into `summarize`. Do NOT scatter `useTranslation` into the lib layer (breaks the node-only test env in `vite.config.ts:test.environment="node"`).

**Language switcher + persistence.** Add a small `<select>` in the header (`App.tsx:200-204`, next to the wordmark) calling `i18n.changeLanguage(lng)`. Persist via `i18next-browser-languagedetector` with order `['localStorage','navigator','htmlTag']` and `caches: ['localStorage']` — there is currently zero localStorage usage, so no collision. Also set `<html lang>` reactively on change (today it is hardcoded `en` at `index.html:2`) for a11y/SEO correctness.

**Pluralization.** Replace `format.ts pluralize` (`format.ts:11-13`) at its two call sites (`SelectionFooter.tsx:50,60`) with i18next's plural support (`t('footer.summary', { count })` + `_one`/`_other`/`_many` keys), since Hindi/Kannada plural rules differ from English `+ "s"`.

**Number/time.** `mmss` (`format.ts:4-8`) is locale-neutral (m:ss) and can stay; but Kannada/Hindi may want native-digit rendering via `Intl.NumberFormat` if the owner wants full localization.

## 6. UX friction for a non-tech-savvy user (concrete)

**Engineering/internal jargon leaks into the UI:**
- `?video=<video_id>` URL/placeholder language is shown verbatim to users in **two** banners and an error (`App.tsx:115-116`, `App.tsx:264`, demo/error banners `App.tsx:262-279`). A non-technical user cannot act on "open with `?video=<video_id> against a running engine`."
- "engine", "compile", "min_shot_count floor", `<code>min_shot_count</code>` surface raw backend vocabulary in the footer warning (`SelectionFooter.tsx:51-53`) and throughout. "the engine's `min_shot_count` floor" is meaningless to an end user.
- "alpha", "experimental", "(under development)" appear in multiple places (`App.tsx:209`, `QueryBar.tsx:97`, `RallyGrid.tsx:60-63`). Honest, but anxiety-inducing and unexplained for a lay user.
- "reel", "rally", "stitched", "compile" assume domain fluency. "Reel name" (`SelectionFooter.tsx:64`) with placeholder "my-highlights" mixes two metaphors.
- Build-failure surfaces **raw engine error text** straight through (`CompileResult.tsx:60-64`, fed by `parseDetail` of FastAPI `{detail}` at `App.tsx:135,250-258`) — likely a stack-ish or technical message, untranslated and unfriendly.

**The query bar over-trusts text literacy:**
- The whole primary filter mechanism is a **free-text command line** ("over 10s", "top 15 longest") (`QueryBar.tsx:42-49`). A non-tech-savvy and/or non-English user will struggle to type valid English grammar tokens. The deterministic parser only understands **English** keywords (`query.ts:59-134`) — a Hindi/Kannada user typing native words gets "Couldn't read that" (`QueryBar.tsx:76`). **Critical localization gap:** translating the UI chrome does NOT make the query bar work in Kannada/Hindi; the grammar itself is English-only. Consider replacing/augmenting the text bar with **tap-only controls** (sort dropdown, length slider, the existing example chips promoted to primary).
- The example pills double as machine input (`QueryBar.tsx:20`), so they can't simply be translated — a Kannada label that no longer parses would break tap-to-apply (guarded by `QueryBar.examples.test.ts`). This is a real i18n tension to design around.

**Density / hierarchy:**
- The parsed-pill row, "not available yet" struck-through chips, "Try:" chips, and the "experimental" note (`QueryBar.tsx:60-98`) stack a lot of meta-information under one input — high cognitive load for a novice.
- Two separate "experimental/not-available" treatments (greyed strike-through chips vs amber note vs amber card chips) may read as errors/warnings to a lay user.

**Small touch targets / desktop assumptions:**
- Bulk buttons, example chips, and unavailable chips use `px-3 py-1` / `py-0.5` / `text-xs` (`App.tsx:224-226`, `QueryBar.tsx:62-92`) — well under the ~44px touch-target guideline; hard for thumbs on mobile.
- The card grid is `minmax(150px,1fr)` (`RallyGrid.tsx:23`); the whole layout is centered in `max-w-5xl` columns (`App.tsx:200,207`, `SelectionFooter.tsx:58`) — a desktop-console layout. On a phone the `min-w-[16rem]` input (`QueryBar.tsx:48`) and sticky footer with many inline items (`SelectionFooter.tsx:58`) will wrap awkwardly.
- "Reel name" label is **hidden on small screens** (`hidden sm:inline`, `SelectionFooter.tsx:64`), leaving a bare input with only a placeholder — a novice may not know what it's for.
- Hover-only affordances: card hover borders (`RallyGrid.tsx:40`), and key explanations live in `title=` tooltips (`QueryBar.tsx:69`, `RallyGrid.tsx:60`) that don't exist on touch devices — so the *reason* a chip says "not available yet" or that shot-count is unreliable is **invisible on mobile**.

**Selection model surprise:**
- "Everything starts selected; drop what you don't want" (`App.tsx:213-215`, default-all at `App.tsx:55,68`, `useRallySelection.ts:7-9`) is a deliberate but non-obvious inversion of the usual "pick what you want." Applying a query *replaces* the whole selection (`App.tsx:160-162`, `useRallySelection.ts:18`), which can silently discard hand-tuning — a novice may not connect Apply with "my checkmarks changed."
- The ✓/empty circle on cards is `aria-hidden` and color-only (green fill vs transparent) (`RallyGrid.tsx:45-53`) — selection state leans on color, a contrast/colorblind concern.

**Positive UX notes (keep):** the duration-first framing is consistent and honest (`App.tsx:212-215`, `RallyGrid.tsx:56`, `QueryBar.tsx:95-98`); the floor warning is genuinely user-protective (`SelectionFooter.tsx:25-56`); aria-labels exist on most interactive elements (`QueryBar.tsx:47`, `RallyGrid.tsx:35`, `SelectionFooter.tsx:70`, `CompileResult.tsx:35`).

## 3. How the HTML is structured today (and where `data-i18n`/`t()` attaches with least churn)

- **Three standalone documents**, each fully self-contained: its own `<head>`, its own inline `<style>` (the design tokens in `:root` are copy-pasted across all three, e.g. `index.html:25-32`, `capture.html:13`, `own-model.html:14`). No shared CSS file, no shared partials, no header/footer include.
- **All copy is inline text nodes** directly in the markup. There is **no templating** of any kind — `server.js` streams the raw file (`server.js:56-58`), so nothing is interpolated server-side.
- Markup is mostly clean, semantic elements (`<h1>/<h2>/<h3>`, `<p>`, `<li>`, `<summary>`, `<label>`, `<option>`), which is **friendly to `data-i18n`** — most strings sit in a single element with no children.
- **Complication: rich inline markup inside strings.** Many strings wrap `<b>`, `<span>`, `<i>`, or even an `<a>` inside the translatable unit (e.g. the golden-rule callout `index.html:334` has a bold lead + a muted `<span>`; the H1 splits across `<span class="hl">` at `:247`; the FAQ "How do I join?" answer embeds `<a href="#join">` at `:487`). A naive `data-i18n` that replaces `textContent` would **destroy that inner markup**. Two least-churn options:
  1. Split into sub-keys where an inner span carries semantic styling (e.g. `hero.h1.lead` + `hero.h1.hl`), giving each `<span>` its own `data-i18n`. This matches how the design already isolates the highlighted fragments in their own elements.
  2. Allow a small subset of inline tags in the catalog value and set `innerHTML` for keys explicitly flagged as rich (a `data-i18n-html` variant), reserving it for the handful of strings with embedded links/bolds.

**Recommended least-churn attach pattern:**
- Add `data-i18n="<key>"` to each leaf element holding a string; the shim queries `document.querySelectorAll('[data-i18n]')` and sets `textContent` (or `innerHTML` for `data-i18n-html`).
- For **attributes** (the `aria-label`, `<input placeholder>`, `<meta content>`, `<title>`, `alt`, button `title`), use a parallel `data-i18n-attr="aria-label:key;placeholder:key2"` convention so the same pass localizes attributes.
- For the **`<option>`** elements and **segment/GPU/storage labels**, each is already a discrete element — straightforward `data-i18n` on each `<option>`/`<span>`.
- Set `<html lang>` and `dir` from the chosen locale at boot. (Kannada + Hindi are both LTR, so no RTL work.)
- Because there's no build step, the shim and catalog must be plain `.js`/`.json` loaded via `<script>` and run on `DOMContentLoaded`, before first paint ideally (inline-blocking, tiny) to avoid a flash of English.

This is **low churn**: it's purely additive (`data-i18n` attributes + one `<script>` per page); no markup restructuring beyond splitting the few rich-text strings into spans that, in several cases, already exist.

## 4. Is the form/reveal JS inline or in `src/`? Where should `t()` live so SPA + site share catalogs?

**Inline.** All interactive page JS — the academy-toggle, the submit/fetch handler, the honeypot, the `mailtoFallback`, and the entire `revealAfterSignup` video logic — is a **single inline IIFE** in `index.html:597-712`. The reveal's user-facing strings ("1 · The tool in action", "2 · A real reel it made", the auto-close stamp, "✕ Close") are **JS string literals built via `host.innerHTML = '…'`** (`:621-627`), so they are *not* reachable by a `data-i18n` DOM pass — the shim's `t(key)` must be **callable from JS** and used to build that HTML.

The `src/` modules are **backend-only** and share nothing with the browser: `src/index.js` (Worker handler), `src/store.js` (D1/SQLite adapters), `src/notify.js` (email). None of them emit page copy; their only strings are JSON error codes and the operator email. So the i18n shim does **not** belong in `src/`.

**The SPA (`web/`) is a separate React/TS/Vite/Tailwind app** with its own `web/src/lib/` of pure formatters (`format.ts` already has `mmss`, `pluralize`, `reelFilename` — `web/src/lib/format.ts`). It has no i18n either. To let **both** the SPA and the static site share one catalog format:

- **Catalog format:** flat JSON keyed by dotted string id, one file per locale: `en.json`, `kn.json`, `hi.json`. Values are plain strings with `{var}` placeholders for `t(key, vars)` interpolation (e.g. `"reveal.autoclose": "auto-closes {secs}s after the reel stops"`). This format is consumable identically by a vanilla `<script>` (site) and by an ESM `import` (SPA/Vite).
- **Shim:** a tiny dependency-free `t(key, vars)` that looks up the active locale's catalog, falls back to `en`, and does `{var}` substitution. It must be authored as **framework-agnostic ES module** (no React, no DOM assumptions in the core `t()`), with a thin DOM-walker wrapper (`applyI18n(root)` doing the `[data-i18n]` pass) used only by the static site, and a thin React hook/`useT()` wrapper used only by the SPA.
- **Where it should live (shared):** a new top-level package the repo can reference from both `site/` and `web/` — e.g. `khelsutra/i18n/` (or `web/src/lib/i18n.ts` re-exported), holding `catalogs/{en,kn,hi}.json` + `t.js`/`t.ts`. The static site copies/symlinks the catalog into `site/public/i18n/` (so `server.js`/`serveStatic` serves it as a static asset — it already serves arbitrary `public/` files and knows `.js`/`.json` MIME types via `TYPES`, `server.js:26-30`) and includes the compiled `t.js` via `<script>`. The SPA imports the same JSON catalogs through Vite.
- **Practical caveat:** today there is **no shared parent module system** — `site/` is dependency-free vanilla and `web/` is a Vite app. The shared catalog is the easy part (plain JSON, copy into both); the `t()` *code* needs two thin adapters (one IIFE/global for the site, one ESM for the SPA) over one core. The cleanest home is a small `i18n/` dir with the core + both adapters, with the JSON treated as the single source of truth both sides consume.

## 1. react-i18next setup essentials (kn/hi)

**Packages** (the standard trio): `i18next`, `react-i18next`, `i18next-browser-languagedetector`; add `i18next-http-backend` for lazy-loading catalogs over HTTP. ([i18next intro](https://www.i18next.com/), [Crowdin tutorial](https://crowdin.com/blog/react-i18n))

**Init** — declare your supported langs explicitly and fail closed to a fallback:

```js
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';
import HttpBackend from 'i18next-http-backend';

i18n
  .use(HttpBackend)
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    supportedLngs: ['en', 'hi', 'kn'],   // restricts detector to what you actually ship
    fallbackLng: 'en',
    ns: ['common', 'highlights', 'errors'],
    defaultNS: 'common',
    interpolation: { escapeValue: false }, // React already XSS-escapes
    backend: { loadPath: '/locales/{{lng}}/{{ns}}.json' }, // lazy per-lng+ns
    detection: {
      order: ['querystring', 'cookie', 'localStorage', 'navigator', 'htmlTag'],
      caches: ['localStorage', 'cookie'],   // persists the user's pick
      lookupQuerystring: 'lng',
      lookupLocalStorage: 'i18nextLng',
    },
  });
```

- **Namespaces**: split catalogs by feature (one JSON file per `{lng}/{ns}`) rather than one giant file; load on demand. ([react-i18next docs / Language Unlimited](https://www.languagesunlimited.com/react-i18next-documentation/))
- **Lazy-loading**: `i18next-http-backend` only downloads a language/namespace file when first needed (e.g., when the user switches to Kannada), so you don't ship hi+kn+en up front. ([Crowdin](https://crowdin.com/blog/react-i18n))
- **Language detector + persistence**: default detection order is `['querystring','hash','cookie','localStorage','sessionStorage','navigator','htmlTag','path','subdomain']`; default `caches` is `['localStorage','cookie']`, so the chosen language is remembered across visits. `supportedLngs` makes the detector pick the best match from your real list instead of an unshipped locale. ([i18next-browser-languageDetector](https://github.com/i18next/i18next-browser-languageDetector))

**Plural handling — important nuance.** i18next's *native* plural system (JSON format v4, since v21) is **suffix-based**, NOT ICU by default. It uses the browser's `Intl.PluralRules` under the hood and resolves keys like `key_one` / `key_other`. The interpolation variable **must be named `count`**. ([i18next plurals](https://www.i18next.com/translation-function/plurals))

```json
// hi/highlights.json — Hindi: only one/other (see §CLDR below)
{ "rallies_one": "{{count}} रैली", "rallies_other": "{{count}} रैलियाँ" }
```
```js
t('rallies', { count: 3 }); // → "3 रैलियाँ"
```

If you specifically want **ICU/MessageFormat** syntax (`{count, plural, one {…} other {…}}`) — e.g., to share one catalog format with translators/tools — add the **`i18next-icu`** plugin; otherwise i18next won't parse ICU strings. **[uncertain on your preference]** — for hi/kn the suffix form is simpler and sufficient (both are one/other), so I'd default to native suffixes and only reach for `i18next-icu` if your translation vendor requires ICU. ([i18next intro](https://www.i18next.com/))

### CLDR plural categories for hi and kn (verified)
Per the Unicode CLDR Language Plural Rules chart (v48), **both Hindi and Kannada use exactly two cardinal categories: `one` and `other`**, with the identical rule:

> `one` ⇐ `i = 0 or n = 1` (i.e. the integer part is 0, or n equals 1); everything else → `other`.

A consequence non-Western devs miss: in hi/kn, **0 is grammatically "one"**, so "0 items" takes the singular form. Source: [CLDR Language Plural Rules chart](https://www.unicode.org/cldr/charts/48/supplemental/language_plural_rules.html). So each plural key needs only `_one` and `_other` for these languages.

## 3. Shared catalog: one JSON format for the SPA *and* the static HTML pages

Goal: the Vite/React SPA (i18next) and a no-framework HTML page consume the **same** `{lng}/{ns}.json` files. Two practical approaches:

**Option A (lowest-friction): use the i18next suffix format as the single source of truth**, and write a ~30-line shim for the static pages that mirrors i18next's `{{var}}` interpolation and its `count`→`Intl.PluralRules` suffix resolution. Because hi/kn are one/other, this is trivial:

```js
// tiny-i18n.js — shared, framework-free; reads the SAME *.json catalogs
export function makeT(catalog, lng) {
  const pr = new Intl.PluralRules(lng); // returns 'one' | 'other' for hi/kn/en
  return (key, vars = {}) => {
    let k = key;
    if (vars.count != null && catalog[`${key}_${pr.select(vars.count)}`])
      k = `${key}_${pr.select(vars.count)}`;       // mirror i18next suffixes
    let s = catalog[k] ?? key;                       // fallback to key, never crash
    return s.replace(/\{\{(\w+)\}\}/g, (_, n) => (vars[n] ?? `{{${n}}}`)); // {{var}}
  };
}
```
This reproduces i18next's two behaviors the static pages need — `{{var}}` interpolation and `_one/_other` plural selection via the same `Intl.PluralRules` i18next itself uses — so **the JSON files are byte-for-byte reusable**. ([i18next plurals](https://www.i18next.com/translation-function/plurals); the minimal-vanilla-i18n pattern is established, e.g. [Andreas Remdt's tiny i18n script](https://andreasremdt.com/blog/building-a-super-small-and-simple-i18n-script-in-javascript/))

For static HTML, drive it declaratively with `data-i18n` attributes and a small loader:
```html
<button data-i18n="share_whatsapp">Share on WhatsApp</button>
<script type="module">
  const lng = localStorage.getItem('i18nextLng') || 'en';   // shares the SPA's stored pick
  const cat = await (await fetch(`/locales/${lng}/common.json`)).json();
  const t = makeT(cat, lng);
  document.querySelectorAll('[data-i18n]').forEach(el => el.textContent = t(el.dataset.i18n));
  document.documentElement.lang = lng;                       // sets <html lang> for fonts/a11y
</script>
```
Both surfaces read the same `localStorage` key (`i18nextLng`) the detector writes, so the language choice **persists across the SPA and static pages** with no extra plumbing.

**Option B (if you want ICU as the canonical format):** store catalogs in ICU MessageFormat, run the SPA with `i18next-icu`, and have the static shim parse ICU with a tiny library (e.g. `@messageformat/core` / `intl-messageformat`). More portable to translation tools, but adds a parser dependency to the static page — only worth it if a translation vendor mandates ICU. **[uncertain — pick based on vendor/tooling; for an in-house hi/kn app, Option A is lighter.]**

## 4. UX for low-literacy / non-tech-savvy Indian users

Grounded in HCI4D research (Medhi-Thies et al.) and India "next billion users" practice ([ICTworks](https://www.ictworks.org/traits-low-literacy-technology-users/), [UX Bulletin](https://www.ux-bulletin.com/designing-low-digital-literacy-users/), [Medhi-Thies, UW](https://courses.cs.washington.edu/courses/cse490c/18au/readings/medhi-thies-2015.pdf), [Next-billion UX](https://medium.com/@meinbhidesigner1/crafting-ux-for-indias-next-billion-digital-users-141b07f55210)):

- **Language switcher placement**: put it **up-front and in-script, on first run** — show each option **in its own script** ("हिन्दी", "ಕನ್ನಡ", "English"), not flag icons or English names. Keep it persistently reachable (top bar / settings), large, and remember the choice (the persisted `i18nextLng`). India is multilingual; let users switch anytime.
- **Icon + text, always paired** — never icon-only. A download control should show an icon **and** the word. Low-literacy/novice users rely on the text and the picture together. ([UX Bulletin](https://www.ux-bulletin.com/designing-low-digital-literacy-users/))
- **Plain words, not tech jargon** — prefer "Save"/"Send" over "Sync"/"Export"; in hi/kn use everyday colloquial terms, not Sanskritized/literary register that even literate users find stiff. Translate *meaning*, and have a native speaker review tone.
- **Big touch targets, linear flows** — large tappable buttons (≥48dp), one primary action per screen, minimal typing, generous spacing; avoid dense menus and Western conventions (hamburger menus, abstract gestures) that novices don't decode. ([Medhi-Thies](https://courses.cs.washington.edu/courses/cse490c/18au/readings/medhi-thies-2015.pdf))
- **Voice & visual cues** — voice input/output and audio labels dramatically help low-literacy users; short looping video/animated demos and real photos (not abstract illustration) teach flows better than text. ([Building UI/UX for non-tech-savvy](https://lightweightsolutions.co/building-ui-ux-for-non-tech-savvy-users-designing-for-digital-literacy/))
- **WhatsApp is the share channel** — it's the default social/sharing surface for this audience. Offer a first-class, prominently-placed "Share on WhatsApp" button. Use the official deep link, URL-encode the text, and **localize the prefilled message** to the active language:
  ```js
  const text = encodeURIComponent(t('share_msg', { url: highlightUrl })); // hi/kn message
  location.href = `https://wa.me/?text=${text}`; // wa.me deep link; works web+mobile
  ```
  (Research on WhatsApp in low-literacy South-Asian populations underscores how central and accessible it is — design the share to land *in* WhatsApp. [ACM SIGACCESS WhatsApp study](https://dl.acm.org/doi/full/10.1145/3663547.3746389))
- **High contrast & forgiving design** — high-contrast text on solid backgrounds, clear focus/selected states, confirmations before destructive actions, and obvious "back"/"home" affordances so users can always recover.

## 5. Common pitfalls

- **Concatenated/“stitched” strings.** Don't build sentences by joining fragments (`t('You have') + n + t('rallies')`) — word order differs in hi/kn and it breaks plurals. Use one full message with `{{var}}`/plural keys per language.
- **Hardcoded plural logic.** Don't write `n === 1 ? 'x' : 'xs'` in code — that's English's rule. Let `Intl.PluralRules`/i18next pick the category; for hi/kn remember **0 → `one`**. ([CLDR chart](https://www.unicode.org/cldr/charts/48/supplemental/language_plural_rules.html))
- **Missing font fallback / tofu.** No Indic web font + a glyph not in the system font = □□□ boxes. Always self-host Noto for both scripts and include a system-font fallback in the `font-family` chain; set `<html lang>` correctly so the browser picks the right shaping/font.
- **Untranslated dynamic content.** Strings from the API/DB (status messages, category names, error text from the backend, `alt` text, `aria-label`, `<title>`, `meta`, validation errors, toast/notification text) silently stay in English. Audit *all* user-visible text, including attributes and server responses.
- **Number/date/locale formatting.** Use `Intl.NumberFormat`/`Intl.DateTimeFormat` (or i18next `format`) with the active locale (`hi`, `kn`) instead of hardcoded `en-US`. Note Indian grouping (lakh/crore: `1,00,000`) and that **Hindi/Kannada commonly display Western (ASCII) digits** in modern UIs — don't force native-script digits unless you've confirmed users prefer them. **[uncertain — validate digit preference with target users.]**
- **FOIT / no `font-display: swap`** → blank text while the (large) Indic font loads on slow networks. Set `swap`.
- **Not persisting the choice** → user re-picks language every visit; ensure detector `caches` and the static shim read the same stored key.
- **English-width assumptions.** Devanagari/Kannada strings and line heights differ from English; don't pin button/container sizes to English text length, and give vertical breathing room for tall conjuncts/matras.
