# Account Aggregator Framework: Where Decryption Happens

## The Data Flow

The framework employs end-to-end encryption where:

1. **FIP encrypts data** using the FIU's public key before transmission
2. **AA remains data-blind** – it never accesses unencrypted financial information
3. **FIU decrypts locally** using its private key after receiving the encrypted payload

As stated in the material: "The FIU receives the encrypted payload and decrypts it locally using its private key. The AA never sees the clear-text data at any point."

## Why This Design

This architecture ensures the AA cannot read, store, or misuse financial data. The FIU maintains exclusive access to decryption keys, preserving data confidentiality throughout transit. This "data-blind" principle is fundamental to the RBI's consent-based framework.

Local decryption at the FIU prevents any cloud intermediary from accessing sensitive financial information, making it a security advantage over traditional statement-sharing methods.

The FIP generates a shared key using an Elliptic Curve Diffie Hellman (ECDH) function using the FIU's public key received in the data request. Similarly, the FIU generates a shared key using an ECDH function using the FIP's public key received in the FIP's response.

# Data-In-Transit Encryption for FIU Backend

Based on the documentation, here's how decryption works in the FIU's technical setup:

## Decryption Process

When the FIU's backend receives encrypted financial data from the FIP (via the Account Aggregator), it performs these operations:

1. **Identity Verification**: The backend validates the AA's permanent digital signature against the central registry.

2. **Shared Secret Generation**: Using ECDH key exchange, the FIU computes a shared secret by combining:
   - The FIP's public key (received in the response)
   - Its own private key (generated during the initial request)

3. **Session Key Derivation**: The backend generates a 256-bit session key using HKDF, incorporating:
   - The shared secret from ECDH
   - A salt derived from both the FIU nonce and FIP nonce

4. **Data Decryption**: The system applies "AES-256bit-GCM algorithm to decrypt the financial data received" without an initialization vector.

## Key Security Features

The approach ensures **"perfect forward secrecy"** because ephemeral key pairs are valid only for each transaction session. Even if keys are compromised, previous communications remain secure since different nonces were used in each exchange.

This architecture maintains end-to-end encryption throughout the entire data journey from FIP to FIU backend systems.
