## 1. Library vs framework decision — VALIDATED, with refinements

**Verdict: build the small in-house library. Confirmed correct.** Rationale:

1. **Shape mismatch is decisive, not just license.** GE/Evidently/ydata/Frictionless model *tabular datasets / data packages* (columns, distributions, expectations over rows). The domain object here is a **per-video pipeline run = an ordered list of heterogeneous stages**, each with a free-form metrics blob and a verdict. Forcing that into a dataframe expectation suite is an impedance mismatch that would itself become a house of cards. The "config language" you actually want is "describe sections/fields/audience + declarative footgun→flag rules," which none of those tools express naturally.
2. **License is a hard gate** (ADR-005) and independently disqualifies Soda. The permissive primitives (pydantic/Jinja2/PyYAML/jsonschema) are already in-tree, so zero new license risk and near-zero new transitive surface.
3. **House-of-cards containment**: the in-house lib is ~6-8 small modules with a frozen typed envelope and pure renderers. It has no I/O coupling to either pipeline except a thin recorder API. That is *far* less fragile than wrapping a heavy framework whose upgrade cadence and API churn you don't control.

**Refinements / cautions to bake in:**
- **Do NOT vendor `json-schema-for-humans` or `yaml-to-markdown` into the core dependency closure.** Keep the core renderer set to hand-written Jinja2 templates (you control wording precisely, which the FAQ-debuggability eval *requires*). Treat those MIT renderers as optional dev-time helpers for generating the schema doc only, not runtime deps.
- **`jsonschema` is optional**: pydantic v2 already does validation and can emit JSON Schema (`model_json_schema()`). Use pydantic as the single source of truth for the envelope; only pull `jsonschema` if you need to validate *externally authored config files* against a published schema. Recommendation: defer `jsonschema` to Phase 2+, validate config with pydantic models first.
- **The "config language" must stay declarative-but-tiny.** Resist building a general expression engine. Use a *restricted, safe* rule grammar (see §2.4) — NOT `eval()`, NOT a DSL parser. A list of typed comparison clauses is enough for every footgun listed.


The spec is intentionally NOT Turing-complete. It can only: pick sections, tag audience, and evaluate restricted rule clauses.

### 2.4 Rule engine (`rules.py`) — restricted & safe

- A rule = `{code, severity, when:[clause], message, faq_ref}`.
- A clause = `{path, op, value}`. `path` is a dotted accessor into the serialized envelope (helper does safe nested `.get`, missing path → clause is False unless `op` is `is_missing`).
- Supported ops only: `eq, ne, gt, ge, lt, le, in, contains, is_missing, is_present, ne_path/eq_path` (compare two paths). NO arbitrary expressions, NO `eval`. Each op is a tiny pure function — trivially unit-testable.
- `when` = AND of clauses (keep simple; if OR ever needed, add a sibling `when_any`). Engine returns `list[Flag]`. Verdict derivation: any `error` → `fail`; any `warn` (no error) → `pass_with_warnings`; else `pass`.

This is the heart of "turn footguns into flags." Every flag carries `faq_ref` so the customer/technical report cross-references README/FAQ — the debuggability requirement.

## 5. README/FAQ-reader debuggability — concrete eval method

## 7. Risks & edge cases (and mitigations)

- **Report write must NEVER break the main run.** All recorder writes wrapped in try/except returning a result object; in main.py, write in a `finally`; a write failure logs a warning and is itself recorded as an `extras.report_write_error` on the next successful surface — but never raises. Add a test that injects an IOError and asserts the pipeline result is unaffected.
- **Remote videos / no local file (collector).** `io.py` resolves to `report.output_dir` or `reports/<video_id>/` when `local_path` is None/missing; `video_meta` carries `video_url`; never assume a local path. Covered by a dedicated test.
- **Schema versioning.** `SCHEMA_VERSION` in `identity`; renderers assert major-version compatibility. Bump = deliberate, with a changelog. Consumers pin a lib tag so a schema bump can't surprise them. Old JSON reports remain readable (additive fields only within a major).
- **Idempotency / overwrite vs append.** Default = overwrite per `run_id` (latest run wins next to the video) — keeps the convention clean and matches `add_video` INSERT-OR-REPLACE semantics. For audit/cross-run diff, support an optional `report.history_dir` that archives `<video_id>/<run_id>.json`. Compile, being a separate step, appends a compile stage to the existing report (read-modify-write) rather than overwriting the process report — or writes a sibling `*.compile.report.json`. Decide per repo; default to sibling files to avoid read-modify-write races.
- **Large reports.** `details` blobs (e.g. all candidate windows, full trajectory) can be big. Mitigation: cap list lengths in the technical renderer (e.g. first N + "…(M more)"), keep full data only in JSON, and provide a `report.max_detail_items` knob. Customer report never includes raw lists.
- **Cross-repo coupling (house of cards).** Tag-pin the lib in both repos; lib is pure (no IO at import, no network); a CI job in the lib repo runs both consumers' relevant tests against `HEAD` before tagging (contract test). A breaking lib change is caught before either repo bumps.
- **Twin-segmenter drift** (wasb_hybrid/tracknet_hybrid are copy-paste): if AI-timing threading is added (A5), apply to both; harvest-from-DB (A2) avoids touching them at all initially — prefer that.
- **video_id semantics differ** (indexer=file MD5, collector=human id): `identity.video_id_kind` records which, so cross-tool diffs don't silently mis-join. Documented in the envelope.
- **cwd-relative paths** (WASB `output/wasb`, manifest): harvest resolves against the run's configured output dir, not raw cwd, to avoid empty reports when run from a different directory.

## 7. Risks & edge cases

- **Report write must never break the run**: writes wrapped to return a result, called in `finally`; inject-IOError test asserts pipeline result unaffected.
- **Remote videos / no local file**: `io.py` resolves to `report.output_dir`/`reports/<video_id>/`; `video_meta.video_url` carried; dedicated test.
- **Schema versioning**: `SCHEMA_VERSION` in identity; renderers assert major compatibility; additive-only within a major; consumers pin a tag so a bump can't surprise them.
- **Idempotency**: default overwrite per latest run next to the video (matches `add_video` INSERT-OR-REPLACE semantics); optional `report.history_dir` archives `<video_id>/<run_id>.json` for diffing; compile (separate step) writes a sibling `*.compile.report.json` to avoid read-modify-write races.
- **Large reports**: cap list lengths in the technical renderer (first N + "…M more"); full data only in JSON; `report.max_detail_items` knob; customer report never includes raw lists.
- **Cross-repo coupling**: tag-pin + pure lib + a contract-test CI job in the lib repo that runs both consumers' relevant tests against `HEAD` before tagging.
- **Twin-segmenter drift**: prefer harvest-from-DB (A2) so you don't touch wasb/tracknet copies at all initially; if A5 lands, apply to both.
- **`video_id` semantics differ** (indexer file-MD5 vs collector human id): `identity.video_id_kind` records which so cross-tool diffs don't mis-join.
- **cwd-relative paths** (`output/wasb`): harvest resolves against the configured output dir, not raw cwd.
