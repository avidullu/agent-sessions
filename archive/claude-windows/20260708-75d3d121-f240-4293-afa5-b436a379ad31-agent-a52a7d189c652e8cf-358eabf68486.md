1199	+## 0. TL;DR
1200	+
1201	+The compile/stitch phase used to run **in-process on the CPU-only 2-vCPU control-plane**, where the
1202	+2026-07-08 live CUJ measured **~12m55s** for an 11-clip / ~80 s reel from a 1.83 GiB 4K source
1203	+(~45–90 s per ~7 s clip — the per-clip branding watermark forces a full 4K re-encode with **no
1204	+NVENC**). Validation (183 s) runs there too; both serialize on `_LOCAL_COMPUTE_LANE`, so one run pins
1205	+the control-plane for ~16 min → the API can't scale past a handful of concurrent users.
1206	+
1207	+#521 makes **where each pipeline phase runs a config edit, not a code change**, and moves the stitch
1208	+to the **L4 worker (NVENC + 8 vCPU)** the way detection already dispatches:
1209	+
1210	+1. **`deployment.phase_placement`** — a per-phase knob (`validation` / `segment` / `compile`) with
1211	+   values `control_plane | cloud_run_l4`. Unset ⇒ **today's placement, byte-identical**.

1213	+   control-plane resolves the reel's segments, stages a compile-spec to the bucket, dispatches
1214	+   `python -m backend.worker compile` on the L4, bucket-polls a done-marker, and returns the same
1215	+   `{status, filepath, download_url}` shape the SPA already expects.
1216	+3. **NVENC on the L4** — `deployment.cloud_stitch_encoder` (default `h264_nvenc`) is forwarded onto
1217	+   the worker's `stitching.encoder`; libx264 stays the everywhere-safe fallback (auto-probed).

1219	+The cloud-serving preset opts compile onto the L4 (`phase_placement.compile=cloud_run_l4`).

1223	+## 1. The placement model
1224	+

1226	+truth** — orchestration and the worker never re-derive the mapping. Precedence: an explicit

1228	+behaviour exactly:

1230	+| phase | knob unset (legacy default) | meaning |

1258	+## 2. compile → L4 dispatch (the flow)
1259	+
1260	+`orchestration._execute_compile` consults `resolve_phase_placement(cfg, "compile")`. When it resolves
1261	+to `cloud_run_l4` **and** cloud dispatch is available (`_cloud_available`), it calls
1262	+`_dispatch_compile_remote`; otherwise it stitches in-process via the shared `_stitch_reel` core
1263	+(unchanged).
1264	+
1265	+`_dispatch_compile_remote` (mirrors `_maybe_dispatch_remote`):
1266	+
1267	+1. **Resolve** the reel's segments HERE — the control-plane owns the DB (`_resolve_compile` →
1268	+   `(video, kept, out_name)`), applying the `stitching.min_shot_count` floor as before.
1269	+2. **Stage a compile-spec** to `<output_root>/_compile/<token>/spec.json` — the resolved
1270	+   `time_pairs`, the control-plane's resolved `stitching` config (watermark + padding, with `encoder`
1271	+   swapped to `cloud_stitch_encoder`), the source `video_uri`, `video_id`, `output_name`, `locale`.
1272	+   The worker therefore needs **no control-plane DB** — everything rides the spec.
1273	+3. **Dispatch** a `compile` Cloud Run Job execution (`CompileJobSpec` → `CloudRunCompute.run_compile`)
1274	+   running `python -m backend.worker compile --spec-uri … --done-uri … --set storage.output_root=…`,
1275	+   forwarding the bucket coordinates (the worker Job has no `DEPLOYMENT_PROFILE`).
1276	+4. **Bucket-poll** the done-marker at `<output_root>/_compile/<token>.done` — the SAME
1277	+   `_await_marker` machinery `run_infer` uses (crash-fast on a terminal-without-marker execution,
1278	+   rescue-or-cancel on a poll timeout). Distinct `_compile/` prefix so a compile and a detection for
1279	+   one bucket never collide on a marker.
1280	+5. The worker (`cmd_compile`) reads the spec, stitches the reel via the **shared `_stitch_reel`
1281	+   core** (no forked pipeline), mirror-uploads it to `<output_root>/highlights/<video_id>/<name>`,
1282	+   and writes the marker (rc + `download_url` + `reel_uri`).
1283	+6. The control-plane returns `{status, filepath, download_url, video_id}` — the reel is already in the
1284	+   bucket, so `/api/highlights` serves it via the existing signed-URL 307. On a worker rc≠0 →
1285	+   `status='failed'` with the worker's message (clean SPA verdict, never a crash).
1286	+
1287	+**Fallback:** if compile is placed on the L4 but the box isn't actually cloud-wired (no output bucket

1292	+## 3. NVENC on the L4 — and the D5/D16(b) parity note
1293	+
1294	+The dominant term in the CUJ stitch was the **per-clip 4K re-encode** the branding watermark forces
1295	+(~67 s/clip on 2 vCPU with libx264). The L4 has a hardware H.264/HEVC encoder, so #521 adds an encoder
1296	+knob:
1297	+
1298	+- `StitchingConfig.encoder` — `libx264` (default, CPU, works everywhere incl. CI) | `h264_nvenc` |
1299	+  `hevc_nvenc`. `VideoCompiler` **probes** the requested encoder once per run (a 1-frame lavfi test
1300	+  encode) and **falls back to libx264** if this ffmpeg build can't run it, so a misconfig / non-GPU
1301	+  box never breaks. All clips share the one chosen encoder → the concat stays `-c copy`.
1302	+- `deployment.cloud_stitch_encoder` (default `h264_nvenc`) — what the compile-dispatch forwards onto
1303	+  the worker's `stitching.encoder` for the L4 run. Set it to `libx264` to run the L4 stitch on CPU.
1304	+- The control-plane's **own** local stitch always uses `stitching.encoder` (libx264 by default) — the
1305	+  CP has no GPU.
1306	+
1307	+**Parity note (honest):** [README.md](./README.md) **D5/D16(b)** kept stitch **encode = libx264** to
1308	+protect a byte-exact stitch parity guarantee, and explicitly **deferred NVENC encode behind a config
1309	+knob, "revisit only if M7 cost data justifies relaxing parity."** The 2026-07-08 CUJ (~13 min stitch,
1310	+a hard scaling wall past ~5 concurrent users) **is** that cost data. #521 lands exactly the deferred
1311	+shape — NVENC **behind a config knob**, libx264 the default, config-reversible per phase. Enabling
1312	+NVENC relaxes byte-identity **at the reel ENCODE layer only** (a cosmetic, shareable artifact); the
1313	+**WINDOW/rally-level parity** (the analytical output) is untouched — detection and windowing are
1314	+unchanged. If bit-exact reels are ever required, set `cloud_stitch_encoder=libx264`.
1315	+
1316	+> Follow-up (tracked, not in #521's first cut): a **pre-rendered / overlay-filter watermark** so the
1317	+> stitch isn't a full re-encode at all (the deeper win beyond swapping the encoder).

1321	+## 4. Validation placement + the "nobody validates" guard
1322	+
1323	+`phase_placement.validation` moves the CPU-bound validator suite off the 2-vCPU control-plane too,
1324	+via the existing `--skip-validation` lever (#513):
1325	+
1326	+- **`control_plane`** (default): the control-plane runs the validators and is the authoritative gate;
1327	+  the worker **skips** its redundant re-validation (`skip_validation=True`) — today's #512/#513
1328	+  behaviour, byte-identical.
1329	+- **`cloud_run_l4`**: when detection **actually** dispatches to the L4, the control-plane **delegates**
1330	+  — it does NOT run the validator suite (`_execute_processing` skips it), and the dispatch carries
1331	+  **no** `--skip-validation`, so the **worker** validates and rejects a bad clip via a non-zero rc
1332	+  (surfaced as a failed job).
1333	+
1334	+**Footgun guard:** a clip can only be validated on the worker if the worker also **detects** it there.
1335	+Two protections:
1336	+
1337	+1. **Config-load guard** (`DeploymentConfig` model-validator): `validation=cloud_run_l4` requires the
1338	+   effective segment placement to also be `cloud_run_l4` (explicit, or via `compute_target=cloud_run`)
1339	+   — else config load fails with an actionable error.
1340	+2. **Runtime guard** (`_will_detect_on_cloud`): if a per-request `compute='local'` forces detection
1341	+   in-process (no worker), the control-plane **still validates** — never leave a clip unvalidated
1342	+   because nobody ran the gate.
