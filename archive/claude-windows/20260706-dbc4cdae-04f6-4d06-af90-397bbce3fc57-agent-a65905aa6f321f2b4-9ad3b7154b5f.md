## Summary

In PyTorch 2.6, the default for the `weights_only` argument of `torch.load` was changed from `False` to `True`. This is an important security improvement measure, though it is a backward compatibility-breaking change.

## What This Means

Previously, `torch.load` used `weights_only=False` by default, which uses the pickle module provided by Python. This breaking change is especially impactful for any `torch.load` calls that are not loading state_dicts of plain tensors.

## Impact

The change has broken the loading of some models, with errors like `_pickle.UnpicklingError: Weights only load failed`. When this error occurs, re-running `torch.load` with `weights_only` set to `False` will likely succeed, but it can result in arbitrary code execution.

## Workarounds

Users encountering this issue have two options:
1. Explicitly set `weights_only=False` when calling `torch.load()` (only if you trust the checkpoint source)
2. Use `torch.serialization.add_safe_globals()` or `torch.serialization.safe_globals()` to allowlist specific classes when loading with `weights_only=True`

## 2. `F.interpolate` / antialias resize vs `cv2.resize` — parity risk

This is the highest-risk area for your CPU-cv2 → GPU parity goal. **PyTorch does not guarantee numerical parity with OpenCV**, and the docs explicitly reference matching **Pillow**, not OpenCV:

- **Antialias matches Pillow, not OpenCV.** *"Using anti-alias option together with `align_corners=False`, interpolation result would match Pillow result for downsampling operation."* No OpenCV-matching claim is made for bilinear/bicubic. Source: https://docs.pytorch.org/docs/2.12/generated/torch.nn.functional.interpolate.html
- **Nearest mode is deliberately "buggy" to match old OpenCV.** *"Mode `mode='nearest'` matches buggy OpenCV's `INTER_NEAREST` interpolation algorithm."* and *"Mode `mode='nearest-exact'` matches Scikit-Image and PIL nearest neighbours interpolation algorithms and fixes known issues with `mode='nearest'`."* So `nearest` ≈ cv2 INTER_NEAREST, but `nearest-exact` does **not**. Same source.
- **align_corners default = False (None→False for linear modes).** *"If set to `True`, the input and output tensors are aligned by the center points of their corner pixels… Default: `None`. When `None` and `mode` is one of the linear modes, it is treated as `False`."* cv2 uses a half-pixel-center convention equivalent to `align_corners=False`, so leave it False — but this only removes one of several divergence sources. Same source.
- **Known non-parity for bicubic upsampling**, tracked upstream: PyTorch bicubic "does not follow opencv result," mainly when the output is larger. Sources: https://github.com/pytorch/pytorch/issues/94335 and https://github.com/pytorch/pytorch/issues/19650
- **Practical parity verdict:** For **bilinear downscale**, `F.interpolate(..., mode='bilinear', align_corners=False, antialias=True)` matches **PIL**, and cv2's `INTER_AREA`/`INTER_LINEAR` differ from PIL — so you should expect small per-pixel deltas vs cv2, not bit-exactness. Community benchmarks confirm PyTorch-GPU resize ≠ cv2 numerically. Sources: https://discuss.pytorch.org/t/is-there-any-differences-between-torch-nn-functional-interpolate-and-cv2-resize/37070 and https://www.simonwenkel.com/notes/software_libraries/opencv/resizing-images-using-nvidia-gpus-opencv-pytorch-tensorflow.html
- **Recommendation for parity:** If exact cv2 numerics are required, do not assume any GPU resize matches it. Options: (a) use **NVIDIA CV-CUDA**, which implements OpenCV-style interpolation semantics on GPU (closest to cv2 by design), or (b) empirically measure max/mean pixel diff on representative frames and confirm the downstream model output is within tolerance. ## 3. YUV→RGB / BGR color conversion on GPU — options and parity risk

- **Options:** (1) **NVIDIA DALI** `fn.color_space_conversion` (RGB↔BGR, RGB↔YCbCr, RGB↔Gray) and its decoders; (2) **CV-CUDA** cvtColor; (3) a **custom CUDA kernel**; (4) torchvision has no general `cvtColor` (it decodes to RGB and lacks arbitrary color-matrix conversion). DALI source: https://docs.nvidia.com/deeplearning/dali/user-guide/docs/operations/nvidia.dali.fn.color_space_conversion.html
- **Color-standard parity is a real risk.** DALI decodes YCbCr using **ITU-R BT.601**: when decoding to YCbCr, "the image will be decoded to RGB and then converted to YCbCr, following the YCbCr definition from ITU-R BT.601." Source: https://docs.nvidia.com/deeplearning/dali/user-guide/docs/operations/nvidia.dali.fn.decoders.image.html . OpenCV's `cvtColor` YUV/YCrCb paths also use **BT.601** coefficients (Y[16,235], U/V[16,240] centered 128) — see https://docs.opencv.org/4.x/de/d25/imgproc_color_conversions.html
- **The specific traps:**
  - **BT.601 vs BT.709:** HD video is usually **BT.709**; SD is BT.601. If a GPU decoder (NVDEC) applies BT.709 or reads the stream's colorimetry metadata while your reference cv2 pipeline hard-codes BT.601 (`cv2.COLOR_YUV2BGR`), colors diverge. Background: https://forum.videohelp.com/threads/395345 and the NVIDIA ColorSpace.cu thread https://forums.developer.nvidia.com/t/question-about-yuv-matrix-in-colorspace-cu/284692

- **Verdict:** Match **three things** to cv2 — the **matrix (BT.601 vs 709)**, the **range (limited vs full)**, and rounding. NVDEC-based decoders may auto-select the matrix from container metadata, which cv2 does not; that is the most likely source of a silent color mismatch. **Verify** on real frames.

## 5. torch 2.x + CUDA 12.x — loading torch 1.11 checkpoints, and the torch 2.6 `weights_only` flip

- **Plain state_dict from torch 1.11 → torch 2.x is generally safe.** PyTorch's serialization format for tensor `state_dict`s is stable across the 1.x→2.x boundary; a plain `dict[str, Tensor]` loads fine. This is exactly the case the new default was designed to preserve: *"`state_dict`s of plain `torch.Tensor`s should be loadable seamlessly."* Source: https://dev-discuss.pytorch.org/t/bc-breaking-change-torch-load-is-being-flipped-to-use-weights-only-true-by-default-in-the-nightlies-after-137602/2573
- **The torch 2.6 breaking change:** PyTorch 2.6 (released **January 29, 2025**) flipped `torch.load`'s `weights_only` default from `False` to `True`. *"Also in this release as an important security improvement measure we have changed the default value for `weights_only` parameter of `torch.load`. This is a backward compatibility-breaking change…"* Source: https://pytorch.org/blog/pytorch2-6/
- **What breaks — directly relevant to a `.pth.tar`:** `weights_only=True` *"rewrites the stack machine of the unpickler to ensure that no modules/functions are imported and only certain allowlisted classes/functions (necessary for loading `state_dict`s of plain tensors) are called."* Consequently: *"Loading serialized `nn.Module`s… will now explicitly fail"* and *"Tensor subclasses, serialized numpy arrays and other objects will require the user to use `safe_globals`…."* Source: the dev-discuss forum post above.
  - **Why a `.pth.tar` specifically can break:** `.pth.tar` checkpoints commonly wrap the state_dict in a dict that **also** contains non-tensor objects — `argparse.Namespace`, numpy scalars/arrays (e.g. `best_acc1`), optimizer state, or a pickled full `nn.Module`. Those top-level objects are exactly what `weights_only=True` refuses to unpickle, so `torch.load('model.pth.tar')` raises `UnpicklingError: Weights only load failed`. Real-world breakage examples: https://github.com/MIC-DKFZ/nnUNet/issues/2681 , https://github.com/Lightning-AI/pytorch-lightning/issues/20643 , https://github.com/huggingface/accelerate/issues/3539
  - **Fixes:** (a) `torch.load(path, weights_only=False)` **only if you trust the file**; (b) preferred — `torch.serialization.add_safe_globals([...])` / `with torch.serialization.safe_globals([...])` to allowlist the specific classes (e.g. `argparse.Namespace`, `numpy.core.multiarray._reconstruct`); or (c) if you only need the weights, extract just the tensor sub-dict. Source: same forum post + https://pytorch.org/blog/pytorch2-6/
