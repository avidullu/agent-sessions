The rally detection pipeline is largely robust, but a deep code review highlighted three minor edge cases/bugs: a potential divide-by-zero or zero-spread in `_spread` for tiny sequences, a density calculation vulnerability for sparse tracks in `_trim_inactive_tail`, and silent skipping of malformed rows in the CVAT parsing script. ## 1. Problem & goal
The current implementation of the candidate windowing handles normal inputs extremely well (including handling blobs), but could fail or behave erratically under specific conditions:

**Goal**: Fix these three issues to harden the rally detection and ingestion pipelines without changing the existing heuristic thresholds. 

## 4. Design / architecture
The changes will be entirely localized to the identified functions:
- `rally_gate.py`: Modify `_spread` to use `math.ceil()` or properly enforce a minimum subset size before trimming percentiles, ensuring it never inadvertently calculates a spread of 0 for non-identical values.
- `tracknet_runner.py`: Update `_trim_inactive_tail` to factor the *temporal length* (or total expected frames in the trailing window) into the density calculation, rather than purely relying on `win_count` (the number of visible frames). 
- `rally_cvat.py`: Introduce `logger.warning` before the `continue` statement in `load_canonical_csv` to surface skipped rows during CVAT ingestion.

This will NOT change the core AI validation (Phase 3) or the existing `velocity_thresh` values. It solely tightens up boundary calculation edge cases. It will not suddenly "fix" rallies that the tracking model missed entirely due to lighting or occlusion.

# Rally Detection Code Review

## 1. How Rally Detection Works

The project identifies rallies through a combination of local trajectory tracking (e.g., TrackNet or WASB) and a series of heuristic gating/trimming rules, culminating in an AI-based refinement (Phase 3). Here's a breakdown of the pipeline:

### Phase 2: Candidate Windowing (The Heuristics)
1. **Velocity Thresholding:** The trajectory detector outputs `(Frame, Visibility, X, Y)`. For each visible frame, the normalized velocity (distance divided by frame width per second) is calculated. Frames with a velocity exceeding `velocity_thresh` (e.g., 0.02) are considered "active" (meaning the shuttle is in flight).
2. **Merging / Grouping:** Active frames within a certain dead time (`merge_gap`, usually 2.0s) are merged into candidate windows.
3. **Splitting Over-merged Windows (W1):** If a window exceeds `max_window_duration`, the code splits it at the largest internal gap (dead-time) that is at least `min_split_gap`. If the window lacks gaps (the shuttle never stops moving), a `window_hard_cap` setting (if enabled) forcibly chops it in half at the temporal midpoint.
4. **Inactive Tail Trimming (R4):** Even after a rally finishes, a player might pick up the shuttle and toss it, creating a slow-moving trajectory tail. To prevent the window from overextending, the algorithm trims the end back to the last segment of the window that had a dense cluster of "fast" frames (velocity > `rally_thresh`).
5. **Blob Fallback (R5):** If a window still vastly exceeds the cap after the W1 split and R4 trim (meaning it's an unusually continuous blob of motion), it is chopped down to the maximum cap limit and marked with a `forced_cut` flag. This signals that the clip needs "rally-state" cues (like net-crossings) rather than a simple duration cap.
6. **Rally Gate (Gate A):** In `rally_gate.py`, a heuristic filters out "false" rallies (like a player tossing a shuttle back to their opponent). It estimates the net position (median play axis coordinate) and counts how many times the shuttle crosses the net. A valid rally must have `min_crossings` (e.g., 2).

### Phase 3: AI Handoff
Valid candidate windows are padded (e.g., by 2 seconds on each end) and sent to a Generative AI Provider (like Gemini) along with a sports-specific prompt. The AI confirms the semantic boundaries, ensuring the window correctly matches a true rally, and also attempts to count the shuttle exchanges.

## 2. Deep Code Review & Potential Issues Found

I performed a deep review of `tracknet_runner.py`, `trajectory_hybrid.py`, `rally_gate.py`, and the parsing logic in `sports-data-collector`. Here are the findings and hidden issues:

### A. Subtle Calculation Artifact in `_spread` (`rally_gate.py`)
**Observation:** The `_spread` function calculates a robust spread (ignoring the bottom 5% and top 5% of coordinates to eliminate outliers):
`lo = s[max(0, int(0.05 * (len(s) - 1)))]`
`hi = s[min(len(s) - 1, int(0.95 * (len(s) - 1)))]`

**Hidden Behavior:** Because `int()` truncates rather than rounds, for very short arrays (e.g., `< 20` items), the 95th percentile will simply be the second-to-last item, and for `len(s) == 2`, the spread evaluates to strictly `0.0`. 

**Impact:** This doesn't crash the pipeline, because the play axis is correctly estimated over the *entire* video's thousands of trajectory points. However, if this utility function is reused on small window slices in the future, it will quietly collapse the spread to zero.

### B. Sensitivity to Sparse Tracking in `_trim_inactive_tail` (`tracknet_runner.py`)
**Observation:** The inactivity trimmer identifies the end of a rally by looking for the last frame where the trailing `trail_frames` window has a sufficient density of fast-moving frames (`fast_sum / win_count >= min_density`).

**Hidden Issue:** `win_count` represents the number of *visible, active frames* in that time boundary, rather than the total elapsed time. If the detector completely loses track of the shuttle for 1.8 seconds and only picks up 1 fast frame right at the end of the window, `win_count` will be very low (e.g., 1 or 2). Consequently, `fast_sum / win_count` could easily evaluate to 1.0 (100% density).

**Impact:** Sparse tracking points at the very end of a clip might prevent the tail trimmer from cutting off dead-time correctly, artificially inflating the end of the candidate window. This is somewhat mitigated by the `merge_gap` breaking trajectories, but it remains a boundary logic quirk.

### C. Graceful Degradation on Incomplete CSV Validation (`rally_cvat.py` in `sports-data-collector`)
**Observation:** The `parse_cvat_boxes` function searches zip files for an `.xml` ending in `annotations.xml` or, failing that, *any* `.xml`.

**Issue:** In `load_canonical_csv()`, `safe_int()` is used to catch malformed `rally_number` fields. If a row is entirely malformed (but doesn't break the CSV parsing), it just `continue`s silently. While this provides stability, a severely malformed CSV might silently drop half its rallies without failing the import gate. Logging a warning for skipped rows would improve observability.

### D. Safe Slicing in the W1/R5 Blob Splitters
The W1/R5 gap-splitters use a recursive worklist:
`split_i = TrackNetRunner._midpoint_split_index(h)`
`work.append(h[:split_i]); work.append(h[split_i:])`

Because it explicitly enforces `len(h) < 2` before splitting, `split_i` will always be at least 1, meaning the code safely guarantees it will never enter an infinite loop of empty arrays. This is an excellent, defensively written chunk of code.
