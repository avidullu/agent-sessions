## What / why

Fixes audit finding **R1-18** (AUDIT_REPORT_khelsutra-guru_2026-07-02) on `backend/storage/gdrive_api.py` — two latent hazards on the Drive-API storage hot path before the reel round-trip goes live:

1. **Whole-file RAM buffering on download.** `fetch_to_local` did `get_media().execute()`, materializing the entire object as one `bytes` value — an OOM waiting to happen for a multi-GB source/reel on a memory-limited Cloud Run box. It now streams via `googleapiclient.http.MediaIoBaseDownload` in bounded **32 MiB chunks** (lazy import behind a `_downloader` seam, mirroring the existing `_media_body` seam/convention). The stream writes to a `dst + ".part"` sibling and `os.replace`s into place, so a mid-download failure can never leave a truncated `dst` that a later `overwrite=False` call would trust as complete.

2. **Delete-before-upload data-loss window in `put()`.** A re-put deleted the existing file at the path and only then ran `files().create(...)` — if the resumable create failed (network/quota), the reel was gone at both ends. Per the audit verifier's refinement, re-puts now overwrite **in place** via `files().update(fileId=existing, media_body=...)`: the old bytes survive until the new upload succeeds, the Drive file id is preserved across re-puts, and no duplicate-`(name, parent)` window opens (which a create-first-then-delete ordering would, given path resolution returns the first match among duplicates). Fresh paths still `files().create(...)`. The **idempotent-put contract from PR #338** (exactly one file per path, latest bytes win) is preserved and still covered by the pre-existing test.

No config knobs, no behavior change for callers: same `StorageBackend` interface, same idempotence semantics — only the failure modes improve.
